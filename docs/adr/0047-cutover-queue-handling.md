# [ADR-0047] 컷오버 · 되돌리기에서 큐 메시지를 잃지 않는 규칙

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-11-07
* **관련 (Related):** T46 #698, T12 #22, T20 #30, 설계 8.6 · FR-9 · NFR-3, ADR-0011(cutover-executor-execution-and-failure) · ADR-0013(executor-workload-access) · ADR-0016(failback-replication-path-check) · ADR-0045 · ADR-0046

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 출발지에서는 SQS → Lambda가, 목적지에서는 SQS 호환 서버 → 실행기가 메시지를 처리하고 결과를 업무 DB에 쓴다. 큐는 업무 DB 밖에 있어 논리 복제로 옮겨지지 않는다(ADR-0046). Executor는 컷오버와 되돌리기를 같은 단계로, 방향만 바꿔 실행한다.
* **문제:** 지금 Executor는 큐를 모른다. 세 가지가 문제가 된다.
  * 진입점 쓰기 차단은 요청 시작에서만 확인되므로(demo-chat `require_writable`), 차단 직전에 통과한 요청의 메시지가 늦게 도착할 수 있다.
  * 컷오버 뒤 출발지 앱이 실제 SQS에 보낸 메시지는 트리거가 꺼져 있으면 처리되지 않는다.
  * 상태를 모를 때 아무것도 자동으로 열지 않는다는 SAFE_HOLD 규칙과 트리거 복원이 충돌할 수 있다.
* **목표:** 큐 의존성이 있는 계획에서 이벤트 결과의 유실 · 중복을 0으로 하고, 큐 의존성이 없는 계획의 동작은 바꾸지 않는다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 떠나는 쪽 큐를 비우고 DB로 완결성을 확인

진입점 차단 뒤 떠나는 쪽 소비자가 남은 메시지를 처리하고, 쓰기가 멈춘 뒤 DB 대조로 모든 메시지에 결과가 있는지 확인한다.

**Pros**
* 메시지 이동이 없어 중복이 생기지 않는다. 판정이 결정적이다.

**Cons**
* 비우는 시간이 쓰기 정지 시간에 더해진다. 실패 메시지는 재전달까지 기다린다.

### 2. 떠나는 쪽에 남은 메시지를 도착하는 쪽 큐로 옮김

**Pros**
* 쓰기 정지 시간 영향이 작다.

**Cons**
* 옮기는 중 실패하면 중복 · 유실 판단이 어렵다. 출발지 AWS 쓰기 권한(메시지 삭제)이 필요하다.

## 3. 결정 사항 (Decision Outcome)

* **소비자 정지 규칙은 방향과 무관하게 하나로 둔다.** 도착하는 쪽 소비자는 진입점 차단과 함께 멈춘다. 떠나는 쪽 소비자는 자기 큐를 처리한 뒤 멈춘다(출발지 Lambda는 이벤트 소스 매핑 끄기, 실행기는 정지 스위치). 컷오버에서는 AWS가, 되돌리기에서는 온프렘이 떠나는 쪽이다.
* **완결성은 DB 대조로 판정한다.** 펜싱 뒤 업무 이벤트마다 결과 행이 있거나 실패 보관 큐에 있음을 확인한다. 맞지 않으면 전환 확정 전이므로 ABORT_PRE_WRITE로 끝낸다. 큐 지표(대기 · 처리 중 수)는 진행 판단에만 쓰고 완결성 판정에 쓰지 않는다.
* **상태 확인 실패는 기존 규칙을 따른다.** 효과를 되돌릴 수 있음이 확인되면 ABORT_PRE_WRITE에서 출발지 LOGIN · RESUME과 함께 떠나는 쪽 트리거를 다시 켠다. 상태를 확인할 수 없으면 SAFE_HOLD로 멈추고 트리거는 꺼 둔다.
* **큐 단계는 Edge가 출발지에 새 요청을 보내지 않는 상태에서만 시작한다.** 컷오버 뒤에도 출발지 큐 잔량을 관측해 기록하고, 0이 아니면 알린다.
* **실행기 정지는 앱과 다른 선택자의 정지 스위치로 한다.** Executor의 exec 대상 · 권한(ADR-0013 executor-workload-access)에 실행기 Pod를 추가한다. 앱 라벨을 공유하지 않는다.
* **Executor의 출발지 AWS 권한은 큐 상태 읽기와 이벤트 소스 매핑 켜기 · 끄기 · 조회로 한정한다.** 메시지 삭제 · 큐 변경 권한은 주지 않는다.
* **큐 단계는 계획에 큐 의존성이 등록된 경우에만 돈다.** 큐 의존성이 인벤토리에 있는데 Executor 설정에 없으면 사전 확인에서 실패한다. 큐 의존성이 없는 계획은 지금과 같다.
* **옵션 2(옮기기)는 옵션 1의 실측 쓰기 정지 시간이 5초를 넘을 때 다시 검토한다.**

**이유**
* 업무 쓰기를 받는 DB는 최대 하나, 상태가 불명확하면 쓰기를 열지 않는다는 원칙(설계 8.6, NFR-3)을 큐에도 그대로 적용한다.
* 방향 무관 규칙이어야 같은 단계를 방향만 바꿔 쓰는 Executor 구조(ADR-0016)와 맞는다.
* DB 대조는 큐 지표의 지연 · 근사치와 무관하게 유실을 잡는다.

## 4. 결과

* Executor 사전 확인 · 진입점 · 펜싱 · 해제 단계와 되돌리기에 큐 처리 단계가 추가된다. 해피패스 검증 뒤, 기존 모의 환경 시험 결과와 함께 병합한다.
* 이벤트 결과 테이블의 복제 · 비교 대상 추가와 GATE 데이터 준비 대상은 계획(배포) 단위로 두며, T8 · T13 · T19 담당과 합의한 뒤 반영한다.
* 출발지 Lambda와 목적지 실행기는 앱과 같은 DB 역할(`chat_app`)과 경로를 쓰고, 한 이벤트의 DB 작업은 짧은 트랜잭션 하나로 끝낸다. 펜싱 · 긴 트랜잭션 판정 범위를 바꾸지 않기 위해서다.
* ADR-0013(executor-workload-access) 개정이 필요하다.
