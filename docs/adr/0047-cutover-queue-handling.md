# [ADR-0047] 컷오버 · 되돌리기에서 큐 메시지를 잃지 않는 규칙

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-11-07
* **관련 (Related):** T46 #698, T12 #22, T20 #30, 설계 8.6 · FR-9 · NFR-3, ADR-0011(cutover-executor-execution-and-failure) · ADR-0013(executor-workload-access) · ADR-0016(failback-replication-path-check) · ADR-0045 · ADR-0046

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 출발지에서는 SQS → Lambda가, 목적지에서는 SQS 호환 서버 → 실행기가 메시지를 처리하고 결과를 업무 DB에 쓴다. 큐는 업무 DB 밖에 있어 논리 복제로 옮겨지지 않는다(ADR-0046). Executor는 컷오버와 되돌리기를 같은 단계로, 방향만 바꿔 실행한다.
* **문제:** 지금 Executor는 큐를 모른다. 세 가지가 문제가 된다.
  * 진입점 쓰기 차단은 요청 시작에서만 확인되므로(demo-chat `require_writable`), 차단 직전에 통과한 요청의 메시지가 늦게 도착할 수 있다.
  * 컷오버 뒤 출발지 앱이 실제 SQS에 보낸 메시지는 트리거가 꺼져 있으면 처리되지 않는다.
  * 상태를 모를 때 아무것도 자동으로 열지 않는다는 SAFE_HOLD 규칙과 트리거 복원이 충돌할 수 있다.
* **목표:** 큐 의존성이 있는 계획에서 이벤트 결과의 유실 · 중복을 0으로 하고, 큐 의존성이 없는 계획의 동작은 바꾸지 않는다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 떠나는 쪽 큐를 비우고 DB로 완결성을 확인

진입점 차단 뒤 떠나는 쪽 소비자가 남은 메시지를 처리하고, 쓰기가 멈춘 뒤 DB 대조로 모든 메시지에 결과가 있는지 확인한다.

**Pros**
* 메시지 이동이 없어 중복이 생기지 않는다. 판정이 결정적이다.

**Cons**
* 비우는 시간이 쓰기 정지 시간에 더해진다. 실패 메시지는 재전달까지 기다린다.

### 2. 떠나는 쪽에 남은 메시지를 도착하는 쪽 큐로 옮김

**Pros**
* 쓰기 정지 시간 영향이 작다.

**Cons**
* 옮기는 중 실패하면 중복 · 유실 판단이 어렵다. 출발지 AWS 쓰기 권한(메시지 삭제)이 필요하다.

## 3. 결정 사항 (Decision Outcome)

* **양쪽 소비자 모두 자기 큐를 비운 뒤 멈춘다(옵션 1).** SHIFT 뒤에는 새 메시지가 대부분 도착하는 쪽 큐에 있으므로, 도착하는 쪽을 비우지 않고 멈추면 부하가 있는 컷오버는 거의 매번 결과 없는 이벤트를 남긴다. 그래서 떠나는 쪽 · 도착하는 쪽을 가리지 않고 둘 다 비운다. 비용은 비우는 시간만큼 쓰기 정지 시간이 늘어나는 것이고, 이 시간은 기존 쓰기 정지 예산(`write_pause_budget_ms`, ADR-0011) 안에서만 기다린다.
* **큐 단계의 위치는 Executor 9단계(precheck · entry · pause · fence · compare · commit · reconnect · release · persist)에 고정한다.**
  * **1 precheck:** 계획에 큐 의존성이 등록돼 있으면 양쪽 소비자 상태(출발지 이벤트 소스 매핑, 목적지 실행기 정지 스위치)와 실패 보관 큐 설정을 읽는다. 읽지 못하면 시작하지 않는다.
  * **2 entry 뒤, 3 pause 전:** 양쪽 소비자를 켠 채 두고, 각 큐의 대기 메시지 수(`ApproximateNumberOfMessages`)와 처리 중 메시지 수(`ApproximateNumberOfMessagesNotVisible`)가 모두 0이 될 때까지 기다린다. 그다음 소비자를 끄고 처리 중 0을 다시 확인한다. 출발지는 이벤트 소스 매핑 `State=Disabled`와 처리 중 메시지 수 0, 목적지 실행기는 정지 스위치 응답의 `in_flight` 0이다. 끈 뒤에 도착한 메시지(차단 직전 요청의 늦은 송신)는 완결성 판정이 ABORT_PRE_WRITE로 잡는다. Lambda · 실행기는 앱과 같은 PgBouncer 경로로 쓰므로, 이 확인이 PAUSE 전에 끝나야 처리 중 쓰기가 PAUSE에 걸려 시간 초과 · 재전달로 이어지지 않는다. 예산 안에 0이 되지 않으면 ABORT_PRE_WRITE다.
  * **5 compare 뒤, 6 commit 전:** 완결성을 DB로 판정한다(아래).
  * **8 release 뒤:** 양쪽 소비자를 다시 켠다. 7 reconnect 뒤 양쪽 PgBouncer는 새 쓰기 DB 하나만 가리키므로, 두 소비자가 함께 돌아도 쓰기 DB는 하나다. 떠나는 쪽 소비자는 Edge가 그쪽으로 요청을 보내지 않게 된 뒤에도 남은 메시지를 처리한다.
* **되돌리기도 같은 단계를 방향만 바꿔 쓴다.** 되돌리기에서 Edge 복귀는 Executor 뒤에 일어난다(ADR-0022). 2 entry가 양쪽 진입점을 막으므로 Executor가 도는 동안 새 메시지는 거의 생기지 않고, 차단 직전 요청이 늦게 보낸 메시지가 생기면 완결성 판정이 잡는다. 8 release 뒤 Edge 복귀까지 목적지 앱이 보내는 메시지는 다시 켠 목적지 실행기가 처리한다. 그래서 Edge 복귀 전 잔량을 따로 처리하는 단계가 필요 없다. 떠나는 쪽 소비자를 끄는 일은 떠나는 쪽 정리 단계에서 그쪽 큐가 빈 것을 확인한 뒤 한다(이 ADR 범위 밖). Edge 쪽 순서는 T17 · T20 담당과 구현 PR에서 대조한다.
* **완결성은 DB 대조로 판정한다.** 5 compare 뒤 업무 이벤트마다 결과 행이 있거나, 그 이벤트 ID가 그쪽 실패 보관 큐에 있음을 확인한다. 맞지 않으면 전환 확정 전이므로 ABORT_PRE_WRITE로 끝낸다. 큐 지표(대기 · 처리 중 수)는 진행 판단에만 쓰고 완결성 판정에 쓰지 않는다.
* **실패 보관 큐는 그 큐에서만 `ReceiveMessage`로 읽는다.** 메시지를 지우거나 옮기지 않는다. 한 번에 최대 10개만 받고, 짧은 폴링은 일부 서버만 표본으로 보므로 가시성 시간 0으로는 같은 메시지가 반복돼 10개를 넘는 큐를 다 볼 수 없다. 그래서 짧은 가시성 시간(예: 30초)과 긴 폴링(`WaitTimeSeconds` > 0)으로 빈 응답이 올 때까지 한 번 훑고, 모은 메시지 수가 큐의 대기 · 처리 중 수 합보다 적으면 확인할 수 없는 것으로 보고 ABORT_PRE_WRITE로 끝낸다. 훑은 메시지는 가시성 시간 동안 다른 수신자에게 보이지 않고 수신 횟수가 는다. 실패 보관 큐에 자체 재전달 설정(RedrivePolicy)이 있으면 수신 횟수 증가가 이동을 일으킬 수 있으므로 1 precheck에서 거부한다.
* **상태 확인 실패는 기존 규칙을 따른다.** 효과를 되돌릴 수 있음이 확인되면 ABORT_PRE_WRITE에서 출발지 LOGIN · RESUME과 함께 양쪽 소비자를 원래 상태로 다시 켠다. 상태를 확인할 수 없으면 SAFE_HOLD로 멈추고 소비자는 꺼 둔다. SAFE_HOLD가 SQS 보존 기간보다 길어지면 메시지가 사라질 수 있으므로, SAFE_HOLD 기록에 큐별 가장 오래된 메시지 시각을 남기고, 그 메시지의 나이가 보존 기간의 절반을 넘으면 경보한다.
* **8 release 뒤 소비자를 다시 켜지 못하면 전환은 되돌리지 않는다.** 6 commit 뒤라 ABORT_PRE_WRITE는 불가하고, 쓰기 DB는 이미 하나라 데이터는 안전하다. 메시지는 큐에 남아 처리가 늦어질 뿐이다. 영수증에 큐별 재개 실패와 사유를 남기고 경보하며, 실행 기한 안에서 재개를 다시 시도한다. 기한 안에 켜지 못하면 운영자가 재개한다.
* **컷오버 뒤에도 출발지 큐 잔량을 관측해 기록하고, 0이 아니면 알린다.**
* **실행기 정지는 앱과 다른 선택자의 정지 스위치로 한다.** 앱 라벨을 공유하지 않는다. 정지 스위치를 exec로 부르면 ADR-0013(executor-workload-access)의 exec 범위가 넓어지므로, ConfigMap 플래그나 scale 방식과 비교해 Executor 구현 PR에서 정한다.
* **Executor의 출발지 AWS 권한은 큐 상태 읽기, 이벤트 소스 매핑 켜기 · 끄기 · 조회, 실패 보관 큐 한정 `ReceiveMessage`로 한정한다.** 메시지 삭제 · 큐 변경 권한은 주지 않는다. 자격은 웹 신원(OIDC)으로 받는 단기 자격이며 장기 키를 쓰지 않는다. `lambda:UpdateEventSourceMapping`은 `Enabled`만 바꾸도록 IAM으로 강제할 수 없으므로, 리소스를 해당 매핑 UUID의 ARN으로 한정하고 `lambda:FunctionArn` 조건을 건다.
* **큐 단계는 계획에 큐 의존성이 등록된 경우에만 돈다.** 큐 의존성이 인벤토리에 있는데 Executor 설정에 없으면 사전 확인에서 실패한다. 큐 의존성이 없는 계획은 지금과 같다.
* **옵션 2(옮기기)는 옵션 1의 실측 쓰기 정지 시간이 5초를 넘을 때 다시 검토한다.**

**이유**
* 업무 쓰기를 받는 DB는 최대 하나, 상태가 불명확하면 쓰기를 열지 않는다는 원칙(설계 8.6, NFR-3)을 큐에도 그대로 적용한다.
* 방향 무관 규칙이어야 같은 단계를 방향만 바꿔 쓰는 Executor 구조(ADR-0016)와 맞는다.
* DB 대조는 큐 지표의 지연 · 근사치와 무관하게 유실을 잡는다.

## 4. 결과

* Executor 사전 확인 · 진입점 · 펜싱 · 해제 단계와 되돌리기에 큐 처리 단계가 추가된다. 해피패스 검증 뒤, 기존 모의 환경 시험 결과와 함께 병합한다.
* 이벤트 결과 테이블의 복제 · 비교 대상 추가와 GATE 데이터 준비 대상은 계획(배포) 단위로 두며, T8 · T13 · T19 담당과 합의한 뒤 반영한다. 결과 테이블이 복제 publication에 없으면 1 precheck에서 실패한다.
* 큐 기능을 켠 계획은 Exit Drill에서 `AWS_ENDPOINT_URL_SQS` 판정이 정해질 때까지 UNKNOWN이다(ADR-0017, ADR-0045 4절). 데모 Exit Drill 장면은 큐 기능을 켜지 않은 계획으로 보여 준다.
* 출발지 Lambda와 목적지 실행기는 앱과 같은 DB 역할(`chat_app`)과 경로를 쓰고, 한 이벤트의 DB 작업은 짧은 트랜잭션 하나로 끝낸다. 펜싱 · 긴 트랜잭션 판정 범위를 바꾸지 않기 위해서다.
* ADR-0013(executor-workload-access) 개정이 필요하다.
