# ADR-0006 모델 제공자와 S2 실패 분석의 책임

* **상태:** 제안됨(Proposed). 2026-11-03 사용자 지시에 따른 구현·설계 PR이며 팀 채택으로 표시하지 않는다.
* **날짜:** 2026-11-03
* **관련:** T7, T10, T11, T15, T19, T31. 정본 v0.2의 8.3을 v0.3으로 제안한다.

## 1. 회의와 정본을 다시 대조한 이유

[11/2 21:00 회의록](https://app.notion.com/p/40b8bee9ada4800785ead22138aecd9e)의 10절에서는 류지환이 CI·DB 등 역할 세분화를 질문했고, 배규태는 리허설이 핵심이며 필요하면 나눌 수 있다고 답했다. 따라서 v0.2의 ‘별도 CI 에이전트를 두지 않는다’는 현재 구성이고, 모든 역할 분리를 영구 금지한 팀 결정으로 읽지 않는다. 이번에는 S2의 실패 분석과 수정 제안 모듈만 나누며 별도 감독자·큐·DB는 추가하지 않는다.

회의록 11절(57:08 부근)의 Bedrock은 **고객이 사용하는 클라우드 AI 의존성을 이전하는 사례**였다. 환경 변수 변경으로 충분한지, Claude SDK 같은 호출 인터페이스로 바꿀지, 자체 모델 호스팅까지 할지 논의했지만 결론은 미정이다. 플랫폼 워커의 기본 모델을 Bedrock으로 정했다는 근거가 아니다. 12절의 류지환 역할은 병합·E2E 지원과 AWS/GCP 계정 제공이다.

v0.2 정본과 T11은 Claude Agent SDK를 적고 있었다. 11/3 사용자는 모델 호출을 OpenAI 위주로 진행하고 Bedrock은 더 논의하라고 지시했다. 이 차이를 숨기지 않고 이전 문서를 보존하고 설계·태스크·구현을 같은 PR에서 제안한다. 회의 댓글이나 개인 요청을 이미 완료된 팀 합의로 표시하지 않는다.

## 2. 서로 다른 세 결정

| 결정 | 이번 제안 | Bedrock과의 관계 |
|---|---|---|
| 플랫폼 프로세스를 어디에 두나 | AWS에서 검증, T7 운영 배치는 별도 완료 기준 | AWS 호스팅만으로 Bedrock 호출이 필요해지지 않는다 |
| 우리 제안 워커가 어떤 모델을 호출하나 | OpenAI Responses 기본, 모델 ID는 운영자가 명시 | Bedrock 등록·권한 확대·자동 fallback을 하지 않는다 |
| 고객 앱의 AI 의존성을 어떻게 이전하나 | 후속 시나리오로 범위·수용 기준부터 결정 | Bedrock API·IAM·세션·도구 동작을 식별하는 고객 어댑터 후보 |

SDK 프로세스를 온프렘에서 실행해도 모델을 외부 API로 호출하면 추론과 전송 데이터가 온프렘에 머무르는 것은 아니다. 고객 데이터 반출 제약, 허용 모델·지역, 세션 연속성, 도구 호출 호환성을 각각 수용 기준으로 정해야 한다.

## 3. 고려한 옵션과 선택

1. **OpenAI Responses 기본:** 사용자 지시와 맞고 두 함수 도구를 직접 제공해 실행 권한을 좁힐 수 있다. 제공자 API 인증과 별도 청구 관리가 필요하다. 이를 선택한다.
2. **Claude SDK 기본 유지:** 기존 문서와 같지만 최신 요청과 어긋난다. 선택 설치 어댑터로 남기며 자동 대체 호출은 하지 않는다.
3. **Bedrock 기본:** AWS IAM·청구 경로에 맞출 수 있으나 모델 접근·지역·사용 조건·지원 기능을 별도로 확인해야 한다. 고객 이전 시나리오와 플랫폼 모델 결정을 혼합하지 않고 보류한다.

AWS 공식 문서상 일부 Anthropic 경로는 최초 사용 등록이 필요하고, 최초 호출이 Marketplace 구독 절차를 시작할 수 있다. 이번 보류 중에는 등록·구독·실제 Bedrock 호출을 수행하지 않는다. [AWS 모델 접근 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)

## 4. 유지하는 책임과 가드레일

- 결정적 조정기가 run/source/proposal/attempt 결속과 최대 3회 시도를 관리한다. 불명 결과는 NEEDS_HUMAN이다.
- 워커는 허용 소스의 `repo.read`와 구조화된 `plan.propose`만 쓴다. OpenAI 함수 이름은 `repo_read`, `plan_propose`이며 두 경로 모두 같은 정책 핸들러를 거친다. [OpenAI 함수 호출 계약](https://developers.openai.com/api/docs/guides/function-calling)
- 자유 텍스트 성공 주장은 판정이 아니다. T15의 독립 검증 receipt가 일치할 때만 승인 대기로 넘어간다. T19와 Executor는 LLM을 import하지 않는다.
- API 키는 플랫폼 워커에만 주입한다. 리허설 Pod와 앱 소스에 키·개인 OAuth·홈 디렉터리를 전달하지 않는다. 도구 제한과 OS·네트워크 격리는 각각 검증한다.
- workflow, lock, 비공개 테스트, 운영 IaC를 모델의 수정 범위에 포함하지 않는다. 검사를 바꿔 성공 처리하지 않는다.
- 저장소 CI는 변경 경로를 결정적으로 선택하고, 공통 계약·불명 영향은 전체 검사로 처리한다. 정상 CI마다 모델을 호출하지 않는다.

## 5. 비용과 검증 범위

한 제안 시도는 최대 8회 호출·180초, 요청 128 KiB·출력 4,096토큰, 응답이 보고한 누적 사용량 32,000토큰을 경계로 중단한다. 응답 후 측정이므로 마지막 호출의 초과 사용량까지 사전에 차단하는 달러 상한이 아니다. 운영 시 선택 모델 가격을 고정한 비용 집계와 제공자 프로젝트의 예산·사용 제한을 별도로 연결해야 한다.

**기존 AWS 월 50만원 예산은 OpenAI 직접 청구를 합산하지 않는다.** OpenAI 예산 배분과 경고 수신 경로를 회의에서 정하고 T1 비용 뷰에 제공자·모델·run 기준을 추가할지 결정한다. 지금은 OAI 사용료가 0이라고 추정하거나 AWS 예산으로 보호된다고 표시하지 않는다.

로컬·AWS에서 가짜 응답과 실제 SDK 직렬화, 정책 경계, 컨테이너 제약을 검증한다. 실제 모델 호출은 플랫폼용 OpenAI 인증 경로가 준비된 뒤 별도 증거로 기록한다. T10의 신뢰 snapshot 발급·영속 시도 수·취소, T15의 실제 Job·인증된 receipt, T31 반영은 통합 완료 전까지 미완료다. [워커 구현](../../services/agent-worker/README.md), [비교 조사](../research/ci-agents-2026-11-03.md)

## 6. 다음 회의에서 정할 질문

- 고객 AI 이전은 P0 데모에 포함할지, P1 조사로 남길지? API 연결 변경·세션 이전·자체 추론 중 무엇을 성공으로 볼지?
- Bedrock을 검토한다면 고객 어댑터인가, 우리 모델 제공자인가? 두 선택의 담당·예산·검증을 분리할지?
- OpenAI 비용을 지원금 50만원 안에서 배분할지, 별도 예산으로 둘지? 허용 모델과 run별 비용 상한을 누가 정할지?

이번 제안은 모델 제공자를 바꾸어도 제안·검증·승인·실행의 책임이 유지되게 한다. 모델 호출 성공만으로 리허설 PASS나 고객 이전 성공을 주장하지 않는다.
