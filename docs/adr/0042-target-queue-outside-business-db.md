# [ADR-0042] 목적지 큐는 업무 DB 밖의 SQS 호환 서버로 둔다

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-11-07
* **관련 (Related):** T46 #698, 설계 8.5 · 8.6, ADR-0041 · ADR-0043

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** ADR-0041의 실행기는 SQS API를 받는 목적지 큐 서버가 필요하다. 후보는 별도 SQS 호환 서버(ElasticMQ 등)와, 업무 DB(Postgres) 안의 테이블을 큐로 쓰고 그 앞에 SQS API를 얹는 직접 구현이었다. 직접 구현은 큐가 논리 복제로 함께 옮겨지고 2단계에서도 그대로 쓸 수 있다는 점 때문에 검토했다.
* **문제:** 컷오버 전에는 업무 쓰기를 받는 DB가 출발지 하나여야 한다. Executor 사전 확인은 목적지 DB에 앱 역할 세션이나 시스템 역할이 아닌 세션이 있으면 상태를 확인할 수 없다고 보고 SAFE_HOLD로 멈춘다(`services/cutover-executor/src/bravo_cutover/runner.py`의 `_target_closed`). 목적지 큐 테이블이 목적지 DB에 있으면, 트래픽 전환 중 목적지 앱이 보내는 메시지마다 목적지 DB에 쓰기가 생긴다.
* **목표:** 큐 서버 후보 비교(T46 할 일 1)의 범위를 정한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 업무 DB 밖의 SQS 호환 서버

목적지 클러스터에 큐 전용 서버를 둔다. 큐 상태는 업무 DB와 분리된다.

**Pros**
* 컷오버 전 목적지 DB에 쓰기가 생기지 않는다. 사전 확인 · 단일 쓰기 DB 원칙과 충돌하지 않는다.
* 기존 오픈소스를 쓰면 구현량이 작다.

**Cons**
* 큐가 복제로 옮겨지지 않으므로 컷오버 · 되돌리기에 큐 처리 단계가 필요하다(ADR-0043).
* 접근 제어 · 전송 암호화를 원본 SQS와 같은 수준으로 갖추는지 따로 시험해야 한다.

### 2. 목적지 업무 DB 안의 큐 테이블

**Pros**
* 큐가 데이터와 같은 곳에 있다.

**Cons**
* 컷오버 전 목적지 DB에 쓰기가 생겨 단일 쓰기 DB 원칙을 어기고, 사전 확인이 SAFE_HOLD로 멈춘다.

### 3. 출발지 업무 DB 안의 큐 테이블 (PgBouncer 경유)

큐 서버가 앱과 같은 PgBouncer 경로로 그때의 주 DB에 큐 행을 쓴다.

**Pros**
* 큐 행이 논리 복제로 옮겨지고, 쓰기 DB는 하나로 유지된다.

**Cons**
* 큐 서버가 앱 역할로 DB에 붙어 PAUSE · 펜싱 · 비교 · 복제 대상에 모두 들어간다. 큐 지연이 쓰기 정지와 긴 트랜잭션 판정에 섞인다.
* 복제 · 비교 · 펜싱 범위를 바꾸는 일이 T8 · T13 · T19와 맞물려 현재 일정에서 위험이 크다.

## 3. 결정 사항 (Decision Outcome)

* **업무 DB 밖의 SQS 호환 서버를 선택한다.** 후보 비교는 이 범주 안에서만 한다(ElasticMQ 등).
* **출발지 DB 안의 큐 테이블(옵션 3)은 2단계 전환 때 다시 검토하는 확장 옵션으로 남긴다.**
* **목적지 DB 안의 큐 테이블(옵션 2)은 채택하지 않는다.**

**이유**
* 업무 쓰기를 받는 DB는 어느 순간에도 하나라는 원칙(설계 8.6)과 기존 사전 확인 규칙을 바꾸지 않는다.
* 컷오버 경로(해피패스)에 영향을 주는 범위를 최소로 한다.

## 4. 결과

* 후보 비교 시험 항목: 최신 boto3 SQS 송수신 · 삭제, 다시 꺼낼 수 있게 되는 시간 뒤 재전달, 실패 보관 큐 이동, 재시작 뒤 메시지 보존, 허용되지 않은 Pod의 접근 거부, 전송 암호화, 목적지 VM 자원 사용량.
* 비교 결과로 고른 제품과 그 이유는 이 ADR에 덧붙여 기록한다.
* 큐가 복제로 옮겨지지 않으므로 컷오버 · 되돌리기의 큐 처리는 ADR-0043을 따른다.
