# [ADR-0045] SQS → Lambda 호환 런타임의 구조와 동등성 검증 위치

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-11-07
* **관련 (Related):** T46 #698, 설계 7.3 · 8.4 · 8.8, ADR-0017 · ADR-0018 · ADR-0046 · ADR-0047

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 앱이 SQS로 보낸 메시지로 Lambda가 실행되는 업무는 앱·DB를 옮겨도 AWS에 남는다. T16은 SQS · Lambda를 "대체 없음"으로 판정한다(`services/inventory/src/bravo_inventory/catalog.py`의 onprem `messaging` · `function`). 목적지에서 같은 기능을 돌릴 구현이 없다.
* **문제:** 목적지에서 무엇으로, 어떤 방식으로 같은 결과를 내고, 그 동등성을 플랫폼 흐름의 어디서 판정할지 정해져 있지 않다.
* **목표:** 앱과 핸들러를 고치지 않고 목적지에서 같은 결과를 낸다. 나중에 공통 인터페이스 방식으로 옮길 수 있게 한다. 기존 승인 · 리허설 · 게이트 흐름을 그대로 쓴다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 실행 주체 교체 (1단계)

앱은 boto3 SQS 호출을 그대로 쓰고 `AWS_ENDPOINT_URL_SQS`만 목적지 SQS 호환 서버로 바꾼다. 실행기가 큐에서 메시지를 꺼내 기존 `handler(event, context)`를 AWS SQS 이벤트 형식으로 부른다.

**Pros**
* 앱 · 핸들러 코드 수정이 없다. 이전 작업이 설정 교체다.
* 카탈로그 등급(설정 교체 · 어댑터 추가)으로 기존 흐름에 들어간다.

**Cons**
* 앱이 AWS API 형식을 계속 쓴다. Exit Drill은 `AWS_ENDPOINT_URL*`이 있으면 UNKNOWN을 낸다(ADR-0017).
* 실행기가 AWS 이벤트 형식을 재현해야 하고, 재현 차이가 버그가 된다.

### 2. 공통 인터페이스 (2단계)

업무 함수를 핸들러에서 떼어 내고, 송신 · 수신을 플랫폼 라이브러리로 바꾼다. 환경마다 연결부만 다르다.

**Pros**
* 업무 코드에 AWS 형식이 남지 않는다. 출구 판정 충돌이 없다.

**Cons**
* 앱 · 핸들러를 고쳐야 해 S2 코드 수정 흐름(에이전트 제안 → 리허설 → 승인)이 필요하다.
* 라이브러리 · AWS 연결부를 새로 만들어야 한다.

## 3. 결정 사항 (Decision Outcome)

* **1단계(실행 주체 교체)를 선택한다.**
* **실행기는 큐 연결 · 호출 관리 · 메시지 형식 세 부품으로 나눈다.** 2단계로 갈 때 큐 연결과 메시지 형식만 바꾸고 호출 관리(제한 시간 · 재시도 · 실패 보관 큐)는 그대로 쓴다. 2단계는 향후 확장 옵션으로 남긴다.
* **핸들러 배포 단위는 런타임 베이스 이미지 위에 핸들러를 얹은 함수 이미지이며, GHCR digest로 고정한다.** 출발지 Lambda 배포본과 같은 핸들러 파일 digest를 기록한다.
* **동등성은 리허설 검증 Job이 채점한다.** 리허설 네임스페이스에 큐 서버 · 실행기 · 합성 DB를 넣고 비공개 시험으로 기대 결과 · 재시도 · 실패 보관 · 중복을 판정한다. 게이트(T19)는 같은 시험을 다시 돌리지 않고 검증 기록과 목적지 실행기 상태만 확인한다.
* **지원 범위는 출발지 AWS SQS 표준 큐 → Python Lambda 핸들러, 목적지 RKE2(onprem · gcp)다.** FIFO · EventBridge · 정해진 시각 실행 · 배치 일부 실패 응답은 실행기가 시작 전에 거부하고 "지원 안 함"으로 표시한다. 핸들러 안의 SQS 외 AWS 호출은 시작 전에 결정적으로 찾을 수 없다. 목적지에서 AWS 송신과 자격을 막고, 그런 호출은 리허설 검증에서 실패로 잡는다.

**이유**
* 이전 시점의 목표는 "코드 수정 없이 AWS 의존 기능을 옮긴다"이고, 1단계가 이 목표를 직접 충족한다.
* 부품 분리로 2단계 전환 비용을 큐 연결 · 메시지 형식 교체로 한정한다.
* 함수 이미지를 digest로 고정하면 승인 결속(FR-7)과 배포 경로(설계 8.8)를 앱 이미지와 같게 쓴다.
* 게이트에서 원본과 목적지에 시험 메시지를 넣으면 출발지 업무 DB에 시험 행이 생긴다. 리허설 검증 Job은 운영 데이터를 건드리지 않고, 기존 FR-5 방식과 같다.

## 4. 결과

* 새 서비스 `services/function-runtime`에 실행기를 둔다. 판정 · 실행 경로이므로 LLM 클라이언트를 import하지 않는다.
* 리허설 러너(T15)에 기존 버킷 · 자격 작업과 같은 형태의 세 번째 작업 종류를 둔다. 에이전트 제안서 없이 정해진 구성을 시험하는 작업이다.
* Exit Drill의 `AWS_ENDPOINT_URL_SQS` 판정은 2단계 전환 여부를 정한 뒤 별도로 정한다. 그 전까지 이 구성은 출구 증거로 세지 않는다.
* 목적지 큐 서버는 ADR-0046, 컷오버 · 되돌리기의 큐 처리는 ADR-0047이 정한다.
