# ADR-0014: Exit Drill 차단은 앱 Pod의 송신 허용 목록으로 한다

* **상태:** 제안됨 — 로컬 k3s 실측까지 끝났고, 실제 RKE2 · Tailscale 실행은 T12 뒤에 한다.
* **날짜:** 2026-11-04
* **관련:** T27 #32, 설계 FR-15, T8 · T30(복제 경로), T6(EKS CNI 실사례)

## 1. 배경과 문제

FR-15는 "목적지 앱의 AWS 접근만 끊고 복제 채널은 유지한다"이다. 그런데 앱이 출발지에 닿는 길은 AWS API만이 아니다. 컷오버 전에는 목적지 풀러의 백엔드가 Tailscale을 거쳐 출발지 DB를 가리키고, 복제도 같은 Tailscale을 쓴다. 끊을 길과 남길 길이 같은 망 위에 있다.

## 2. 고려한 선택

| 선택 | 이점 | 제약 |
|---|---|---|
| 앱 · 풀러 Pod의 송신 허용 목록(NetworkPolicy) | 주소를 몰라도 나머지가 전부 닫힌다. DB Pod를 안 고르면 복제에 손대지 않는다 | CNI가 강제해야 한다. 이미 맺은 연결은 안 끊길 수 있다. 정책이 합집합이라 기존 허용을 봐야 한다 |
| AWS 주소 차단 목록(ipBlock except) | "AWS만"이라는 말과 그대로 맞는다 | NetworkPolicy에 거부 규칙이 없어 결국 넓은 허용이 필요하다. AWS 주소가 바뀌면 조용히 빠진다 |
| tailnet ACL 변경 | Tailscale 경로를 근원에서 끊는다 | AWS API 경로는 못 막는다. 복제 태그까지 건드릴 위험이 있고, 렌더러는 ACL을 바꾸지 않는 것이 현재 경계다 |
| 복제 프록시 제외 후 tailnet 전체 차단(노드 방화벽) | 강제가 확실하다 | 노드 권한이 필요하고, 앱만 고르는 선을 Pod 수준에서 긋지 못한다 |

## 3. 결정

1. **앱 · 풀러 Pod의 송신 허용 목록을 쓴다.** 앱 역할 Pod는 선언한 목적지 내부 경로로만 나간다. "AWS만"을 말 그대로 구현하는 대신, 나가도 되는 곳을 적어 그 밖을 모두 닫는다. 이 차이는 결과에 드러난다: 선언 안 한 외부(Cloudflare 등)로 앱 Pod가 직접 나가는 길도 닫힌다.
2. **DB Pod는 정책으로 고르지 않는다.** 복제 유지는 정책을 더 만드는 방식이 아니라 건드리지 않는 방식으로 지킨다. 선택자가 DB Pod까지 고르면 만들지 않고 실패한다.
3. **정책 객체를 증거로 삼지 않는다.** 차단 여부는 실제 연결 시험과 대조군으로 판정한다. T6에서 EKS CNI가 정책을 강제하지 않은 사례가 있었고, k3s에서 강제를 끈 경우도 정책 객체는 계획과 같은데 AWS가 열려 있음을 쟀다.
4. **재시작을 두 번 판정에 넣는다.** 이미 맺은 연결은 정책을 넣어도 끊기지 않아(k3s에서 실측) Pod를 새로 만든다. 그런데 새 Pod는 정책이 있어도 처음 잠깐 막히지 않아, 시작할 때 AWS를 부르는 앱이 그 틈에 떠 버린다(k3s에서 실측, 첫 측정의 거짓 PASS). 그래서 정책에 묶인 Pod에서 컨테이너만 한 번 더 재시작하고, 그 기록이 없으면 UNKNOWN이다.

## 4. 결과

- 생성기는 클러스터 읽기(Pod · 기존 정책)를 필수 입력으로 받는다. 합집합으로 남는 허용을 보지 않고는 "막았다"고 말할 수 없기 때문이다.
- 컨테이너 재시작은 1번 프로세스가 SIGTERM을 처리해야 하고, Pod 안에서 명령을 실행할 권한이 필요하다. 실제 demo-chat과 PgBouncer에서 되는지는 아직 재지 않았다.
- 실제 환경에서 Canal(RKE2)의 강제 방식과 연결 추적 동작은 k3s와 다를 수 있다. 판정이 정책 객체가 아니라 실측을 보므로 실행 방식이 달라도 같은 기준으로 잰다. 다만 UNKNOWN이나 FAIL로 시험이 막힐 수 있고, 그 확인은 T12 뒤의 실제 실행 몫이다.
- 복제 채널은 유지된다. 즉 드릴을 통과해도 출발지와의 연결은 남아 있고, 잔존 의존성 지도가 그 사실을 `kept`로 표시한다. "완전히 떠났다"는 복제를 끊는 별도 단계 뒤에야 말할 수 있다.
