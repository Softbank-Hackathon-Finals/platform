# ADR-0007 계획 상태와 이벤트의 원자 저장 · 조회 watermark

* **상태 (Status):** 제안됨(Proposed), 로컬 참조 구현 검증
* **날짜 (Date):** 2026-11-03
* **관련 (Related):** T10 #19, T21, T24; 설계 초안 v0.3 §8.2 · §8.9

## 1. 배경 및 문제 상황

SSE 계약은 계획별 순번과 재생을 제공하지만 화면이 처음 열릴 때의 계획 상태는 제공하지 않는다. 상태를 먼저 저장하고 이벤트를 별도로 쓰면 중간 실패로 서로 어긋날 수 있다. 또 상태와 마지막 이벤트 번호를 다른 시점에서 읽으면 조회 중 일어난 전이를 이미 처리한 것으로 건너뛸 수 있다.

## 2. 고려한 옵션들

1. 상태와 이벤트를 별도 저장소에 기록한다. 독립 확장은 쉽지만 이중 저장 실패와 전달 복구를 새로 다뤄야 한다.
2. 기존 이벤트 저장소와 같은 DB 트랜잭션으로 상태 · 이벤트 · 명령 영수증을 기록한다. 작은 로컬 모듈에서 롤백과 경쟁을 검증할 수 있다. 운영 DB로 옮길 때 같은 원자성 경계를 다시 구현해야 한다.

## 3. 결정 제안

옵션 2를 참조 구현으로 제안한다. 기존 `services/platform-events`의 SQLite 로그를 재사용하고 별도 큐 · 서비스 · 배포 단위는 만들지 않는다. 이벤트 테이블이 커밋된 전달 원장이며 SSE가 이를 직접 읽는다. 외부 메시지 브로커용 dispatcher나 운영 outbox가 완성된 것은 아니다.

계획은 서버가 검증한 불변 참조로만 내부 등록한다. 첫 상태 `COLLECT`와 최초 이벤트를 함께 기록한다. 이 단계에서 허용하는 유일한 전이는 신뢰된 수집기의 완료 증거가 계획 digest · 수집 범위 digest와 일치하는 `COLLECT → ANALYZE`다. 상태 버전 비교와 명령 키 충돌 검사는 같은 쓰기 트랜잭션 안에서 수행한다. 관리되는 계획의 `state.changed`를 일반 이벤트 append로 쓰는 경로는 거부한다.

`GET /v1/plans/{id}`는 같은 읽기 트랜잭션의 상태 · 버전 · 마지막 이벤트 ID를 반환한다. 조회와 SSE에 동일한 서버 principal/저장된 tenant 접근 정책을 사용한다. 인증 resolver가 없으면 거부한다. 실제 인증 검증과 추가 역할 정책은 호스트 책임이며 요청 헤더의 tenant를 신뢰하지 않는다.

## 4. 결과와 제한

- 상태 화면은 snapshot의 `last_event_id` 다음부터 이어갈 수 있다. snapshot은 승인 · 게이트 · 실행 · 감사 이력 전체를 포함하지 않으므로 T24 이력 재생 cursor를 이 값으로 덮어쓰면 안 된다.
- SQLite 로컬 시험에서 쓰기 중 실패 · 동시 전이 · 같은 명령 재시도 · 조회 중 쓰기 · 재기동을 검증한다. PostgreSQL · 여러 인스턴스 · 실제 로그인 · 수집기/환경 검증 · 원격 실행 복구는 별도 통합 과제다.
- T5의 서버 정본 게이트 조회, 승인 결속/만료 검증, T12 실행 idempotency/epoch, SAFE_HOLD 및 전체 COLLECT → DONE은 이 변경의 완료 범위가 아니다.
- 새 HTTP 생성/전이 API는 제공하지 않는다. 등록과 `CollectionProof`는 신뢰된 호스트의 Python 경계이며 클라이언트가 보낸 `complete: true`를 증거로 사용할 수 없다.
- 운영 DB/서비스의 채택 결정은 팀 리뷰에 남아 있다. 이 ADR의 제안 상태는 코드 병합만으로 자동 변경하지 않는다.
