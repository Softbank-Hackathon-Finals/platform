# [ADR-0051] 데모 앱 로그인 이전: Cognito → Keycloak 설정 교체

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-11-08
* **관련 (Related):** T47 #699, 설계 7.3 · 8.10, demo-app #28 · #29 · #30, platform #651 · #652 · #653 · #927, ADR-0018

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** demo-chat에는 로그인이 없어 플랫폼이 관리형 인증(Cognito)도 찾아 옮기는 장면을 보여 줄 수 없었다. 설계 7.3 대응표에도 인증 행이 없었다.
* **문제:** 출발지 로그인을 무엇으로 대체하고 어느 이전 등급으로 둘지, 비밀번호와 이사 중 로그인 상태를 어떻게 다룰지, 언제 AWS 의존이 끝났다고 볼지 정해져 있지 않았다.
* **목표:** 같은 앱 이미지가 `AUTH_ISSUER`만 바꿔 Cognito에서 Keycloak으로 옮겨지고, 이사 중 로그인한 사용자의 쓰기가 끊기지 않는다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 표준 OIDC만 쓰는 앱 + 목적지 Keycloak

앱은 OIDC 발급자 주소와 공개 클라이언트 ID만 안다(demo-app #28). 출발지는 Cognito 사용자 풀(#651), 목적지는 같은 규칙의 Keycloak realm(#652)이다.

**Pros**
* 발급자 바꾸기가 설정 교체다. 앱 코드와 이미지를 바꾸지 않는다.
* Cognito와 Keycloak이 같은 코드 경로로 시험된다.

**Cons**
* Cognito가 비밀번호 해시를 내보내지 않아, 사용자는 옮겨도 비밀번호는 다시 정해야 한다.

### 2. 앱이 Cognito 전용 API를 직접 부름

**Pros**
* 출발지 기능을 그대로 쓴다.

**Cons**
* 목적지로 옮기려면 앱 코드를 고쳐야 한다. 코드 수정 등급의 예는 이미 Secrets Manager(8.10)가 맡고 있다.

## 3. 결정 사항 (Decision Outcome)

* **표준 OIDC + 목적지 Keycloak(옵션 1)을 선택한다.** 7.3 대응표에 인증 행을 **설정 교체(`AUTH_ISSUER`)**로 둔다.
* **비밀번호는 옮기지 않는다.** `identity_users.py`가 Cognito 사용자 목록을 Keycloak 가져오기로 바꾸고, 운영자가 준 임시 비밀번호로 첫 로그인할 때 새 비밀번호를 정한다.
* **이사 중에는 양쪽 앱이 서로의 발급자를 믿는다.** `AUTH_ALSO_TRUST`에 상대 발급자를 넣고(demo-app #29), 전환이 끝나면 목적지에서 지운다. 앱은 토큰의 이름(`preferred_username` 등)으로 작성자를 정하므로, 이 이중 신뢰는 **양쪽 모두 관리자만 계정을 만들고 사용자가 이름을 바꿀 수 없을 때만 안전하다.** 출발지는 클라이언트 `WriteAttributes`가 `locale` · `zoneinfo`뿐이고, 목적지는 `editUsernameAllowed=false`에 모든 속성을 관리자만 고친다.
* **PKCE는 양쪽이 다르다.** 목적지 Keycloak은 S256을 강제하고, 출발지 Cognito는 강제하지 않아 앱이 항상 S256으로 보낸다(#651 README). 목적지가 더 엄격한 차이이므로 출발지에는 강제를 요구하지 않고, 목적지에서는 강제되는지 확인한다.
* **목적지 앱이 AWS 발급자를 믿는 동안은 출구 증거가 아니다.** Exit Drill이 `AUTH_ISSUER` · `AUTH_ALSO_TRUST`에서 `.amazonaws.com` · `.amazoncognito.com`을 찾으면 `AWS_IDENTITY_TRUSTED`로 판정한다(#653). 두 값을 `valueFrom`이나 `$(다른 변수)`로 넣거나 컨테이너가 `envFrom`을 쓰면 값을 읽지 못하므로, 통과가 아니라 `ELIGIBILITY_NOT_READ`로 판정한다.
* **부하 생성기(T18) 클라이언트는 브라우저 클라이언트와 따로 두고, 앱이 그 클라이언트를 `loadgen` 이름에 묶는다(#927, demo-app #30).** 부하 생성기는 사람 없이 토큰을 받아야 하므로 비밀번호로 받는다(출발지 AWS 서명 AdminInitiateAuth, 목적지 비밀 있는 password grant). 그래서 이 클라이언트에는 브라우저 로그인 · PKCE · 등록 redirect가 적용되지 않고, 발급자는 이 클라이언트를 계정에 묶지 않는다. 앱은 `AUTH_ALSO_TRUST=<발급자>|<부하 클라이언트>|loadgen`처럼 세 번째 칸에 적힌 이름일 때만 그 클라이언트의 토큰을 받고, 다른 계정의 토큰은 401로 거부한다. 목적지 부하 클라이언트는 갱신 · offline 토큰을 내지 않는다. offline 토큰은 비밀번호 교체 · 관리 API logout 뒤에도 남기 때문이다. 이름 고정은 부하 클라이언트에만 걸리고 `loadgen`은 일반 계정이라 비밀번호만 있으면 브라우저 클라이언트로도 그 이름의 토큰을 받으므로, 측정하지 않는 동안에는 부하 항목을 `AUTH_ALSO_TRUST`에서 지우고 부하 클라이언트와 계정을 닫는다. demo-app #30이 배포되기 전에는 이 클라이언트를 `AUTH_ALSO_TRUST`에 넣지 않는다. 이전 앱은 발급자마다 클라이언트를 하나만 남겨, 넣으면 출발지에서 로그인한 방문자의 쓰기가 목적지에서 401이 된다.
* **동등성은 시험 결과로 판단한다.** 양쪽에서 스스로 가입이 막히고, 사용자가 이름을 바꿀 수 없고, 등록한 redirect만 받고, 토큰 없는 쓰기가 401인지 실제로 확인한다. PKCE S256 강제는 목적지에서만 확인한다.

**이유**
* 설계 원칙(동등성은 제품 이름이 아니라 시험 결과)과 맞고, 이전이 앱 코드 수정 없이 끝난다.
* 비밀번호 해시는 출발지가 내보내지 않으므로 옮길 방법이 없다. 첫 로그인에 새로 정하는 것이 유일한 경로다.
* 두 발급자를 함께 믿어야 트래픽을 나누는 동안 어느 환경에서 로그인했든 쓰기가 받아진다.

## 4. 결과

* 설계 v0.9에서 7.3 대응표에 인증 행과 설명 문단을 더했다.
* 출발지 쪽 동등성 확인은 [T47 로그인 동등성 증빙](../evidence/t47-identity-equivalence-2026-11-08/README.md)에 있다.
* 부하 생성기 클라이언트(#927): 출발지 Cognito `demo-chat-loadgen`(관리자 흐름만), 목적지 Keycloak `identity.loadgen_client()`(관리 API로 등록), `services/loadgen`의 선택형 토큰 공급. 7.3의 "등록한 redirect만" · "PKCE S256 강제" 동등성은 브라우저 클라이언트에 대한 것이고, 부하 클라이언트의 경계는 앱의 이름 고정이다.
* 남은 것: 목적지 Keycloak의 클러스터 적용과 실제 로그인 확인, Edge 로그인 경로(T17), 인벤토리 탐지(T16), 부하 생성기 클라이언트의 적용(출발지 `plan` · `apply`, 목적지 관리 API 등록)과 demo-app #30 배포.
