# [ADR-0023] 리허설 러너: T10이 접수한 시도만 한 번 실행하고, 러너 서명 기록과 대조군 관측으로 판정한다

* **상태 (Status):** 제안됨(Proposed). 결정은 T15 spec과 [#259](https://github.com/Softbank-Hackathon-Finals/platform/pull/259)에서 확정했고, 이 문서는 병합 뒤 남기는 기록이다. 버킷 정책 작업을 개인 RKE2 VM에서 실측했다. 팀 목적지에서 다시 실측한 뒤 채택한다.
* **날짜 (Date):** 2026-11-05
* **관련 (Related):** T15 #24, T10 #19, T11 #20, T38 #150, T3 #7, T31 #33, 설계 문서 FR-5 · 8.4, [ADR-0003](0003-rehearsal-namespace-isolation.md), [ADR-0019](0019-agent-tool-boundary.md), [ADR-0021](0021-approved-change-promotion.md), [T10 변경 승인 계약](../contracts/T10-change-approval.md)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 리허설 러너(`services/rehearsal-runner`)는 에이전트(T11)가 낸 변경안을 격리된 리허설 namespace(T3)에서 시험하고, 결과를 T10 승인 대기로 넘긴다. 검증한 변경만 승인하고, 승인된 변경만 목적지에 반영한다(T31). 변경안은 버킷 정책과 코드 수정 두 종류다.
* **문제:**
  * 재시도를 T15와 T10 중 누가 소유하는지 정해야 한다. T15 자체 재시도 루프와 T10의 시도 접수 · hold가 함께 있으면, 재시작이나 응답 유실 때 시도 수가 초기화되거나 같은 시도가 두 번 실행될 수 있다.
  * 검증 결과의 진위를 확인해야 한다. 모델 출력이나 복사된 파일을 PASS 증거로 받으면 시험하지 않은 변경이 승인 대기에 올라간다.
  * 거부를 관측했다는 사실만으로는 PASS라고 할 수 없다. 버킷이나 경로가 처음부터 막혀 있었으면, 후보 정책이 틀려도 "무인증 읽기 거부"가 관측된다.
* **목표:** 시도마다 실행은 최대 한 번이다. T10이 받는 PASS · FAIL은 러너가 직접 관측하고 기록한 것뿐이다. 판정은 환경이 정상임을 확인한 뒤에만 내린다. 확인할 수 없으면 사람에게 넘긴다.

## 2. 고려한 옵션들 (Considered Options)

결정할 것이 세 가지다. 각 항목에서 앞의 옵션을 선택했다.

### 1. [재시도 소유] T10이 시도 접수 · hold · 상한을 맡고, T15는 접수된 단일 시도만 실행

T10은 계획 잠금 안에서 `Admission`(실행 ID · 시도 번호 · 원본 revision · 작업 digest)을 커밋하고 시도를 1~3회로 제한한다. 러너는 `submit_once`로 시도마다 claim을 한 번만 잡고 실행한다. claim은 있는데 결과가 없으면 재실행하지 않고 T10에서 UNCONFIRMED로 남긴다. 2 · 3회차는 직전 FAIL 기록의 증거 digest를 T11 재시도 근거로 받는다.

**Pros**
* 시도 수와 hold의 기준이 T10 저장소 하나뿐이다. 재시작 · 동시 요청 때도 시도 수가 초기화되지 않는다.
* 결과를 모르는 시도를 다시 실행하지 않아, 효과가 확인되지 않은 시도가 성공으로 처리되지 않는다.

**Cons**
* 러너가 중간에 죽으면 그 시도는 사람이 `recovery_lookup`으로 namespace · Job을 조사해야 한다.
* T11 Coordinator 상태가 메모리에 있어, 재시작 뒤 복원은 T11과 따로 맞춰야 한다.

대안은 T15 자체 재시도 루프였다. 모의 시험은 간단하지만, T10의 hold · 시도 이력과 기준이 두 개가 된다. #259에서 제거했다.

### 2. [결과의 진위] 러너 호스트만 가진 키로 서명한 write-once 기록

`AttemptStore`는 시도마다 claim과 결과를 파일로 한 번만 만든다(`O_EXCL`). 기록은 러너 호스트만 가진 키로 HMAC-SHA256 서명한다. T10은 `EvidenceReader` · `ChangeIntake.read_original`로 이 기록만 읽는다. 서명이 없거나, 바뀌었거나, 다른 시도를 가리키는 기록은 거부한다. PASS 기록에는 다음이 모두 일치해야 한다: 생성 UID와 삭제 UID, 격리 시험 실행 ID, 제안 digest, namespace. 하나라도 다르면 `NEEDS_HUMAN`(`EVIDENCE_IDENTITY_MISMATCH`)이다.

**Pros**
* 모델 출력이나 복사된 파일은 서명이 없어 증거가 될 수 없다.
* 같은 시도의 결과를 덮어쓸 수 없다. T10은 받은 PASS 원문을 다시 읽어 수신 내용과 대조한다.

**Cons**
* 키 보관과 기록 저장소를 러너 호스트에 둬야 한다. 운영 호스트 배치는 T10 운영 연결 때 한다.

대안은 Job 출력이나 에이전트 보고를 그대로 T10에 넘기는 방식이었다. 연결은 단순하지만, 시험하지 않은 결과가 승인 대기에 들어가는 것을 막을 수 없다. 운영 원문 저장소를 T38 · T10이 따로 제공하면 이 결정을 다시 검토한다.

### 3. [판정 기준] 대조군에서 무인증 허용을 먼저 관측해야 후보의 거부를 PASS로 인정

검증 Job은 같은 시험 버킷에 원본 공개 정책(대조군)과 후보 정책을 차례로 적용한다. 정책마다 서명 읽기 → 무인증 읽기 → 서명 읽기를 관측한다. 판정은 다음과 같다.
* 대조군에서 적용 · 무인증 허용 · 앞뒤 서명 읽기 일치가 관측되지 않으면 판정하지 않는다(`control_unconfirmed`, 사람에게 넘김).
* 대조군이 정상일 때, 후보가 무인증 읽기를 허용하면 `ANONYMOUS_READ_ALLOWED`, 서명 읽기를 깨뜨리면 `AUTHENTICATED_READ_BROKEN`, 정책 적용이 거부되면 `POLICY_REJECTED`로 FAIL이다.
* 관측값 중 하나라도 불명이면 판정하지 않는다.

Job은 플랫폼이 가진 스크립트로, 토큰 없는 기본 서비스 계정을 써서 별도로 실행한다. 에이전트 도구 계정은 쓰지 않는다.

**Pros**
* 환경 탓의 거부(경로 차단, 버킷 부재)를 PASS로 오인하지 않는다. "원본에서 거부되지 않던 접근이 대상에서 실제로 거부되는지" 시험한다.
* 과잉 거부(서명 읽기까지 막는 정책)도 FAIL로 잡는다.

**Cons**
* 시험 버킷에 원본 공개 정책을 잠시 적용해야 한다. 그래서 앱 버킷과 분리된 시험 전용 버킷과 그 버킷에만 쓰는 자격이 필요하다(T9).
* Job이 정책마다 하나씩 돌아 시간이 더 걸린다.

대안은 후보 정책만 적용하고 무인증 거부만 관측하는 방식이었다. 빠르지만 환경 원인의 거부와 정책 효과를 구별할 수 없다.

## 3. 결정 사항 (Decision Outcome)

* **옵션 1~3을 모두 선택한다.**
  * T15는 T10이 커밋한 시도만 실행한다. 시도 수 · hold · 이전 결과 무효화는 T10이 맡는다.
  * claim 뒤 결과가 없는 시도는 재실행하지 않고 UNCONFIRMED로 남긴다.
  * T10이 확정하는 것은 서명된 기록의 PASS · FAIL뿐이다. 그 밖의 결과는 확정하지 않는다.
  * PASS는 T10 수신(재조회 포함)이 끝난 뒤에만 승인할 수 있다. 승인 값(diff_hash · image_digest · 대상 · 만료)이 현재 값과 같아야 한다.
  * 격리 실패 · 격리 확인 불가 · UID 불일치 · 정리 미확인이면 승인 대기로 넘기지 않는다.
* **제품 템플릿은 버킷 정책을 먼저 구현하고 코드 수정을 다음에 한다.** 코드 수정 작업의 검증 Job은 아직 합의가 필요하다. 남은 합의는 리허설 namespace의 Secret 전달 경로(T9), 후보 이미지 빌드와 digest 산출(T31), 다른 서비스 계정의 Secret 읽기 거부를 확인하는 방식이다. 확인 방식은 정한 뒤 별도 ADR로 남긴다.
* **T15 자체 재시도 루프와 Job 출력의 직접 전달은 채택하지 않는다.**

**이유**
* 판정과 실행은 코드가 한다. 모델 출력은 제안일 뿐 증거가 아니다.
* 재시도와 승인의 기준을 T10 하나로 두면, 재시작 · 응답 유실 때도 시도 수와 결과가 어긋나지 않는다.
* 동등성은 제품 설정이 아니라 대조군과 후보의 실제 접근 결과로 판단한다.

## 4. 결과

* 로컬 시험은 `services/rehearsal-runner` 306개, T10 연동 35개, T11 연동 31개가 통과했다(#259 시점, Kubernetes · 제안 · Job은 모의). T10 연동은 실제 `RehearsalService` · `ChangeIntake` · `ChangeApprovalService`로 다음을 확인했다.
  * PASS → 수신 → 승인
  * FAIL → hold → 2회차
  * 응답 유실 시 재실행 없음
  * 전달되지 않은 PASS는 확정하지 않음
  * 변조된 기록 거부
* 개인 RKE2 VM(RKE2 v1.35.9, CIS 프로필)에서 실제 T10(SQLite) · T11 · T3 · SeaweedFS Job으로 실측했다.
  * 1회차 과잉 거부 정책은 FAIL(`AUTHENTICATED_READ_BROKEN`)이었고, hold 뒤 2회차 익명 거부 정책은 PASS였다.
  * 회차마다 대조군에서 무인증 허용을 확인했다. 생성 · 삭제 UID가 같았고 리허설 namespace가 남지 않았다.
  * 버킷 삭제 시도는 T11 도구 계층이 거부 · 기록했다([ADR-0019](0019-agent-tool-boundary.md)).
* 실측 한계:
  * 제안은 스크립트로 고정했다(모델 미사용). OpenBao는 대역이고 JWT 키 · 운영자 주체는 시험용이다.
  * 소프트웨어 에뮬레이션 VM이라 정리 대기와 Job 기한을 운영 기본값보다 길게 썼다.
  * 이 VM은 T2 설치 스크립트로 세운 목적지가 아니다. 팀 목적지 실측과 [ADR-0003](0003-rehearsal-namespace-isolation.md) 채택은 남아 있다.
* 남은 연결:
  * 운영 호스트에 `RecordedAttemptSender` · `RecordedEvidence`를 주입하는 배치(서명 키 · 발급자 · hold 권한, T10)
  * 러너에서 목적지 클러스터로 접속하는 경로와 권한(T7 · T10 · T2)
  * 실제 모델 입력 전달(T38)
  * 삭제 차단 기록의 감사 · 콘솔 표시(T24 · T21)
