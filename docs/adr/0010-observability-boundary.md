# [ADR-0010] 관측의 경계: 판정 입력은 바깥에서, 로그는 각 환경 안에, 지표는 OpenTelemetry로 플랫폼에

* **상태 (Status):** 제안됨(Proposed)
* **날짜 (Date):** 2026-11-03
* **관련 (Related):** T36 · T37 (신규), T17 #26, T18 #14, T10 #19, T21 #27, T34 #56, 설계 문서 FR-8 · 8.2 · 8.6 · 8.7 · S4 · NFR-1~3 · NFR-5, 2.1(비용 · 횡단 모니터링은 얕게)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 오류율 · p95는 이미 자동 결정의 입력이다. SHIFT는 단계마다 오류율 · p95가 기준을 넘으면 가중치를 0으로 돌리고(FR-8), WATCH는 S4 1단계에서 "오류율이 기준을 넘어 알림"을 보낸다. 목적지의 앱 · 감사 로그는 통제 시험 SEC-01.3 · AUD-01이 "클러스터 로그 수집기"에서 검색한다(T34). 킥오프 자료는 온프렘에서 감사 로그 · 모니터링을 어떻게 재현하고 보여 줄지 묻고(p.17), 테마 예시로 OpenTelemetry 횡단 모니터링을 든다(p.18).
* **문제:** 오류율 · p95를 어디서 재는지, 데이터가 없을 때 어떻게 판정하는지, 로그와 지표를 어디에 모으는지가 정해져 있지 않다. 7.3 대응표에도 로그 · 모니터링 줄이 없다. 판정 입력을 잘못 고르면 평가 대상이 스스로를 합격시키거나, 관측이 끊긴 것을 "오류 0"으로 읽을 수 있다.
* **목표:** 결정적이고 다시 계산할 수 있는 판정 입력, 동등성 시험을 해치지 않는 로그 위치, 온프렘의 바깥 방향 연결 제약 안에서 동작하는 수집 경로를 정한다. 범위는 설계 2.1대로 얕게 둔다.

## 2. 고려한 옵션들 (Considered Options)

### A. 판정 입력(오류율 · p95)을 어디서 재는가

#### A1. 각 환경 앱의 서버 지표 (OTel)

**Pros**
* 실제 사용자 요청을 모두 센다
* 앱 계측만 하면 되고 부하 생성기에 의존하지 않는다

**Cons**
* 목적지는 평가 대상이다. 목적지가 보낸 수치로 목적지를 합격시키는 구조가 된다
* Edge · Tunnel에서 난 오류는 앱까지 오지 않아 보이지 않는다
* 수집이 끊기면 "요청 0, 오류 0"과 구별하기 어렵다

#### A2. Cloudflare LB의 분석 데이터

**Pros**
* 사용자와 같은 경로를 본다

**Cons**
* 지연 · 요금제별 제공 범위를 실측해야 하고, 10초 단계 판정에 쓸 수 있는지 확인되지 않았다
* Cloudflare는 이미 잔존 의존성(8.7)이다. 판정까지 맡기면 의존이 커진다

#### A3. 바깥 클라이언트(T18 부하 생성기)가 Edge를 거쳐 잰 값

**Pros**
* 평가 대상 밖에서 사용자와 같은 경로로 잰다. Edge · Tunnel 오류도 오류로 잡힌다
* T18이 이미 오류율 · p95 · 쓰기 공백을 만들기로 돼 있다(T18 "만들 것")
* 응답 헤더로 처리 환경을 세면 실제 분배 비율(T17 "실제 분배 비율 관측")도 같은 데이터로 나온다

**Cons**
* 부하가 있을 때만 판정할 수 있다. 실제 운영에서는 합성 요청(synthetic probe)이나 실사용자 지표로 바꿔야 한다
* 데모 앱에 응답 헤더 하나가 더 필요하다

### B. 앱 · 감사 로그를 어디에 두는가

#### B1. 모든 환경의 로그를 플랫폼에 모은다

**Pros**
* 검색 위치가 하나다

**Cons**
* 목적지에 자체 로그 기능이 없는 상태가 된다. AUD-01은 "목적지도 원본처럼 감사 이벤트를 검색할 수 있는가"를 시험하므로 동등성 시험의 의미가 흐려진다
* 출구전략의 끝은 AWS를 떠나는 것이다. 플랫폼(AWS VPC ②) 없이 목적지가 운영돼야 한다

#### B2. 각 환경 안에 둔다 (출발지 CloudWatch Logs, 목적지 클러스터 로그 저장소)

**Pros**
* CloudWatch Logs의 대체 구현이 목적지에 실제로 있고, T14가 양쪽에 같은 질문을 던진다
* 개인정보 · 비밀이 섞일 수 있는 로그가 환경 밖으로 나가지 않는다

**Cons**
* 플랫폼에서 로그를 한 화면에 모아 보지 못한다(필요한 것은 통제 결과와 탐지 결과로 본다: T14 · T33)

### C. 서버 지표를 플랫폼으로 어떻게 모으는가

#### C1. 플랫폼 Prometheus가 각 클러스터를 긁어 온다(pull)

**Pros**
* 수집 대상이 응답하지 않으면 `up=0`으로 바로 보인다

**Cons**
* 온프렘은 바깥 방향 연결만 쓴다(7.2). 플랫폼에서 온프렘 안쪽으로 긁으려면 Tailscale로 클러스터 내부 엔드포인트를 노출해야 한다

#### C2. 클러스터마다 OpenTelemetry Collector가 플랫폼으로 보낸다(push, OTLP)

**Pros**
* 바깥 방향 연결만으로 된다
* 한 종류의 수집기로 지표와 로그 파이프라인을 모두 구성할 수 있다(로그는 B2대로 환경 안 저장소로)
* 킥오프가 든 OpenTelemetry와 맞는다

**Cons**
* 데이터가 오지 않는 것을 "정상"으로 오해할 수 있다. 환경별 최근 수신 시각으로 "확인 불가"를 따로 판정해야 한다

## 3. 결정 사항 (Decision Outcome)

* **A3을 선택한다.** 판정 입력은 T18의 창 요약(`SliWindow`)뿐이다. A1(서버 지표)은 원인 파악과 화면 표시에만 쓰고 판정에 쓰지 않는다. A2는 실측 뒤 보조 입력으로 검토할 수 있게 남긴다.
* **B2를 선택한다.** 로그는 각 환경 안에 둔다. 목적지 로그 수집은 T34의 범위다.
* **C2를 선택한다.** 서버 지표는 클러스터별 OTel Collector가 플랫폼으로 보내고(T37), 환경 이름은 Collector가 덮어쓴다. 환경별 최근 수신 시각으로 "확인 불가"를 표시한다.
* **관측 데이터는 원본 대조 게이트(T19)의 입력이 아니다.** 통제 판정은 T14 결과만 쓴다.
* **판정 규칙은 `docs/observability/`의 계약으로 고정한다.** 데이터가 없거나 오래됐거나 표본이 적으면 UNKNOWN이다. SHIFT의 FAIL은 자동으로 가중치 0으로 돌린다. WATCH는 알림과 제안까지만 하고 되돌리기는 사람이 승인한다.
* **Grafana 같은 별도 대시보드는 지금 채택하지 않는다.** 화면은 콘솔(T21) 하나다.

**이유**
* 평가 대상이 스스로를 합격시키지 않는다. 검증 Job의 결과를 대상이 보고하지 않고 플랫폼이 수거하는 것(7.5)과 같은 원칙이다
* "불명확하면 열지 않는다"(설계 원칙)와 NFR-3에 맞게, 관측이 끊기면 진행하지 않는다
* 동등성은 시험 결과로 판단한다. 목적지 로그 기능도 목적지 안에서 시험돼야 한다
* 설계 2.1의 "얕게"를 지킨다. 새 저장소는 플랫폼 지표 저장소 하나다

## 4. 결과

* T36이 판정 계약(스키마 · 기준 프로필 · 계약 시험)을 고정한다. T17 · T18 · T10 · T21 · T22는 이 계약을 쓰도록 협의한다(`docs/observability/README.md` 8절).
* T37이 클러스터별 Collector와 플랫폼 지표 저장소를 만든다. 목적지 Collector를 T34의 로그 파이프라인과 하나로 둘지는 T34와 정한다.
* 7.3 대응표에 "로그 · 모니터링: CloudWatch Logs · CloudWatch 지표 → 목적지 로그 저장소 · OTel Collector" 줄을 추가하는 설계 문서 변경을 T29에 제안한다(버전을 올리는 변경).
* 알려진 공백: 플랫폼이 자기 자신을 감시한다. 쓰기 정지 중 플랫폼이 죽으면 그 사실을 알릴 주체가 없다. 8.6의 P1 "클러스터별 컷오버 에이전트"가 다룰 문제로 남긴다.
