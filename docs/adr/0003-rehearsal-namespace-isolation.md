# [ADR-0003] 리허설 네임스페이스 격리: 템플릿 고정 + 생성 직후 격리 시험

* **상태 (Status):** 채택됨(Accepted, 2026-11-06). k3d 실측(11-03)과 시연 목적지 RKE2 재확인(11-06)에서 필수 항목이 모두 통과했다
* **날짜 (Date):** 2026-11-03
* **관련 (Related):** T3 #7, T15 #24, T2 #6, T9 #13, 설계 문서 8.4 · NFR-4, [ADR-0002](0002-rehearsal-egress-allowlist.md)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** AI가 만든 변경은 목적지 클러스터 안의 리허설 네임스페이스에서만 시험한다(8.4). 이 네임스페이스는 운영 앱이 돌 클러스터 안에 있다.
* **문제:** 격리 설정(NetworkPolicy, Pod Security, 서비스 계정 토큰, 권한, 할당량)은 오타 하나로 뚫려도 겉으로 티가 나지 않는다. 또 NetworkPolicy는 CNI가 지원하지 않으면 써도 아무것도 막지 않는다. 설계 문서 위험 표의 "격리가 설정 실수로 뚫림" 항목이다.
* **목표:** 리허설 네임스페이스를 만들 때마다 격리가 실제로 되는지 시험으로 확인하고, 실패하면 BLOCK할 수 있게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 1. 템플릿만 고정

**Pros**
* 가장 단순하다

**Cons**
* 템플릿이 맞아도 클러스터(CNI · 어드미션 설정)가 다르면 막히지 않는다. 확인할 방법이 없다

### 2. 템플릿 고정 + 생성 직후 격리 시험

템플릿으로 만들고, 바로 시험용 Pod를 띄워 막혀야 할 접속 · 생성 · 읽기를 실제로 시도한다.

**Pros**
* 클러스터마다 실제 동작을 확인한다. k3d와 RKE2의 차이도 같은 시험으로 드러난다
* 종료 코드(0 · 1 · 2)로 T15가 그대로 BLOCK 판단에 쓴다

**Cons**
* 리허설마다 약 25초가 더 든다(k3d 기준)
* 시험용 이미지를 노드에 미리 받아 둬야 한다

### 3. Kyverno 정책으로 강제

**Pros**
* 규칙을 세밀하게 쓰고 위반 보고서(PolicyReport)를 남긴다

**Cons**
* Kyverno는 T9의 P1이라 아직 없을 수 있다
* 네트워크 차단은 Kyverno가 아니라 CNI의 일이라 여전히 시험이 필요하다

## 3. 결정 사항 (Decision Outcome)

* **2번(템플릿 고정 + 생성 직후 격리 시험)을 선택한다.**
* **Pod 보안은 Pod Security Admission `restricted` 라벨로 건다. Kyverno 규칙은 T9에서 들어오면 더한다.**
* **템플릿은 YAML + `${변수}` 치환, 시험은 Python 표준 라이브러리 + `kubectl`로 만든다.**

**이유**
* 격리가 되는지는 설정이 아니라 시험 결과로 판단한다(설계 원칙 "동등성은 시험 결과로 판단한다")
* 외부 구성요소 없이 k3d와 RKE2에서 같은 방식으로 돈다
* T15(같은 담당)가 Python이라 진입점을 그대로 부른다

## 4. 결과

**구성** (`services/rehearsal-runner/`)

* `templates/`: 네임스페이스(PSA restricted), 서비스 계정 2개(토큰 자동 마운트 끔), 네임스페이스 한정 Role, NetworkPolicy 4개(ADR-0002), ResourceQuota(NodePort · LoadBalancer 0) · LimitRange
* `bin/create-and-check <ns> <프로필>`: 렌더링 → 서버 측 apply → 격리 시험. 종료 코드 0 통과 · 1 격리 실패 · 2 시험 불가
* `testing/mutation-check.sh`: 격리 설정을 빼면 시험이 실패하는지 확인

**판정 규칙**

* 양성 대조(같은 네임스페이스 접속, DNS, 허용 대상 접속)가 실패하면 시험 불가(2)로 끝낸다. 시험 환경이 고장 났을 때 "막힘"으로 착각하지 않기 위해서다.
* 네트워크 시험은 정책이 없는 별도 네임스페이스에서 같은 대상이 열리는지 함께 본다. 거기서도 닫혀 있으면 "막힘"이 아니라 "대조 불가"로 남긴다.
* `kubectl exec` 자체가 실패하면 막힘이 아니라 시험 불가다.
* N9 · N10은 `kubectl auth whoami --as`로 `rehearsal-exec` 가장이 실제로 적용되는지 먼저 확인한다. 응답 신원이 다르거나 확인하지 못하면 대조 불가로 남긴다. 인증 프록시가 가장 헤더를 버리면 호출한 사람의 권한으로 답이 나오기 때문이다. N9는 거부 메시지가 `rehearsal-exec` 신원을 가리킬 때만 통과다.

**목적지 RKE2 실측 (2026-11-06, 시연 목적지 VM, RKE2 Canal: Calico가 NetworkPolicy 적용)**

시험 코드는 `864d5b2`이고, 실행한 격리 모듈 7개 파일의 해시가 이 버전과 같다. T7 담당이 목적지 직접 API에서 관리자 권한으로 실행했다. `--as rehearsal-exec`가 그대로 전달되는 경로가 필요해서다. 개인 접속용 인증 프록시는 `--as`를 무시하고 접속한 사람의 권한으로 판단하므로 N9·N10 증거로 쓰지 않는다. 판정 함수는 바꾸지 않았고, 실행 ID 고정과 UID 조건 정리만 실행기에서 감쌌다. 시험 이미지는 busybox를 digest로 고정했다. 프로필은 `profiles/onprem.env`의 네임스페이스·라벨·컨테이너 포트를 그대로 썼다.

| 시험 | 결과 |
|---|---|
| P1~P4 양성 대조 (restricted Pod, 같은 네임스페이스, DNS, SeaweedFS 8333 · OpenBao 8200) | 통과 |
| N1 · N2 다른 네임스페이스 송신 · 수신 | 막힘 |

리허설 Pod → SeaweedFS 8333 수신은 상시 정책(#332)을, OpenBao 8200 수신은 T9 담당이 승인한 임시 정책(시험 네임스페이스의 이번 실행 라벨 Pod만)을 썼다. 원자료(보고서 JSON, Pod IP, UID)는 공개 문서에 넣지 않고 팀 채널에 보관한다.

**알게 된 것**

* busybox `nslookup`은 검색 도메인 중 하나라도 NXDOMAIN이면 종료 코드 1을 낸다. 짧은 이름 대신 `resolv.conf`의 첫 검색 도메인을 붙인 전체 이름으로 조회한다.
* NetworkPolicy는 Service 포트가 아니라 Pod의 컨테이너 포트(targetPort)에 적용된다. 목적지 프로필의 포트는 컨테이너 포트로 적는다.
* 기본 거부 정책 하나만 지워서는 뚫리지 않는다. 같은 Pod를 고르는 다른 허용 정책도 송신 · 수신을 격리하기 때문이다. 변이 시험은 정책 전체를 지운다.

* 목적지에서도 N5는 막힘이었다. Canal에서도 기본 거부가 쿠버네티스 API 송신을 막는다.
* 시험은 네트워크 판정의 대조용 네임스페이스와 가장 권한이 필요해, 개인 접속 권한만으로는 끝까지 돌릴 수 없다.

**RKE2 재확인 항목 처리**

* CNI: Canal(Calico NetworkPolicy)로 확인했다. CIS 프로필의 클러스터 기본 PSA는 따로 조회하지 않았다. 리허설 네임스페이스는 템플릿 라벨로 `restricted`를 강제하고, N7 · N8로 실제 거부를 확인했다.
* `profiles/onprem.env`: T9의 실제 네임스페이스 · 라벨 · 컨테이너 포트와 일치한다.
* 시험용 이미지: digest로 고정해 목적지에서 받았다.

**남은 일**

* 러너(T15)가 자동으로 시험할 때 쓸 신원에 시험용 Pod 생성과 `rehearsal-exec` 가장 권한을 넣는다. 이번 실측은 T7 담당의 관리자 권한으로 실행했다.
* OpenBao가 8201 등 다른 포트를 쓰는 구성으로 바뀌면 N12를 다시 시험한다.
