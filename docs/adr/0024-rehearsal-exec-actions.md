# [ADR-0024] rehearsal.exec 동작 범위와 실행 위치: 정해진 동작 3종만 허용하고, 후보는 제안서 형식으로만 받으며, 조회·변경은 API로, 공간 안 접속은 도구용 Pod로 실행한다

* **상태 (Status):** 제안됨(Proposed). T15 설계 루프에서 확정했다. 구현과 T11 연결 뒤 시연 목적지에서 실측하고 채택한다.
* **날짜 (Date):** 2026-11-05
* **관련 (Related):** T42, T15 #24, T11 #20, T38 #150, T3 #7, 설계 문서 8.3 도구 표 · 8.4, [ADR-0019](0019-agent-tool-boundary.md), [ADR-0025](0025-rehearsal-exec-spaces-and-order.md), [ADR-0026](0026-rehearsal-exec-records-and-failures.md), [호출 계약 v1](../contracts/T42-rehearsal-exec-v1-proposal.md)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:** 설계 8.3은 에이전트 도구로 `rehearsal.exec`("리허설 네임스페이스 안에서만 명령 실행, 파괴적 명령은 도구 계층에서 차단")와 `rehearsal.run/result`(검증 Job 실행 요청과 결과 조회)를 둔다. 지금 T11은 두 이름을 예약만 하고 `TOOL_NOT_PROVIDED`로 거부한다(`services/agent-worker/src/bravo_agent/tools.py`). ADR-0019는 `rehearsal.exec`를 격리 실측 뒤로 미뤘다. 데모 전에 구현하기로 했다.
* **문제:**
  * 데모 전에 어떤 도구를 어디까지 만들지 정해야 한다.
  * AI가 보내는 명령의 형태에 따라, "파괴적 명령은 프롬프트가 아니라 도구 계층에서 막는다"(설계 원칙)를 보장할 수 있는지가 갈린다.
  * T15 러너는 플랫폼(리허설 공간 밖)에 있다. 리허설 공간의 NetworkPolicy는 공간 밖에서 들어오는 연결을 막는다. 공간 안 서비스에 대한 접속 확인은 러너에서 직접 할 수 없다.
* **목표:** AI가 목적지와 같은 격리 공간에서 수정안을 시험해 보되, 허용한 동작 밖은 실행되지 않고 그 공간 밖에는 닿지 못하게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 질문 1. 도구의 범위와 명령 형태

#### 1-1. `rehearsal.exec`를 만들지 않고, 검증 실패 사유를 정확히 돌려주는 재시도만 강화

AI는 지금처럼 수정안만 내고, 러너의 검증 Job 실패 사유를 받아 다시 고친다(최대 3회).

**Pros**
* 새 실행 경로가 없어 안전 경계가 바뀌지 않는다.
* 구현량이 가장 적다.

**Cons**
* AI는 목적지에서 실제로 어떻게 동작하는지 보지 못하고 고친다. 첫 제출이 틀릴 가능성이 크고 재시도가 늘어난다.
* 설계 8.3·8.4가 정한 도구가 빠진다.

#### 1-2. 자유 셸 명령 + 차단 목록 (설계 8.3 문구 그대로)

AI가 셸 명령 문자열을 보내고, 도구 계층이 파괴적 패턴만 막는다.

**Pros**
* 유연하다. 목록을 미리 정할 필요가 없다.
* 설계 문구와 그대로 맞다.

**Cons**
* 차단 목록은 글자 쪼개기·인코딩·스크립트 파일 실행으로 피할 수 있다. 파괴적 동작을 막는다고 보장할 수 없다.
* 인자를 검사할 수 없어, 기록할 때 비밀값 포함 여부를 판단하기 어렵다.

#### 1-3. 정해진 동작 몇 가지만 제공 (채택)

AI는 미리 만든 동작 중 하나를 고르고 값만 넣는다. 동작은 ① 후보를 리허설 공간에 띄우기·고치기 ② 상태·이벤트·로그 보기 ③ 공간 안에서 접속 확인(HTTP/TCP)이다.

**Pros**
* 허용한 동작 밖은 아예 실행되지 않는다. 막을 대상이 분명하다.
* 인자는 도구 계층이 허용 목록으로 검사한 값뿐이다.

**Cons**
* 목록 밖 동작이 필요하면 동작을 추가해야 한다.
* 설계 8.3의 "명령 실행"보다 범위가 좁다.

#### 1-4. 1-3에 더해 `rehearsal.run/result`까지 제공

AI가 수정안을 내기 전에 검증 Job을 직접 돌려 보고 결과를 받는다.

**Pros**
* AI가 제출 전에 채점 결과를 보고 고칠 수 있다.

**Cons**
* 설계 8.4는 "에이전트는 테스트를 볼 수도 고칠 수도 없다"고 정한다. 결과를 반복해 받으면 문제를 고치는 대신 검사만 통과하게 맞출 수 있다.
* 결과를 합격/불합격만 주는 등 감추는 방식부터 새로 정해야 한다.
* 검증 Job은 몇 분이 걸리는데, 모델 1회 실행 한도는 180초다(`services/agent-worker/src/bravo_agent/sdk.py`).

### 질문 2. 동작을 실행하는 위치

#### 2-1. 러너가 Kubernetes API만 호출

러너가 namespace 한정 계정 `rehearsal-exec`를 가장해 API를 호출한다.

**Pros**
* 따로 Pod를 띄우지 않아 빠르다.
* 권한이 `rehearsal-exec` 역할(`services/rehearsal-runner/templates/20-rbac.yaml`)로 묶인다.

**Cons**
* 러너는 리허설 공간 밖에 있어, 공간 안 서비스로 가는 접속 확인(③)을 할 수 없다.

#### 2-2. 리허설 공간 안의 도구용 Pod에서만 실행

공간 안에 도구용 Pod(이미지 digest 고정, 계정 토큰 없음)를 띄우고, 모든 동작을 그 안에서 실행한다.

**Pros**
* 모든 동작에 공간의 NetworkPolicy가 그대로 적용된다.

**Cons**
* 조회·변경(①②)에도 Pod를 거쳐야 하고, Pod 안에 API 권한을 줘야 한다. 토큰 없는 Pod 원칙과 충돌한다.

#### 2-3. 혼합: ①②는 API 호출, ③은 도구용 Pod (채택)

**Pros**
* 각 동작이 필요한 경로만 쓴다. API 동작은 `rehearsal-exec` 권한, 접속 확인은 공간의 NetworkPolicy 안에 갇힌다.
* 도구용 Pod에는 계정 토큰을 주지 않아도 된다.

**Cons**
* 실행 경로가 둘이라 구현과 시험이 늘어난다.
* 도구용 Pod를 준비하는 시간이 든다(추정 몇 초, AI 실행 전에 미리 띄움).

### 질문 3. 동작 ①(후보 띄우기·고치기)이 받는 인자

`rehearsal-exec` 역할(`services/rehearsal-runner/templates/20-rbac.yaml`)은 Secret 읽기 권한이 없지만 Pod·Deployment를 만들 수 있다. Pod 명세에 Secret 볼륨이나 다른 서비스 계정을 넣으면, 그 Pod 안에서 Secret 값을 읽을 수 있다. 다른 namespace 요청을 거부하는 것만으로는 이 경로가 막히지 않는다.

#### 3-1. AI가 Pod·Deployment 명세를 직접 보냄

**Pros**
* AI가 시험할 수 있는 범위가 가장 넓다.

**Cons**
* Secret 볼륨, `secretKeyRef`, 서비스 계정, 토큰 projection, 이미지, 명령을 AI가 정한다. 역할 권한 안에서 Secret 값을 읽는 Pod를 만들 수 있다.

#### 3-2. 서버 템플릿 + AI가 바꿀 수 있는 필드 목록

러너가 가진 명세 템플릿을 쓰고, 비밀값이 아닌 환경변수·ConfigMap data 같은 필드만 AI가 바꾼다.

**Pros**
* 3-3보다 유연하다.

**Cons**
* 필드 목록과 검사 규칙을 제안서 스키마와 따로 유지해야 한다.
* AI가 공간 A에서 시험한 내용과 실제 제출한 수정안이 달라질 수 있다.

#### 3-3. 제출용 제안서와 같은 스키마의 초안을 받고, 공간 B와 같은 적용 코드로 반영 (채택)

AI는 제출할 수정안과 같은 JSON Schema(예: 버킷 정책 JSON, 자격 이전 파일 diff)로 초안을 보낸다. 러너는 공간 B 검증에서 쓰는 적용 코드와 서버 템플릿으로 공간 A에 반영한다. 이미지(digest), 서비스 계정, 토큰 미마운트, 볼륨, 명령은 템플릿이 정하고 인자로 받지 않는다.

**Pros**
* Secret 연결·계정 지정·이미지 교체를 표현할 입력 자체가 없다.
* AI가 시험한 것과 채점받는 것이 같은 코드로 적용된다.
* 인자 검사가 기존 제안서 스키마 검사(T11)와 같다.

**Cons**
* 제안서 스키마로 표현할 수 없는 변경은 시험할 수 없다.

#### 3-4. 3-3 + 클러스터 정책(ValidatingAdmissionPolicy)으로 Secret 참조·계정 지정 거부

**Pros**
* 러너 코드에 결함이 있어도 클러스터가 한 번 더 막는다.

**Cons**
* 클러스터 범위 자원이라 T7과 합의·배포가 필요하고 데모 전 준비 시간이 늘어난다.

동작 ②③의 인자는 러너가 정한 형식의 값만 받는다. 도구 이름·필드명·필수 여부·응답은 [호출 계약 v1](../contracts/T42-rehearsal-exec-v1-proposal.md)이 원본이다. namespace는 인자로 받지 않고 러너가 그 시도의 공간 A로 고정한다.

| 동작 | 인자 |
|---|---|
| ② 상태·로그 보기 | 대상 종류(`pod`·`deployment`·`events`·`logs` 중 하나), 이름(`[a-z0-9-]{1,63}`), 로그 줄 수(최대 200) |
| ③ 접속 확인 | 공간 A 안 Service 이름, 포트(1~65535), 방식(`TCP`·`HTTP GET`·`HTTP HEAD`), HTTP 경로(`/`로 시작, 최대 256자) |

도구용 Pod 명세도 러너 템플릿으로만 만들고 AI가 바꿀 수 없다.

## 3. 결정 사항 (Decision Outcome)

* **1-3(정해진 동작 3종), 2-3(혼합 실행 위치), 3-3(제안서 스키마 초안 + 공간 B와 같은 적용 코드)을 선택한다.**
* **1-4의 `rehearsal.run/result`는 향후 확장 옵션으로 남긴다.** 결과를 합격/불합격만 주는 방식이 정해진 뒤 검토한다.
* **3-4는 보류한다.** 데모 뒤 T7과 클러스터 정책을 합의하면 추가한다.
* **1-1(도구 미구현)과 1-2(자유 셸 + 차단 목록), 2-1·2-2(단일 실행 위치), 3-1·3-2는 현 단계에서 채택하지 않는다.**
* **선행 조건: 모델 → T15 실행부 통로 계약.** 모델은 T38 지정 VM의 T11 프로세스 안에서 도구를 부른다(`services/agent-worker/src/bravo_agent/sdk.py`). T38 제품 실행 mailbox(`product_execution_mailbox.py`)는 실행 요청과 영수증만 넘기고, 실행 도중의 도구 호출은 중계하지 않는다. 다음을 T38·T11과 합의하기 전에는 실행부를 열지 않는다. 통로는 2026-11-06 T38이 확정했다(T11 자식 프로세스 → 실행 전용 로컬 채널 → 기존 T38 broker → 고정 사설 TLS T15 경로). 메시지 형식은 호출 계약 v1에서 T11 확인을 받는다.
  * 통로와 인증 주체(누가 어떤 신원으로 러너를 부르는가)
  * 요청 결속: 실행 ID·시도 번호·공간 A UID. 다른 시도나 지워진 공간의 요청은 거부한다.
  * 요청 ID와 중복 요청 처리: 같은 요청 ID는 한 번만 실행하고 같은 결과를 돌려준다.
  * 연결 종료 규칙: 모델 실행이 끝나거나 끊기면 그 시도의 실행부를 닫는다.

**이유**
* 설계 원칙 "파괴적 명령은 도구 계층에서 막는다"를 차단 목록이 아니라 허용 목록으로 보장한다.
* 공간 안 접속은 공간 안에서 나가야 실제 NetworkPolicy 결과를 얻는다.
* 후보 명세를 러너가 정해야 `rehearsal-exec` 권한 안에서도 Secret이나 다른 계정 권한에 닿는 Pod를 만들 수 없다.
* 설계 8.3·8.4의 도구를 데모 전에 제공하되, 채점 노출(8.4)은 만들지 않는다.

## 4. 결과

* 좋은 점: AI가 목적지와 같은 공간에서 수정안을 먼저 시험해, 첫 제출이 통과할 가능성이 오른다.
* 나쁜 점: 동작 목록과 인자가 고정이라 새 작업 유형이 생기면 동작과 제안서 스키마를 추가해야 한다. 설계 8.3 문구보다 좁아 설계 문서 갱신이 필요하다.
* 남은 확인: 호출 계약 v1의 T11 확인(전동훈), 러너 신원에 `pods/exec`·`rehearsal-exec` 가장 권한(T7)
* 공간 분리와 순서는 [ADR-0025](0025-rehearsal-exec-spaces-and-order.md), 기록과 실패 처리는 [ADR-0026](0026-rehearsal-exec-records-and-failures.md)에서 정한다.
