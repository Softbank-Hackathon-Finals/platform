# [ADR-0026] rehearsal.exec 기록과 실패 처리: 동작·검사된 인자·결과 코드만 기록하고, 결과를 모르는 변경이 생기면 그 시도의 exec를 닫는다

* **상태 (Status):** 제안됨(Proposed). T15 설계 루프와 독립 검토(2026-11-05)를 거쳐 확정했다. 재시도 횟수·간격과 시간 한도는 추정값이라 시연 목적지에서 실측한 뒤 조정하고 채택한다. 2026-11-06 호출 계약 v1에 맞춰 T15 실행 기록의 전달 칸(`exec_events`)과 접속 확인 결과 키를 정했다.
* **날짜 (Date):** 2026-11-05
* **관련 (Related):** T42, T15 #24, T11 #20, T10 #19, T21 #27, T24, T38 #150, 설계 문서 8.4 · 8.6 Executor 계약, [ADR-0019](0019-agent-tool-boundary.md), [ADR-0023](0023-rehearsal-runner-attempt-evidence.md), [ADR-0024](0024-rehearsal-exec-actions.md), [ADR-0025](0025-rehearsal-exec-spaces-and-order.md), [호출 계약 v1](../contracts/T42-rehearsal-exec-v1-proposal.md)

## 1. 배경 및 문제 상황 (Context and Problem Statement)

* **상황:**
  * T11의 도구 호출 기록은 서명된 시도 기록 `tool_events` → T10 `data.tool_events` → 감사 로그(T24) → 콘솔(T21)로 전달된다. 감사 로그는 지울 수 없다.
  * 실제 chatgpt-plan 경로에서는 모델이 다른 VM에서 돌아 T11 이벤트가 T15에 오지 않는다. 제품 응답은 `tool_events_status=UNAVAILABLE`이다(`services/agent-worker/src/bravo_agent/subscription_product.py`).
  * ADR-0019는 파괴적 시도를 원문 없이 범주(`category`)만 기록한다.
  * 동작 결과는 AI 응답으로 모델 공급자에게도 전달된다.
  * 지금 러너는 T11 이벤트를 시도가 끝날 때 proposer에서 한 번에 모은다(`services/rehearsal-runner/src/rehearsal_runner/attempt_store.py` `collect_tool_events`). 이벤트 값은 문자열·정수·불리언이면 그대로 서명한다.
  * 모델 1회 실행은 최대 8턴·180초다(`services/agent-worker/src/bravo_agent/sdk.py`).
* **문제:**
  * 무엇까지 기록하고 AI에게 돌려줄지 정해야 한다. 출력(로그·응답 본문)에 비밀값이 섞이면 지울 수 없는 감사 로그나 모델 공급자에게 간다.
  * 동작이 실패했을 때 즉시 멈출지, 다시 시도할지 정해야 한다. 변경이 서버에 반영된 뒤 응답만 사라질 수 있어, "응답 없음"만으로는 실행 여부를 알 수 없다.
  * 결과를 모르는 변경 뒤에 AI가 새로 호출해도 같은 변경이 반복될 수 있다.
  * 동작 실행 직후 러너가 종료되면, 끝날 때 모으려던 이벤트가 사라져 어떤 동작이 실행됐는지 복구할 수 없다.
  * 재시도까지 합친 시간이 모델 1회 실행 한도를 넘을 수 있다.
* **목표:** 비밀값이 영구 기록과 모델 공급자에 가지 않게 하고, 결과를 모르는 변경은 반복하지 않으며, 재시작 뒤에도 실행된 동작을 복구하고, 모든 경우가 시간 한도 안에 끝나게 한다.

## 2. 고려한 옵션들 (Considered Options)

### 질문 1. 기록 범위

#### 1-1. 동작·인자·출력을 모두 기록

**Pros**
* 콘솔과 감사 로그에서 AI가 한 일을 그대로 볼 수 있다.

**Cons**
* 출력에 섞인 비밀값이 지울 수 없는 감사 로그에 남는다.

#### 1-2. 동작 이름·결과 코드와 digest만 기록 (ADR-0019 방식)

**Pros**
* 비밀값이 기록에 남을 일이 없다.

**Cons**
* 콘솔에서 "무엇에 접속했는지" 같은 내용을 읽을 수 없다.

#### 1-3. 동작 이름·검사된 인자·결과 코드는 기록하고, 출력은 digest와 크기만 (채택)

인자는 ADR-0024에서 허용 목록으로 검사한 값뿐이다. 동작 ①의 초안은 원문 대신 제안서 digest만 기록한다.

**Pros**
* 콘솔에 "시험 버킷에 무인증 접속 → 403 거부"처럼 보여 줄 수 있다.
* 비밀값이 섞일 수 있는 출력은 기록하지 않는다.

**Cons**
* 출력 원문은 감사 로그에서 볼 수 없다.
* 기록 필드를 동작별로 고정해야 한다.

### 질문 2. 실패 처리

#### 2-1. 실패하면 항상 즉시 중단 (재시도 없음)

**Pros**
* 규칙이 단순하고 같은 동작이 두 번 실행될 일이 없다.

**Cons**
* 도구용 Pod 준비 전 같은 일시 오류에도 시도가 실패해, 회차 전체를 다시 돌리게 된다.

#### 2-2. 실패하면 항상 정해진 횟수만큼 재시도

**Pros**
* 일시 오류에 강하다.

**Cons**
* 변경이 반영된 뒤 응답만 사라진 경우에도 다시 실행해, 같은 변경이 두 번 들어갈 수 있다. 설계 8.6 Executor 계약의 "응답 유실 시 같은 호출을 반복하지 않는다"와 맞지 않는다.

#### 2-3. 실패를 세 종류로 나눠 처리 (채택)

* **즉시 중단:** 파괴적 동작, 격리 미통과, 공간 UID 불일치, 다른 시도의 요청, 권한 거부. 실행하지 않는다.
* **재시도:** 요청이 전송되지 않았음이 확인된 오류(연결 거부, 도구용 Pod 준비 전)와, 상태를 바꾸지 않는 동작 ②③의 일시 실패. ③은 TCP 연결과 HTTP `GET`·`HEAD`만 허용하므로 상태를 바꾸지 않는다고 본다.
* **결과 모름:** 동작 ①의 요청이 전송된 뒤 응답 유실·시간 초과·끊김. 다시 실행하지 않고 질문 3에 따라 처리한다.

**Pros**
* 반복해도 안전한 경우에만 재시도한다.
* 실패 사유가 종류별로 분명해, AI와 운영자가 같은 사유를 본다.

**Cons**
* 요청 전송 여부를 구분하는 구현이 필요하다.
* 새 사유 코드는 ADR-0019의 열거값 밖이라 콘솔·감사 로그 표시를 맞춰야 한다.

### 질문 3. 결과를 모르는 변경이 생긴 뒤

공간 A는 AI 실행이 끝나면 지우고, 채점은 새 공간 B에서 한다(ADR-0025).

#### 3-1. 그 시도 전체를 사람 확인(`NEEDS_HUMAN`)으로 고정

**Pros**
* 가장 보수적이다.

**Cons**
* 응답이 한 번만 유실돼도 시도가 멈춘다. 공간 A는 채점에 쓰지 않으므로, 공간 A의 불확실성 때문에 채점까지 멈출 이유가 약하다.

#### 3-2. 실제 상태를 다시 읽어 반영 여부를 판정한 뒤 계속 (설계 8.6 방식)

**Pros**
* 시도와 exec를 모두 계속 쓸 수 있다.

**Cons**
* 동작 ①의 작업 종류마다 반영 여부 판정 코드가 필요하다. 판정이 틀리면 같은 변경이 반복된다.

#### 3-3. 그 시도의 남은 exec 호출을 모두 거부하고, 제출과 공간 B 채점은 진행 (채택)

이후 exec 호출은 `EFFECT_UNKNOWN`으로 거부한다. AI는 수정안 제출만 할 수 있다.

**Pros**
* AI가 새로 호출해도 같은 변경이 반복되지 않는다.
* 채점은 AI가 손대지 않은 공간 B에서 하므로 결과에 영향이 없다. 시연이 멈추지 않는다.

**Cons**
* 그 시도에서 AI는 더 시험하지 못하고 제출해야 한다.

### 질문 4. 재시작 뒤 동작 기록 복구

#### 4-1. 지금처럼 시도가 끝날 때 T11 이벤트를 한 번에 모음

**Pros**
* 바꿀 것이 없다.

**Cons**
* 동작 실행 직후 러너가 종료되면 이벤트가 사라져, 어떤 동작이 실행됐는지 복구할 수 없다.

#### 4-2. 실행 전·후 기록을 T15 시도 기록에 바로 남김 (채택)

동작마다 실행 전에 순번·동작 이름·검사된 인자·인자 digest를 쓰기 1회 서명 기록으로 남기고, 실행 뒤에 결과 코드·사유·출력 digest·크기를 남긴다.

**Pros**
* 재시작 뒤에도 실행된 동작을 순서대로 복구한다. 결과 기록이 없는 동작은 결과 모름으로 확정된다.
* T11 이벤트와 대조할 수 있다.

**Cons**
* 동작마다 서명 기록 쓰기 두 번이 더 든다.

## 3. 결정 사항 (Decision Outcome)

* **1-3, 2-3, 3-3, 4-2를 선택한다.**
* **기록 필드.** 동작별 허용 키만 서명한다. 목록 밖 키나 형식이 맞지 않는 값이 있으면 그 이벤트 목록 전체를 `UNAVAILABLE`로 둔다(지금 `collect_tool_events` 규칙과 같다).

  | 동작 | 기록 키 |
  |---|---|
  | 공통 | `run_id`, `attempt`, `seq`, `action`, `request_id`, `args_sha256`, `result_code`, `reason`, `stage`, `output_sha256`, `output_bytes` |
  | ① 띄우기·고치기 | `proposal_digest` |
  | ② 상태·로그 보기 | `target_kind`, `target_name`, `lines` |
  | ③ 접속 확인 | `service`, `port`, `method`, `path`, `probe_outcome`(`CONNECTED`·`REFUSED`·`TIMED_OUT`·`DNS_FAILED`), `http_status` |

  값은 문자열·정수·불리언만 쓰고, 해당 없는 키는 `null`로 두지 않고 뺀다. `probe_outcome`·`http_status`는 코드가 만든 값이라 비밀값이 섞이지 않고, 콘솔이 "무인증 접속 → 403 거부"를 보여 주는 근거다.
* **전달 칸.** T15 실행 기록은 T11 이벤트와 섞지 않고 시도 기록의 `exec_events`(`exec_events_status`: `OFF`·`COMPLETE`·`UNAVAILABLE`)로 따로 서명한다. T10은 `data.exec_events`로 넘긴다. `tool_events`는 지금 규칙(T11 목록을 순서 그대로, 빼거나 더하지 않음)을 유지한다. 실제 chatgpt-plan 경로에서도 실행된 동작이 T10에 닿게 하기 위해서다. 두 목록은 `request_id`로 대조한다.

* **AI에게 돌려주는 값.** 결과 코드, 사유 코드, 동작별 상태 필드, 그리고 출력 끝부분(최대 2KiB)이다. 출력은 다음 검사를 통과할 때만 돌려준다.
  * 공간 A에는 운영 비밀값을 넣지 않고, 러너가 만든 리허설 전용 값만 넣는다. 러너는 그 값을 알기 때문에 원문·base64·URL 인코딩 형태로 출력에서 찾는다.
  * 값이 발견되거나, 출력이 UTF-8이 아니거나, 검사가 실패하면 출력 전체를 돌려주지 않고 `OUTPUT_WITHHELD`만 돌려준다.
  * 러너가 값을 알 수 없는 비밀값(예: 외부에서 발급받는 자격)이 필요한 작업은, 검사 방법이 정해질 때까지 `rehearsal.exec`를 끈다(ADR-0025).
* **사유 코드.** 고정된 열거값만 쓰고 자유 문장은 넣지 않는다: `BLOCKED`, `FOREIGN_ATTEMPT`, `TIMEOUT`, `NONZERO_EXIT`, `UNAVAILABLE`, `EFFECT_UNKNOWN`, `OUTPUT_WITHHELD`, `BUDGET_EXHAUSTED`. 같은 값이 AI 응답 → 시도 기록 `exec_events` → T10 `data.exec_events` → 감사 로그·콘솔까지 전달된다.
* **시간과 횟수 (추정값, 실측 뒤 조정).**
  * 동작 하나의 한도 15초에 재시도(최대 2회, 간격 1초 → 3초)를 포함한다. 남은 시간이 다음 재시도에 모자라면 재시도하지 않는다.
  * 시도당 exec 호출은 5회다. 재시도는 횟수에 세지 않는다.
  * 모델 1회 실행에서 exec가 쓰는 시간은 첫 호출부터 합쳐 90초까지다. 횟수나 시간을 넘으면 `BUDGET_EXHAUSTED`로 거부한다. 최악의 경우 5 × 15초 = 75초라 90초 안에 들어가고, 나머지 90초를 모델 추론과 제출에 남긴다.
  * 턴 수: exec 5회 + 실패 사유 읽기 1회 + 제출 1회 = 7턴으로 8턴 안에 들어간다.
* **재시작.** 실행 전 기록만 있고 결과 기록이 없는 동작은 `EFFECT_UNKNOWN`으로 확정한다. 그 시도는 ADR-0025에 따라 사람 확인으로 넘긴다. T11 이벤트를 모을 수 없으면 `tool_events_status`는 `UNAVAILABLE`이고, 실행된 동작은 T15 실행 기록으로 확인한다.
* **3-1, 3-2는 현 단계에서 채택하지 않는다.** 1-1, 1-2, 2-1, 2-2, 4-1도 채택하지 않는다.
* **출력 원문을 콘솔에 보여 달라는 요구가 생기면, 비밀값 검사를 거친 표시 경로를 별도로 검토한다.**

**이유**
* 지울 수 없는 감사 로그와 모델 공급자에게는 비밀값이 섞일 수 있는 값을 보내지 않는다.
* 결과를 모르는 변경을 반복하지 않는 규칙은 Executor 계약(8.6)과 T15 시도 실행(ADR-0023)과 같다. 채점은 공간 B에서 하므로 공간 A의 불확실성 때문에 시도를 멈추지 않는다.
* 실행 전에 기록을 남겨야 재시작 뒤에도 무엇이 실행됐는지 알 수 있다.
* 재시도를 포함한 상한을 두어야 실패 경로에서도 모델 실행 한도 안에 제출할 수 있다.

## 4. 결과

* 좋은 점: 운영자와 AI가 같은 실패 사유를 본다. 감사 로그와 모델 공급자에게 리허설 비밀값이 가지 않는다. 재시작 뒤에도 실행된 동작을 복구한다.
* 나쁜 점: 출력 원문은 감사 로그에서 볼 수 없다. 출력이 막히면 AI가 볼 수 있는 정보가 줄어든다. 사유 코드 목록을 T21·T24와 맞춰야 한다.
* 남은 확인: 숫자는 시연 목적지 격리 시험 때 실측해 조정하고 이 ADR에 남긴다. 새 사유 코드의 표시는 T21(이상무)·T24(전동훈)와 맞춘다. `data.exec_events`를 싣는 T10 이벤트 위치는 T10(류지환)과 맞춘다. 자격 이전 작업의 공간 A에 들어가는 값을 러너가 알 수 있는지는 T9와 확인한다.
