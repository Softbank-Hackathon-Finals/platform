# 해야 할 일: 단계별 정리

> 설계 문서(`docs/design.html` 11장)의 작업을 **선행 관계 순서대로** 정리한 것이다. 같은 단계 안의 작업은 동시에 진행할 수 있다.

## 읽는 법

- **단계**: 앞 단계의 선행 작업이 끝나야 시작할 수 있다. 같은 단계 안에서는 병렬로 진행한다.
- **선행과 통합 시점**: `선행`은 끝나야 시작할 수 있는 작업이다. `(통합 시점: …)`은 먼저 시작해도 되고(모의 환경 · 모의 데이터), 완료 확인만 그 작업 뒤에 한다(설계 문서 그림의 점선).
- **우선순위**: `P0` 데모에 꼭 필요 · `P1` 점수에 중요 · `P2` 여유 있으면
- **구조**: 레포는 두 개다(둘 다 public). `platform`(플랫폼 코드 · 인프라 · 설계 문서 · 작업 관리)과 `demo-chat`(이전 대상 데모 앱).
- 각 작업은 GitHub 이슈 하나에 대응한다(제목 · 체크리스트 · 완료 기준).

## 작업 규칙

**진행 상황의 기준은 [프로젝트 보드](https://github.com/orgs/Softbank-Hackathon-Finals/projects/2)(이슈)다.** 이 문서는 계획이고, 체크박스와 담당은 보드를 따라 자동으로 바뀐다.

1. 작업 전에 보드나 이 문서에서 **자기 작업**을 찾고, **선행** 작업이 끝났는지 본다.
2. 작업은 브랜치에서 한다(예: `t3-rehearsal-ns`). `main`은 보호돼 있어 PR과 CI(`secrets` · `infra` · `platform`) 통과가 필요하다. 리뷰 승인은 필요 없다. 단, `.github/workflows/`와 `CODEOWNERS`를 바꾸는 PR은 본인 외 팀원 1명의 승인이 필요하다.
3. 커밋 메시지와 PR 제목 앞에 작업 번호를 붙인다. 예: `[T3] 리허설 네임스페이스 템플릿 추가`. PR 본문에 `Refs #이슈번호`, 마지막 PR이면 `Closes #이슈번호`. demo-chat의 PR은 `Closes Softbank-Hackathon-Finals/platform#이슈번호`.
4. **끝낸 할 일은 이슈에서 체크한다**(이슈 화면에서 클릭하거나 `python3 scripts/sync_tasks.py tick T3 2`). 이 문서의 체크박스는 직접 고치지 않는다.
5. 담당은 이슈의 Assignees로 정한다. 작업마다 한 명이고, 그 작업 영역의 담당자(설계 문서 11.2) 중에서 고른다.
6. 그러면 자동으로(`sync-tasks` 워크플로):
   - 체크가 하나라도 생기면 보드 **In progress**, 전부 체크되면 이슈가 닫히고 **Done**
   - 이 문서의 체크박스 · 담당 · 역할 분담이 봇 PR로 갱신된다
7. 계획을 바꿀 때(작업 추가, 할 일 문장 수정 · 추가 · 다른 작업으로 이동, 우선순위)는 이 문서를 고쳐 PR로 올린다. 머지되면 이슈에 반영되고, 이미 한 체크는 유지된다.
8. 작업 번호(T번호)는 바꾸거나 다시 쓰지 않는다. 이슈와 짝을 맞추는 열쇠다. 설계 문서에는 진행 상황을 적지 않는다.

Claude Code는 `/todo-task`, Codex는 `$todo-task`로 이 순서를 따르는 스킬을 쓸 수 있다(`.claude/skills/todo-task`).
