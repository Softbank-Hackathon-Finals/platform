# 해야 할 일: 단계별 정리

> 설계 문서(`docs/design.html` 11장)의 작업을 **선행 관계 순서대로** 정리한 것이다. 같은 단계 안의 작업은 동시에 진행할 수 있다.

## 읽는 법

- **단계**: 앞 단계의 선행 작업이 끝나야 시작할 수 있다. 같은 단계 안에서는 병렬로 진행한다.
- **선행과 통합 시점**: `선행`은 끝나야 시작할 수 있는 작업이다. `(통합 시점: …)`은 먼저 시작해도 되고(모의 환경 · 모의 데이터), 완료 확인만 그 작업 뒤에 한다(설계 문서 그림의 점선).
- **우선순위**: `P0` 데모에 꼭 필요 · `P1` 점수에 중요 · `P2` 여유 있으면
- **구조**: 레포는 두 개다(둘 다 public). `platform`(플랫폼 코드 · 인프라 · 설계 문서 · 작업 관리)과 `demo-chat`(이전 대상 데모 앱).
- 각 작업은 GitHub 이슈 하나에 대응한다(제목 · 체크리스트 · 완료 기준).

## 작업 규칙

**진행 상황의 기준은 [프로젝트 보드](https://github.com/orgs/Softbank-Hackathon-Finals/projects/2)(이슈)다.** 이 문서는 계획이고, 체크박스와 담당은 보드를 따라 자동으로 바뀐다.

1. 작업 전에 보드나 이 문서에서 **자기 작업**을 찾고, **선행** 작업이 끝났는지 본다.
2. `develop`에서 `feature/T번호-설명` 브랜치를 만들어 `develop`으로 PR을 올린다(예: `feature/T3-rehearsal-ns`). `main`은 release/hotfix로 반영한다. 두 브랜치는 보호돼 있어 PR과 CI(`secrets` · `infra` · `platform`) 통과가 필요하다. Gitflow 순서는 `docs/development.md`를 따른다. 현재 대상 브랜치의 리뷰 요건과 변경 요청 해소를 충족한 최종 커밋을 GitHub 기본 auto-merge로 병합하도록 예약할 수 있다. `.github/workflows/`와 `CODEOWNERS`를 바꾸는 PR은 팀원에게 리뷰 요청 알림이 간다.
3. 커밋 메시지와 PR 제목 앞에 작업 번호를 붙인다. 예: `[T3] 리허설 네임스페이스 템플릿 추가`. PR 본문에 `Refs #이슈번호`, 마지막 PR이면 `Closes #이슈번호`. demo-chat의 PR은 `Closes Softbank-Hackathon-Finals/platform#이슈번호`.
4. **끝낸 할 일은 이슈에서 체크한다**(이슈 화면에서 클릭하거나 `python3 scripts/sync_tasks.py tick T3 2`). 이 문서의 체크박스는 직접 고치지 않는다.
5. 담당은 이슈의 Assignees로 정한다. 작업마다 한 명이고, 그 작업 영역의 담당자(설계 문서 11.2) 중에서 고른다.
6. 그러면 자동으로(`sync-tasks` 워크플로):
   - 체크가 하나라도 생기면 보드 **In progress**, 전부 체크되면 이슈가 닫히고 **Done**
   - 이 문서의 체크박스 · 담당 · 역할 분담이 봇 PR로 갱신된다
7. 계획을 바꿀 때(작업 추가, 할 일 문장 수정 · 추가 · 다른 작업으로 이동, 우선순위)는 이 문서를 고쳐 PR로 올린다. 머지되면 이슈에 반영되고, 이미 한 체크는 유지된다. 이슈 본문 · 제목은 직접 고치지 않는다(보드에서 연 카드도 같다. 다음 동기화 때 이 문서 내용으로 덮어써진다).
   - 새 작업은 현재 마지막 번호 다음의 빈 번호로 해당 `## N단계` 섹션 안에 추가한다. 이슈와 역할 분담 목록의 줄은 봇이 만든다.
   - 작업을 빼면 이슈는 닫히지 않는다. 이슈를 직접 닫고, 역할 분담 목록의 줄도 지운다.
8. 작업 번호(T번호)는 바꾸거나 다시 쓰지 않는다. 이슈와 짝을 맞추는 열쇠다. 설계 문서에는 진행 상황을 적지 않는다.

Claude Code는 `/todo-task`, Codex는 `$todo-task`로 이 순서를 따르는 스킬을 쓸 수 있다(`.claude/skills/todo-task`).

## 1단계

### [T41] 기존 Actions 인증을 재사용하는 Merge Queue 자동 등록

**어디에 필요** T40 큐에 준비된 일반 PR을 사람이 반복 등록하는 절차를 줄인다.

**만들 것** 기존 PROJECT_TOKEN을 재사용하는 신뢰된 Actions workflow, exact-head 큐 등록과 보류 판정, 회귀 시험·운영 절차.

- **우선순위** P0 · **영역** 통합 · CI · **담당** 이상무, 류지환
- **선행** `T40` · **후속** `T28` · **설계 문서** 8.3 (저장소 병합 자동화, 제품 실행 계약 변경 없음)

**목표** 사람 승인을 필수로 추가하지 않고 CI가 준비된 PR을 GitHub 기본 큐에 등록한다. 같은 revision의 실패를 무한 재시도하거나 미해결 지적을 지우지 않는다.

**할 일**
- [x] 기존 봇·인증 재사용, PR 코드 실행 없는 exact-head 등록·보류·실패 처리와 회귀 시험
- [x] 실제 기존 인증으로 자동 큐 등록과 merge_group CI 실행·병합을 확인하고 보류 PR 제외 검증
- [x] 활성화·중단·재시도·적용 범위와 운영 결과 기록

**완료 기준** 새 계정·키·Slack 봇 없이 일반 PR의 실제 자동 큐 등록과 CI 병합이 확인된다. main·GitHub 보호 규칙·제품 승인·기존 sync 동작을 유지하며, Draft·미해결 수정 요청·충돌·같은 head의 큐 실패는 자동 재등록하지 않는다.

**어디에 필요** 회의에서 합의한 develop 통합 속도 개선. main과 운영 실행 승인은 유지한다.

**만들 것** merge_group 필수 CI, GitHub 기본 Merge Queue, 운영 규약·검증 기록.

- **우선순위** P0 · **영역** 통합 · CI · **담당** 이상무
- **선행** 없음 · **후속** `T28` · **설계 문서** 8.3 (저장소 통합 절차, 제품 실행 계약 변경 없음)

**목표** develop은 사람 승인을 필수로 요구하지 않고 최신 기준선과 앞선 PR을 합친 결과의 CI로 병합한다. 알려진 결함은 큐에 넣지 않는다.

**할 일**
- [x] merge_group SHA·검사 범위·필수 결과의 회귀 시험과 운영 규약 반영
- [x] 별도 시험 브랜치에서 실제 큐 병합과 실패 차단을 확인하고 develop 규칙 적용
- [x] 기존 PR의 충돌·실패·미해결 지적을 정리하고 main 불변·설정 readback·복구 절차 기록

**완료 기준** develop의 숫자 승인과 코드 오너 승인 요구가 모두 해제되고 Merge Queue가 필수다. secrets·infra·platform은 유지하며 실제 merge_group 검사 실패는 병합되지 않는다. main·운영 실행 승인·타 담당 범위 합의·Slack 봇 중단은 유지한다.
