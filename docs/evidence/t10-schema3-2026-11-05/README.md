# T10 스키마 3 운영 연결 검증

실제 플랫폼 DB는 스키마 2였고, 실행 중인 창 수신 서버도 2까지만 허용했다. 저장소에 v3 호환 코드가 있다는 사실만으로 현재 DB를 변경할 수 없었다. 수신 서버 교체 → 새 연결 확인 → migration 역할로 0003 적용 → 기존 자료와 runtime 권한 대조 순서를 고정했다.

## 현재 근거

| 단계 | 검증 범위 | 결과 |
|---|---|---|
| 실제 클러스터 읽기 | 실행 중인 수신 파일의 해시·허용 버전, DB/Pod/자격 참조 | v2 전용 소비자 확인. 원본 쓰기 0 |
| 변경 전 백업 | 실제 DB를 메모리에서 암호화, 기존 KMS로 감싼 복구 키, 호스트 밖 보존 | 성공. 평문 파일·역할 암호 출력 0 |
| 격리 복원 | 네트워크 없는 PostgreSQL에 역할·DB·ACL을 포함해 복원 | DB·역할·열·제약·권한·테이블·시퀀스 7개 일치 |
| 복원본 migration | 기존 migration 역할로 정본 0003, 재실행과 runtime 권한 | schema 3, 기존 행 보존, 빈 등록 테이블, SELECT/INSERT만 허용, 재실행 거부 |
| 로컬 회귀 | 플랫폼 전체 / 등록·수신·Job / 최종 Job 변경 | 996 통과·2 제외 / 116 통과 / 8 통과 |
| 실제 수신 배포·schema 3 | 합의된 운영 창에서 적용·재접속·권한 확인 | 진행 전 |
| 실제 환경·앱·계획 등록 | 실제 사람 신원과 tenant, collector·릴리스 대조 | 인수 대기 |

복원 중 ACL의 `NULL`과 PostgreSQL 기본 ACL 표현은 기본 권한으로 정규화해 비교했다. 스키마 3는 처음 등록할 테이블을 추가할 뿐 사람의 권한이나 실제 계획을 만들지 않는다. 개인 AWS SSO의 클러스터 관리 권한과 T38 Actions 서비스 OIDC도 자동으로 등록 권한이 되지 않는다.

SSM 이미지 전송에서 문서 worker의 IPC 경로/timeout 실패가 발생했다. 대체 문서는 터널까지 열렸지만 수신 서버 실행을 확인하지 못했으므로 이미지 반영으로 기록하지 않았다. 자기 터널 3개와 로컬 프로세스 종료, 수신 포트의 자기 listener 부재를 확인했다. 다른 담당의 T8 복구 창 동안 추가 전송·DB 변경을 중지했다.

[검증 영수증](verification.json)에는 개인·계정·클러스터 주소를 제외한 해시와 판정만 둔다. 원본 덤프·접속 참조·SSM 기록은 운영자의 비공개 암호화 보존 대상이다. 백업은 플랫폼 DB 복구 검증이며, Secret·전체 클러스터·etcd 재해복구 시험으로 확대하지 않는다.

## 인수 경계

- [등록 계약](../../contracts/T10-registration.md)의 실제 사람 인증·tenant 권한과 환경·릴리스 검사를 유지한다. 합성 계획을 운영 계획으로 승격하지 않는다.
- T10 원문 저장과 목적지 누락 차단은 [별도 검증 #294](https://github.com/Softbank-Hackathon-Finals/platform/pull/294)에서 확인했다. T19 통제 결과의 PASS를 뜻하지 않는다.
- T19는 출발지·목적지 실제 원문과 같은 운영 계획을 인수한 뒤 BLOCK→수정→PASS를 확인해야 한다. 현재 목적지 원문은 미인수이며 T19 완료 체크를 추가하지 않는다.
