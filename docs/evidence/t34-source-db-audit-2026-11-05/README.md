비공개 원문에서 다시 계산해 대조했다.

## 실행과 정리 범위

기존 관리자 신원의 로컬 Unix socket 접속을 사용했다. 비밀번호·Secret 값은 읽지 않았으며,
이 접속으로 외부 TLS 경로의 검증까지 주장하지 않는다. 실제 SQL 신원과 관리자 속성을
확인했다. 앱·클러스터·Pod UID·실행 이미지·재시작 횟수·현재 primary를 전후 대조했다.

DDL은 **업무 DB와 분리된 기존 postgres 유지보수 DB**에서 수행했다. 기존 pgAudit 확장과
DDL 로그 설정을 먼저 읽기 전용 확인한 뒤, 고유한 자체 시험 스키마/표를 한 트랜잭션에서
생성·삭제했다. 실제 생성 확인과 커밋 후 스키마 부재를 확인했다. 업무 테이블·앱 설정·
역할·확장·감사 정책 변경은 없었다. 이번 SSM 터널만 종료했다.

## 실패 기록과 남은 인수

- 첫 접속은 SSM 포트 플러그인 준비 실패로 DB 호출 전에 중단됐다. 실패 세션의 서버 측
  Terminated와 로컬 plugin 종료를 확인한 뒤 새 세션으로 수행했다.
- 초기 로그인 검색 `61c42520-9f54-4df8-ac7a-207837bb7ce5`는 조회 시각보다 나중인 종료 로그까지
  포함해 UNKNOWN/TOOL_ERROR였다. 검색 시각 상한을 적용한 별도 새 실행으로 재검증했다.
- 중간 `5432d09e-1b90-4fcd-94bc-062f7da9a956`은 검색이 통과했지만 원문 보존 인수가 부족한
  진단 실행으로 남긴다. 위 최종 실행만 원문·증거 해시 보존을 확인한 근거다.

이는 출발지 Pod 로그의 실제 검색 검증이다. **목적지 감사 수집, Collector를 통한 중앙 전달,
검색 저장소의 보관/불변성, S3 Object Lock, 최소권한 전용 조회자, 운영 계획 등록**은 별도다.
T34의 양쪽 완료 체크와 T19 최종 게이트·컷오버 승인을 올리지 않는다.
