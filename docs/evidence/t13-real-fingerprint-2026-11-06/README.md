# T13 DB 안 지문 비교 실제 두 DB 실행 (2026-11-06)

**실제 출발지와 목적지 DB에서 `db-sql-v1` 지문 비교가 `MATCH`였다.** 컷오버 실행기가 기본으로 쓰는 `DbFingerprintComparer`를 그대로 돌렸고, 두 표 모두 데이터와 스키마가 같았다. 비교는 약 8초 걸렸다. 값은 [results.json](results.json)에 있다.

[11/4 기록](../t13-db-fingerprint-2026-11-04/README.md)은 로컬 컨테이너 값이었고 "실제 복제 환경에서 이 비교기로 끝까지 돈 적은 없다"고 적었다. 이번이 그 첫 실제 실행이다. 컷오버는 하지 않았다.

## 결과

| 표 | 행 (출발지 · 목적지) | 데이터 | 스키마 |
| --- | ---: | --- | --- |
| `public.attachments` | 1 · 1 | MATCH | MATCH |
| `public.messages` | 2 · 2 | MATCH | MATCH |

- 양쪽 모두 PostgreSQL 18.4, 데이터베이스 정렬 규칙 `C`(libc)다. 메이저 차이나 정렬 버전 차이로 `UNKNOWN`이 될 조건은 없었다.
- 시퀀스는 읽기만 했다. `public.messages_id_seq`의 다음 값은 출발지 13, 목적지 8이고 두 표의 최대 ID는 4로 같다. 실행기가 컷오버 때 목적지를 올릴 값(`next_safe_value`)은 13이다. 보정(쓰기)은 하지 않았다.

## 어떻게 돌렸나

- 실행 코드: develop `04a61261`의 `bravo_cutover.db_fingerprint`(현재 develop과 같은 파일).
- 연결만 바꿨다. 실행기는 psycopg로 DB에 붙지만, 이번에는 각 DB 파드 안의 `psql`로 같은 질의를 보냈다. 출발지는 출발지 EKS의 `source-db-1`, 목적지는 목적지 RKE2의 `target-db-1`에서 로컬 소켓으로 붙었다.
- 모든 질의는 모듈의 스냅샷 설정(`REPEATABLE READ, READ ONLY`, `TimeZone=UTC` 등) 안에서 돌고 `ROLLBACK`으로 끝났다. DB에 쓰지 않았다.
- **실행기와 다른 점:** 실행기는 표 하나의 카탈로그 조회와 지문 조회를 한 트랜잭션에서 하지만, 이번에는 질의마다 같은 스냅샷 설정을 붙인 별도 트랜잭션으로 보냈다. 두 앱의 쓰기가 막혀 있고 복제 지연이 0인 상태에서 돌렸기 때문에 결과가 달라질 이유는 없지만, 같은 스냅샷이라는 보장은 아니다. 접속 계정도 실행기 계정이 아니라 각 DB의 로컬 관리자다.
- 이 연결 방식은 일회성이라 저장소에 넣지 않았다.

## 공개하지 않은 값

행 · PK · 내용 지문 값과 스키마 지문 값은 넣지 않고, 양쪽이 같은지만 적었다. 원본은 비공개 기록에 있다.

## 재지 않은 것

- 실행기 자체의 접속 계정 · 연결 경로로 돌린 비교. 컷오버 때 실행기가 처음 돈다.
- 쓰기를 멈춘 직후 데이터가 들어오고 있는 상태의 비교 시간.
