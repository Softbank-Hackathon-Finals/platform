# T19 계획별 서명 저장·재조회 자격 시험

현재 T19 서명 형식을 기존 계획 원장에 연결한 선택적 어댑터를 검증했다.
개인 키를 발급하거나 서명하는 서버를 만들지 않았다. 출처: [source manifest](source-manifest.json),
[집계 결과](results.json), [사용·인수 경계](../../../services/control-gate/docs/signature-records.md).

## 검사와 결과

- 새 108개 / 전체 게이트 661개 통과. 원장 시험은 실제 격리 SQLite·Unix socket PostgreSQL 17을 사용하고,
  관측·신원·키는 합성 fixture다.
- 정상 저장/재시도/새 인스턴스 재조회, 동시 상충 서명·다른 생산자·용도·문맥 거부,
  등록/키 유효 시작 전 수집 거부, 외부 원문의 정확한 타입·범위·관측 시각 검사.
- 저장 후 기한/권한 상실 롤백, 종료한 계획 트랜잭션 재사용 거부, 서명 예산을
  넘겨도 기존 근거를 지우지 않음. 현재 폐기는 다음 검증에서도 반영됨.
- 실제 자식 프로세스를 커밋 전 또는 커밋 후 응답 전에 종료한 4개 DB/시점 조합 통과.
  전자는 원문 미저장, 후자는 같은 요청 재시도에도 정확히 한 건이며 계획은 불변.
  자식의 시험 DB 접속 정보는 private fixture 파일로만 전달하고 argv·출력에 넣지 않음.
- 신뢰 시작 제한·저장 후 만료 검사·저장 생산자 결속을 각각 제거한 사본에서
  지정 회귀가 4/2/2건 실패. 실제 변이 모듈 경로·해시를 확인했다(3/3 검출).
- Linux arm64/Python 3.12.14 wheel을 비root·network none·read-only root에서
  SQLite 등록/공개/새 인스턴스 조회/폐기 거부와 계획 불변으로 검증했다.
- 실제 T21 HTTP와 연결한 최신 모듈로 비공개 소비자 자격 시험 32개 통과. 양쪽 저장소와 초기/재대조
  단계에서 현재 키 폐기·기한·권한 회수 후 이전 보고서를 제공하지 않음을 확인했다.
  3초/30초의 실제 서명 기한을 HTTP read_valid_until에 전달하는 것도 확인했다.
  이는 합성 보고서이며 운영 T10 저장·T19 PASS·배포된 콘솔 검증이 아니다.

별도 거부 시험은 보존된 실제 양쪽 T14 TLS 원문 바이트를 격리 저장소에 그대로 넣고
새 합성 키로 소급 인증하려는 입력 4개를 거부했다. 원문·시각·hash는 불변이며 서명은
메모리의 공격 입력일 뿐 저장·출력하지 않았다. 운영 키 등록이나 과거 실행의 운영 승격이 아니다.

## 실패 시도와 남은 범위

확대 시험의 최초 2건은 read 권한 거부를 다른 고정 오류 코드로 기대해 실패했다.
실제 AUTHORITY_FORBIDDEN 계약으로 기대값을 수정했고 제품 거부 조건은 유지했다.
프로세스 종료 하네스의 최초 4건은 Path.open의 잘못된 opener 인자로 실패해 builtin open으로
바꿨다. 과거 원문 거부 스크립트의 초기 read_run 호출도 현재 연결/계획 인자를 쓰도록
고쳤다. 해당 초기 실패 원본은 비공개로 보존했으며 통과 결과에 포함하지 않았다.

최신 선행 브랜치에 반영한 후 최초 전체 실행은 PostgreSQL 실행 도구의 PATH 누락으로
512개 통과·149개 설정 오류였다. 기존 고정 도구 경로를 지정해 전체 661개를 다시 통과했다.
제품·시험 조건을 변경하거나 PostgreSQL 시험을 생략하지 않았다.

운영 생산자 인증·키 자격/보관/회전·감사·새 T14 수집·T13/예외/네트워크 정본 공급자는
호스트 인수 항목이다. 실제 운영 DB 쓰기 0회, 업무 쓰기/승인/트래픽 변경 0회다.
신뢰 호스트·DB 관리자 침해나 모든 금융 보안 요구를 이 어댑터만으로 해결했다고 주장하지 않는다.
