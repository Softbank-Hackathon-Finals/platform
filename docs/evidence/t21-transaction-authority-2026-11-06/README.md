# T21 동일 계획 트랜잭션의 보고서 출처 조회

운영 발급자 키·서명 원문을 정본 DB에서 읽는 호스트가 T10 보고서 조회와 다른
트랜잭션을 열지 않도록, 기존 `T10ControlReports`에 선택형 `authority_factory(view)`를
추가했다. 기존 출처 콜백 방식과 정확히 한 가지를 사용하며 기본 신뢰는 없다.

## 확인한 결과

- 새 32개를 포함한 콘솔 Python 전체 244개 통과, Ruff·gitleaks·diff 통과.
- 실제 로컬 SQLite/PostgreSQL과 Ed25519 검증을 사용했다.
- 키·서명 원문을 읽는 두 조회가 정확히 같은 T10 계획 연결을 사용하는지 확인했다.
- 다음 요청에는 새 view/연결로 현재 권한·issuer를 다시 읽으며 캐시하지 않는다.
- 현재 키 폐기·만료·서명 누락·조회 중 권한 회수·잘못된 공급자 반환을 거부했다.
- 공급자가 비밀을 포함한 오류를 던져도 고정 공개 오류만 반환했다.
- 최초·반영 후 단계의 기존 조회 방식과 계획 snapshot을 유지했다.
- 기존 Starlette/httpx deprecation 경고 1건은 유지했다. 검사 예외·의존성·CI 변경은 없다.

신원·발급자·키·통제 데이터는 합성 시험 자료다. 실제 팀 환경에 키를 등록하거나
이미지·권한·DB를 변경하지 않았다. T10 실제 원문 저장·T19 운영 평가·서명 발급과
이 호스트 공급자 배포를 같은 계획으로 확인해야 운영 인수가 된다.

소스 결속은 [source-manifest.json](source-manifest.json), 호스트 연결은
[콘솔 README](../../../services/console/README.md#기존-t10-저장소에서-읽기)를 따른다.
