# T2 arm64 · x86_64 실제 재설치 검증 — 2026-11-03

Mac의 로컬 QEMU 도구로 두 아키텍처의 빈 Ubuntu VM을 순서대로 만들었다. 같은 RKE2 user-data로 설치하고 CIS, 재부팅 후 노드와 시스템 Pod 준비 상태, 접속 포트 보존, 정상 종료·삭제를 확인했다. 실행 코드는 [`dd03235`](https://github.com/Softbank-Hackathon-Finals/platform/commit/dd03235cfa20dcbdb04974f75591465df03b4df9)이며 이후 증빙 문서 추가와 구분한다. [구조화 결과와 소스 SHA-256](results.json)에 실행 입력을 고정했다.

## 실제 환경과 결과

- 호스트: Mac mini, Apple M5 Pro, 18 CPU cores, 64 GiB RAM, macOS 27.0.
- QEMU 11.1.3. arm64는 HVF, x86_64는 TCG로 실행했다. Intel Mac이나 별도 물리 x86 호스트에서 실행한 결과는 아니다.
- 각 VM: 4 vCPU, RAM 8 GiB, 가상 디스크 40 GiB, Ubuntu 24.04 `release-20261017`. 아키텍처별 이미지 SHA-256을 검증했다.
- RKE2 `v1.35.9+rke2r1`, kube-bench `0.16.0`, benchmark `rke2-cis-1.9`.
- 기존 T8와 다른 호스트 작업을 보존하고 추가 VM은 한 번에 하나만 실행했다. 두 최종 실행은 이미지를 미리 내려받았다. 아래 시간은 그 환경의 측정값이며 아키텍처 성능 비교가 아니다.

| 확인 | arm64 / HVF | x86_64 / TCG |
|---|---:|---:|
| 게스트 `uname -m` | `aarch64` | `x86_64` |
| `up` 전체 / cloud-init 대기 | 183.852초 / 182초 | 914.047초 / 913초 |
| 설치 후 `verify-node.sh` | 10 PASS / 0 FAIL | 10 PASS / 0 FAIL |
| kube-bench | 82 PASS / 0 FAIL / 41 WARN / 7 INFO | 82 PASS / 0 FAIL / 41 WARN / 7 INFO |
| 재부팅 후 노드 10개 항목 검증 | 110.835초 | 211.115초 |
| 재부팅 후 시스템 Pod 준비 확인 | 121.536초 | 326.046초 |
| 최종 시스템 Pod | 11 Running/Ready, 6 Succeeded | 11 Running/Ready, 6 Succeeded |
| `down` 종료 코드 | 0 | 0 |
| VM 프로세스·전체 임시 상태 삭제 | 확인 | 확인 |

두 실행 모두 부팅 ID가 바뀌었고 재부팅 후 `verify-node.sh`도 10 PASS였다. 시스템 Pod는 10초 간격의 연속 두 조회에서 실행 중인 모든 컨테이너가 준비됐거나 Job이 완료됐는지 확인했다. 이 대기의 상한은 600초다. VM의 저장된 SSH 포트가 이후 다른 환경변수 값보다 우선하는 것과 QEMU 수명에 묶인 호스트 절전 방지 assertion도 실제로 확인했다.

41 WARN은 수동 점검 33개와 감사 결과의 WARN 8개다. 감사 WARN의 항목 번호는 `results.json`에 남겼다. WARN을 PASS로 합산하지 않으며 `rke2-cis-1.9` 결과를 운영 환경 전체의 CIS 준수로 확대하지 않는다. [원래 T2 기록](../t2-onprem-rke2-2026-11-03/README.md)의 "WARN 41개는 모두 Manual"이라는 설명은 이번 원본 JSON의 분류와 맞지 않는다. 원기록은 보존하고 이 추가 증빙에서 분류를 정정한다.

## 첫 시도와 재검증

첫 x86_64 시도는 설치, 노드 10개 항목, CIS 0 FAIL, 부팅 ID 변경과 재부팅 후 노드 10개 항목을 확인했다. 하지만 그 직후 시스템 Pod를 한 번만 조회했을 때 일부 CNI·컨트롤러가 아직 준비되지 않아 전체 시험은 FAIL로 기록했다. 이 첫 결과를 성공으로 바꾸지 않았다. `down`은 0으로 끝났고 임시 자원은 삭제됐다.

제품 소스는 그대로 두고 시험의 준비 상태 확인을 위의 제한된 연속 조회로 바꿨다. 이후 새 x86_64 VM의 설치부터 삭제까지 다시 실행한 결과가 위 표다. 첫 시도의 판정·시간·원본 해시도 `results.json`에 별도로 남겼다. 노드 Ready와 모든 시스템 Pod의 준비 완료는 같은 시점이 아닐 수 있다.

앞선 arm64 실행에서는 macOS가 종료 중인 QEMU를 `?E` 및 잘린 실행 파일명으로 잠깐 표시해, 기존 삭제 방어가 상태를 보존하며 실패했다. 8 GiB 실제 QEMU로 수정 전후를 재현했다. 수정 후에도 E/Z를 종료 완료로 인정하지 않고 같은 시작 시각의 프로세스가 실제로 사라질 때까지 기다린다. 다른 살아 있는 프로세스, 종료 시간 초과와 신원 불일치는 계속 보존한다. 위 표의 두 최종 실행은 이 수정이 포함된 같은 코드다.

## 자원 경쟁과 삭제 안전성

실행 중인 arm64 VM의 SSH 포트를 새 x86_64 VM에 지정했을 때 `up`은 VM 생성 전에 종료 코드 1로 거부했다. 기존 두 VM의 프로세스 신원은 유지됐고 충돌 시험용 상태도 제거했다. 아키텍처별 기본 경로·포트 외에도 여러 세션은 상태 경로와 두 포트를 모두 분리해야 한다.

정상 `down`은 UUID·QMP·디스크·프로세스 확인 후 QMP quit을 보내고 PID 소멸을 기다렸다. 각 실행은 열린 파일 핸들이 없음을 확인한 뒤 자신이 만든 이미지 캐시·키를 포함한 임시 루트도 제거했다. 기존 T8는 PID·시작 시각·VM 및 디스크 inode를 전후 대조했다. 이는 같은 자원의 보존 확인이며, 다른 소유 세션의 정상 데이터 쓰기가 없었다는 뜻은 아니다. 공유 QEMU와 의존성은 T8가 사용하므로 유지했다.

## 로컬 시험과 CI

실제 QEMU 선택 시험을 활성화한 저장소 `scripts/tests` 177개가 모두 통과했고 skip은 0이다. 이 중 작은 QEMU의 수명·안전성 시험과 위 Ubuntu/RKE2 전체 설치는 별도 실행이다. Ruff, Bash 문법, 공개 증빙 및 diff 검사를 통과했다. 실행 소스 커밋의 [필수 CI](https://github.com/Softbank-Hackathon-Finals/platform/actions/runs/41630281865)도 통과했다. 이후 문서 커밋의 CI는 PR에서 별도로 확인한다.

재현 순서는 [사용법](../../../infra/envs/onprem/README.md)에 따라 아키텍처·전용 상태·포트 지정 → `up` → `verify-node.sh` → `run-kube-bench.sh` → 게스트 재부팅 → 새 부팅 ID 및 노드·Pod 준비 확인 → `down`이다. 재부팅 직후 한 번의 조회만으로 복구를 판정하지 않는다.

## 범위와 원본

VM CPU 지원은 앱 OCI 이미지의 CPU 지원과 다르다. 이번 실행은 기존 amd64 앱 이미지의 arm64 지원이나 T8/T30 애플리케이션 통합을 검증하지 않았다. 최종 행사 데모 머신도 아직 지정되지 않았으므로 이슈 #6의 세 번째 항목은 완료 처리하지 않는다.

공개 JSON은 비공개 로그에서 필요한 판정·측정값을 선택한 요약이며 원본 전체가 아니다. 소스 해시와 원본 로그 해시를 보존했지만, 공개본만으로 비공개 자원의 실체를 독립 확인할 수는 없다. 프로세스 ID, VM UUID, 실제 상태 경로, 키와 관리자 설정은 공개하지 않았다. 이전 증빙은 덮어쓰지 않았다.
