# T22: 실제 앱의 읽기 전용 브라우저 재접속

실제 출발지 EKS·온프렘 앱을 Chromium/WebKit의 데스크톱·모바일 화면에서 확인했다.
총 8개 조합에서 시험 브라우저 자신의 WebSocket만 코드 4000으로 닫았다.
앱의 원래 재접속 코드가 마지막으로 표시한 ID 이후를 요청하고, 기존 메시지를
유지하며 중복 없이 다시 연결함을 확인했다. 실행 환경 표시·가로 넘침도 검사했다.

| 범위 | 결과 |
| --- | --- |
| 두 브라우저 × 두 화면 × 두 실제 앱 | 8/8 통과 |
| 실제 정적 JS 바이트 | demo-chat의 고정 소스와 일치 |
| 전후 배포 | 양쪽 Deployment UID·generation·spec 동일, Ready 1 유지 |
| 시험의 HTTP 쓰기·앱 WebSocket 송신·서버 관리 API | 0 |
| 메시지 본문 증빙 저장 | 없음 |
| 임시 로컬 포워드 | 자신의 두 포워드만 종료 |

## 검사 방법과 개인정보

공식 개인 접근과 로컬 전용 포워드로 실제 앱을 열었다. WebSocket 생성자를 감싸
자기 연결과 URL을 관측했지만 서버 응답·메시지·접속 URL은 바꾸지 않았다.
마지막 ID 이후 요청은 실제 앱의 기존 cursor 코드가 생성했다. 빈 이력을 만들기
위해 `after` 값을 강제로 넣지 않았다.

HTTP 쓰기와 앱 WebSocket 송신을 차단하고 첨부파일도 읽지 않았다. 기존 메시지는
브라우저 메모리에 표시했지만 본문·작성자·ID 목록을 증빙에 저장하지 않았다.
공개 요약에는 개수와 판정만 남겼고 비공개 화면 캡처도 본문·작성자 영역을 숨겼다.
운영 토큰·관리자 토큰을 브라우저에 전달하지 않았다.

## 해석의 한계

이 시험은 **클라이언트 자신의 연결 종료와 재접속**이다. 서버가 1012로 연결을
종료하거나 장애·DB 컷오버·Edge 전환을 실행한 것이 아니다. 두 앱이 같은 출발지
DB를 사용하는 컷오버 전 구성이므로 독립된 목적지 DB 운영·출발지 의존 제거의
증거도 아니다. 업무 쓰기·휴대폰 실기기·공개 고정 URL·쓰기 차단 해제는 시험하지 않았다.
전체 통합 시연과 T22 완료 체크는 별도 인수 대상으로 유지한다.

최초 소스 대조는 URL `/chat.js`를 저장소 `app/chat.js`에 잘못 대응해 실패했다.
실제 정적 파일 위치인 `app/static/chat.js`로 대조해 같은 수집 바이트의 일치를
확인했다. 브라우저 검사를 반복해 실패를 덮거나 소스를 바꾼 것은 아니다.

[summary.json](summary.json)은 실제 시각과 검사 결과이며,
[source-manifest.json](source-manifest.json)은 **demo-chat 저장소**의 실행 자산에
결속한다. 수집 스크립트·배포 메타데이터·가린 화면은 비공개로 보존했다.
