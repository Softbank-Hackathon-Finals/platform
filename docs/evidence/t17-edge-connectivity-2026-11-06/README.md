## 첫 읽기 부하에서 확인한 문제

04:17 KST에 목적지 0%를 유지한 채 EC2에서 읽기 200 req/s를 60초 실행했다.
업무 쓰기는 0건이었다. 요청 12,000건 중 200 응답 4,084건, 502 응답 366건,
시간 초과 7,550건이었다. 오류율은 65.9667%, 전체 p95는 17,280.685ms였다.
부하 생성기 지연 경고도 있어 이 실행의 창은 판정 근거로 사용할 수 없다.
DB 대조를 수행하지 않아 리포트의 최종 상태는 `UNKNOWN / NOT_RECONCILED`다.
이 실패 원본을 보존했다. 이후 같은 경로의 읽기 진단은 다음과 같았다.

| 실행 | 요청 | HTTP 오류 | 전체 p95 | 생성기 지연 경고 |
| --- | ---: | ---: | ---: | --- |
| 50 req/s · 30초 | 1,500 | 0 | 31.711ms | 없음 |
| 200 req/s · 15초 | 3,000 | 0 | 97.44ms | 없음 |
| 200 req/s · 60초 재측정 | 12,000 | 0 | 57.39ms | 없음 |

재측정 동안 인스턴스·Pod 용량을 변경하지 않았다. 처음 실패한 원인은 아직
확정하지 못했으므로 후속 성공을 원인 해결로 표시하지 않는다. 모든 실행은
목적지 0%·업무 쓰기 0·T10 창 전송 0이며, DB 전수 대조를 하지 않아 최종
리포트는 `UNKNOWN / NOT_RECONCILED`다. 네 실행의 원본 파일 24개를 내려받아
원격 SHA-256과 대조했다.

사용자 지시에 따라 추가 부하 진단을 중단하고 기능 해피패스 1회를 우선한다.
진단 종료 후 부하 프로세스 0, 증빙 서버 정지, 증빙 SSM 연결 종료를 확인했고
전용 EC2 정지를 접수했다. 공유 VM 이전 담당에게 반환하기 전 provider GET에서
활성 LB·출발지 100%·목적지 0%·출발지 fallback을 다시 확인했다. 개인 EKS
접속 연결도 종료하고 로컬 수신 포트가 닫힌 것을 확인했다.

복제에서는 기존 5초 receiver timeout에 따른 연결 오류를 확인했다. 정방향
`disable_on_error`를 다시 true로 적용하고 실제 catalog에서 ON·worker 1·오류 5를
확인했다. timeout, 역방향과 DB writer는 바꾸지 않았다. 누적 오류가 존재하므로
ON만으로 지속적인 복구 완료를 주장하지 않는다.

목적지는 ARM Mac에서 x86_64/TCG로 실행하는 개발 VM이다. 이 환경의 기능·복구
결과와 최종 네이티브 성능 근거를 구분한다. 제안 프로필을 measured로 바꾸지 않았다.

실제 T10 계획은 이 조회에서 `COLLECT` v1이었다. 새 프로필에 결속한 계획,
현재 승인·실행 권한, 창 수신·canonical 판정과 Edge 명령 연결이 남았다.
합성 계획이나 SQL 상태 변경으로 SHIFT를 만들지 않았으며 T17 완료 체크도 바꾸지 않았다.

provider 응답, 클러스터 신원, 설치·조회·SSM 영수증은 비공개 운영 원장에 보존했다.
이 공개 기록에는 계정, 클러스터·Tunnel·pool·LB 식별자, 토큰, 접속 자격을 넣지 않았다.
