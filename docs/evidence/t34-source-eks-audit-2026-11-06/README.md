# T34 실제 출발지 EKS 권한 변경 감사 경로 부분 인수

2026-11-06 03:40 KST에 등록된 출발지 EKS에서 시험용 RoleBinding의 생성·삭제를
실행하고 CloudWatch 감사 로그에서 검색했다. 실제 앱과 분리된 관측 namespace의
시험이며 앱 namespace 전체, 목적지 또는 T19 운영 게이트의 완료 근거는 아니다.

## 실행과 결과

- 실제 앱 Deployment UID로 접속 대상이 기존 등록 출발지와 같은지 확인했다.
- 기존 EKS 감사 설정과 등록 로그 그룹·정확한 감사 스트림 목록을 읽었다.
- 자격을 발급하지 않은 비존재 ServiceAccount를 대상으로, 고유한 비존재 ConfigMap
  하나에 대한 `get`만 허용하는 Role과 RoleBinding을 생성했다. 기존 권한을 바꾸거나
  해당 ServiceAccount·토큰을 만들지 않았다.
- 생성 응답을 보존하고, 본인이 생성한 객체의 UID·resourceVersion 조건을 걸어
  삭제했다. 실제 조회로 두 객체가 사라진 것을 확인했다.
- API 서버의 실제 사용자·namespace·대상·verb·응답·시각을 검색 결과와 대조했다.
  생성·삭제가 처음 함께 보인 시점은 시험 시작 후 **24.61초**였다. 이는 주기 조회로
  확인한 최초 가시성 시간이며 CloudWatch 자체의 정확한 처리 지연 측정은 아니다.
- 03:45 KST에 보강한 검색기로 같은 실제 로그를 다시 조회했다. 조회 11건 중 실제
  RoleBinding 생성·삭제 **2건**이 일치했다. 사전 검사(dry-run) 기록은 제외했다.
- 임시 SSM 세션과 로컬 포트는 종료했다. 앱·DB·기존 네트워크·감사 설정은 변경하지 않았다.

## 실제 로그에서 발견한 차이와 수정

서버 dry-run도 성공 감사 기록을 남겨 기존 검색기의 일치 이벤트에 포함됐다.
이번 실행에는 실제 생성·삭제 응답과 readback이 별도로 있었으므로 실제 변경이
없었던 시험을 성공으로 바꾼 사례는 아니다. 원본 URI의 `dryRun`과 요청 본문의
dry-run 표식을 제외하고, URI가 있으면 대상 경로도 대조하도록 수정했다.

전체 control-runner 시험 **971개 통과, 조건부 5개 제외, subtest 58개 통과** 및
Ruff 통과. 초기 실행의 개인정보 필터 경로 fixture 실패를 확인해 기존 계약을 유지했다.
제한 환경에서 loopback 소켓이 거부된 별도 실행은 성공으로 기록하지 않았으며,
소켓을 허용한 최종 실행 결과가 위 수치다.

기존 OTLP 개인정보 필터는 URI·본문을 제거한다. 해당 경로는 신뢰된 실행기의
실제 변경 성공 영수증에 계속 의존하며, 이번 원본 로그 배제 검증과 같다고 주장하지 않는다.

## 미완료 범위

- 실제 앱 namespace의 동일 시험, 목적지 권한 변경·DB 접속·DDL 감사 검색
- 운영 수집기의 읽기 전용 검색 권한 및 보관·접근 거부 검증
- 운영 T10 계획과 원문 저장, 양쪽 결과의 T19 게이트 인수

따라서 T34 전체 완료 체크와 T14 전체 PASS는 변경하지 않는다. 요약의 `present`는
이 시험의 감사 이벤트가 검색됐다는 뜻이며 컷오버 승인 또는 보안 동등성 판정이 아니다.

원본 로그·사용자·자원명·영수증은 비공개로 보존한다. 공개본에는 측정값·정리 여부와
해시만 남긴다. 해시는 원문을 식별하며 공개본만으로 실제 자원이나 로그 진위를 증명하지 않는다.
