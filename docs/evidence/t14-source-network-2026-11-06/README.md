# T14 출발지 namespace 간 DB 접근 시험 — 2026-11-06

**전체 NET-01.3 결과는 UNKNOWN(`POSITIVE_CONTROL_FAILED`)이다.** 실제 출발지 DB의 5432 포트는 다른 namespace의 시험 Pod에서 연결됐다. 하지만 계약에 고정된 풀러 6432 포트의 정상 대조군이 실패했다. 출발지 PgBouncer의 실제 listener·Service·EndpointSlice는 모두 **5432**다. 이 포트 차이를 네트워크 차단 성공으로 처리하지 않았다.

## 실제 확인한 범위

- 등록된 EKS의 원본 앱 Deployment/Pod/이미지·Service를 전후 대조했다. 앱, DB, 보안 그룹, NetworkPolicy는 변경하지 않았다.
- 앱 namespace의 허용 시험 Pod, 별도 namespace의 접근 시험 Pod·건강 확인용 Pod를 만들었다. 소유 namespace는 restricted PSA, 모든 Pod는 비루트·읽기 전용 root·capability 제거·서비스 계정 토큰 없음·CPU/메모리 한도·600초 기한을 적용했다. 업무 Service에 선택되는 앱 라벨을 붙이지 않았다.
- 원본 namespace의 NetworkPolicy와 SecurityGroupPolicy는 0개였다. 실제 노드 보안 그룹과 정책 원문을 비공개 보존하고 해시를 결속했다. 정책 부재만으로 접근 성공을 추론하지 않았다.
- 5432: 전후 허용 연결·시험 서비스 연결·DNS 대조가 성공했다. 다른 namespace의 TCP 연결도 성공해 해당 포트의 관찰은 `allow`다. SQL·비밀번호·업무 payload는 보내지 않았다. 이 결과는 DB 로그인 성공이나 데이터 유출을 뜻하지 않는다.
- 6432: 허용 시험 Pod부터 3초 안에 연결하지 못했다. 부정 시험은 실행하지 않았고, 전체 항목을 UNKNOWN으로 유지했다. 실제 PgBouncer 설정을 추가 조회해 5432 listener임을 확인했다.
- 소유 Pod 3개와 namespace 1개를 UID/resourceVersion 조건으로 제거하고 부재를 확인했다. 동일 노드에서 실행한 시험이며 모든 노드·외부 경로를 검증한 것은 아니다.

## 시험 도구와 실패 기록

첫 호스트는 원격에 넘기는 고정 SocketTCPRunner 코드의 보조 함수가 누락돼 실패했고, 반복 kubectl 인증/실행 준비도 5초 시도 기한을 넘겼다. 각 실행은 UNKNOWN으로 남기고 소유 자원을 정리했다. 이후 같은 제품 TCP/DNS 검사만 받는 두 세션을 먼저 준비했다. 단기 토큰은 명령 인자·파일에 남기지 않고 메모리 파이프로 전달했다. TCP 3초, 시도 5초, 전체 60초 조건은 완화하지 않았다.

최종 원문·시각·지문·정리 결과는 [result.json](result.json)에 있다. 비공개 호스트·원문은 개발 기록에 보존한다. 이 호스트는 운영 무인 실행기로 인수한 것이 아니며 개인 SSO로 수행한 시험이다. 수집기의 원문을 다른 계획·시각·목적지로 바꿔 등록하지 않는다.

## 남은 결정

T5가 요구하는 두 실행 경계(DB·풀러)와 실제 등록 listener를 맞춰야 한다. 실제 풀러는 5432인데 6432를 그대로 검사하거나, 한 포트만 성공한 결과를 전체 PASS/FAIL로 축약하지 않는다. 계약의 고정 포트를 실제 서비스 역할·listener 등록으로 바꿀 경우 방법 버전과 소비자의 검증을 함께 갱신해야 한다. T6의 운영 포트·연결을 시험 통과 목적으로 임의 변경하지 않았다.

목적지 결과와 운영 T10 계획 입력은 별도다. T14 완료 체크는 유지한다.
