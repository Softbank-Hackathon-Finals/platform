# [T18] 합동 측정 절차 로컬 리허설 — 2026-11-06

**결론.** [합동 측정 절차](../../operations/t18-joint-measure.md)를 로컬 대역으로 처음부터 끝까지 두 번 돌렸고, 검사는 두 번 모두 17건 중 실패 0건이다. 가중치 4단계(10 → 50 → 100 → 0%)가 창에서 확인됐고 쓰기 대조의 실패 · 유실 · 중복은 0이다. **실제 Edge, Cloudflare, 클러스터, EC2에는 요청을 한 건도 보내지 않았다. 아래 반영 시간과 p95는 실제 값의 근거가 아니다.**

두 번 모두 다른 세션의 Docker 시험과 겹쳤고, 겹친 구간에서 값이 나빠졌다. 고르지 않고 둘 다 남긴다.

- **반영 상한은 상한이다.** 대역은 약 0.1초면 바뀌는데 값은 13초대다. 첫 온전한 창의 끝까지 재기 때문이다. 실제 Edge에서도 창(10초)보다 짧은 차이는 이 값으로 가를 수 없다.
- **겹친 구간에서 나빠졌다.** 다른 세션의 `t8-job-*` 컨테이너가 15:41:41과 15:46:41에 처음 보였고, 약 20~35초 뒤부터 응답이 느려졌다. 2회차는 그 전 110초 동안 창의 p95가 5~12ms였고, 이 구간에 가중치를 네 번 모두 바꿨다. 시점이 일치한다는 뜻이고 **원인을 확인하지는 않았다.** 이 시험은 앱과 생성기가 같은 맥에 있어 실제 측정의 지연을 말해 주지 않는다.
- **리포트가 이것을 드러냈다.** 두 번 모두 `GENERATOR_LAGGING`과 `HTTP_ERRORS`가 떴고, 나빠진 창은 참고 판정이 FAIL이고, 쓰기 대조는 재시도로 복구되어 PASS다. 노트북 부하를 Edge 실측으로 잘못 읽을 경로는 없었다.
- 사전 점검의 왕복 기준값은 1회차 p50 2.555ms · 최대 8.171ms, 2회차 p50 1.72ms · 최대 5.122ms다. 같은 맥 안의 값이라 회선을 재지 않는다.

## 실제 T10 수신부 확인

사전 점검이 빈 문서로 찌르는 방식이 실제 코드에서도 맞는지, `services/platform-events`의 `create_window_app`과 `WindowIntake`에 SQLite 저장소를 붙여 돌렸다(`t10-receiver-check.json`). 일회용 스크립트라 저장소에 넣지 않아 다시 돌릴 수 없다.

| 상황 | 사전 점검 | 창 저장 |
|---|---|---|
| 맞는 토큰, 켜진 계획 연결 | 통과, 종료 코드 0 | 없음 |
| 틀린 토큰 | "토큰을 거부했다", 종료 코드 2 | 없음 |
| 수신부 길이 기준(32자)보다 짧은 토큰 | 같음 | 없음 |
| 계획 연결을 끔 | "계획 연결이 꺼졌거나 만료됐다", 종료 코드 2 | 없음 |
| 다시 켠 뒤 `measure` | 통과, 창 2개 전달 실패 0 | 있음, 계획 일치 |
| 토큰은 맞고 `--plan-id`만 다름 | **통과**, 창 2개 모두 전달 실패 `WINDOW_DELIVERY_FAILED` | |

마지막 줄이 사전 점검의 한계다. 계획 일치는 문서 검사 뒤에 보므로 빈 문서로는 알 수 없고, 시험 실행에서 드러난다. 절차에 그렇게 적었다.
