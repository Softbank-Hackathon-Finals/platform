# [T18] 부하 생성기 · 대조 리포트 · 창 요약 로컬 실측 — 2026-11-04

**결론.** 로컬에서 쓰기 50 · 읽기 150 req/s를 넣고 DB와 전수 대조해 실패 · 유실 · 중복 0건을 확인했다. 일부러 넣은 결함은 모두 잡혔다(검사 90건, 실패 0건). **실제 Edge · 실제 클러스터 측정이 아니다.** 그리고 앱과 DB 사이에 모의 왕복 지연을 넣으면 쓰기 잠금이 초당 50건을 못 견디는 구간이 나왔다(5절). 실제 지연이 정해지면 다시 봐야 한다.

측정 뒤 창 전송에 인증을 더했다. **수치는 다시 재지 않았다.** 바뀐 범위와 다시 돌린 검사는 10절에 있다.

그 뒤 demo-chat `c1c74ab`가 `X-Bravo-Env`를 보내게 되어 같은 조건으로 다시 쟀다. **직접 실행의 환경 미확인이 12,000건에서 0건이 됐다**(11절). 이것도 로컬 측정이다. 2~10절의 값은 이전 demo-chat 기준으로 그대로 둔다.

## 5. 발견: 앱과 DB 사이 왕복 지연과 쓰기 잠금

**지연은 모의값이다.** 목적지 앱과 DB 사이에 TCP 중계기(`testing/tcp_fault.py`)로 왕복 지연을 넣고, Edge 대역으로 비중을 나눴다. 트래픽 전환 중 목적지 앱이 출발지 DB에 쓰는 경로(설계 8.6)의 대역이다. 클라우드 사이 실제 왕복 지연은 아직 재지 않았다(T8). 각 칸은 30초 실행 한 번이다. 0ms는 중계기가 병목이 아닌지 보는 대조군이다.

- **왕복 20ms · 목적지 50%에서 쓰기가 밀렸다.** 이 칸의 판정 입력을 `judge`로 읽은 결과가 표의 마지막 열이다. 판정이 FAIL이면 SHIFT는 가중치를 0으로 되돌린다.
- **원인은 코드에서 읽힌다(이 시험으로 증명한 것은 아니다).** `demo-chat` `app/store.py`는 메시지 쓰기마다 advisory lock을 잡은 채 INSERT · SELECT · COMMIT을 차례로 보낸다. 잠금을 쥔 동안 DB까지 왕복이 여러 번 들어, 왕복 지연이 곧 잠금 점유 시간이 된다. `statement_timeout` 200ms를 넘은 쓰기는 503이 된다.
- **유실 · 중복은 어느 칸에서도 없었다.** 재시도가 받아 냈다. 다만 이전 실행(`earlier-run/rtt40-w50.json`)의 왕복 40ms · 50%에서는 재시도 한도 안에 확인을 못 받은 쓰기가 1건 나왔다.
- **포화 근처에서는 값이 크게 흔들린다.** 왕복 40ms · 10%의 쓰기 p95는 실행마다 크게 달랐다. 칸 하나를 정확한 값으로 읽지 말고 경향으로 읽는다. 경계가 되는 왕복 지연은 재지 않았다.
- 이 저장소에서 고칠 일이 아니라 고치지 않았다. demo-chat의 잠금 방식과 T8 실측, T17 단계 기준의 문제다.
