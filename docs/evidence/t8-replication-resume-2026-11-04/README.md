# T8 정방향 구독 재개 절차와 설정 판단

**구독이 다시 꺼지면 `resume_replication.py`로 유실 없이 되살릴 수 있고, 재발을 줄이려면 `disable_on_error`를 끄는 쪽을 추천한다.** `wal_receiver_timeout` 5초는 그대로 둔다. 전부 로컬 컨테이너 결과이고 네트워크 조건은 가정값이다. 실제 환경에서는 아무것도 실행하거나 바꾸지 않았다.

첫 실제 재개(11/4 16:26 KST)의 결과는 [#201](https://github.com/Softbank-Hackathon-Finals/platform/pull/201)이 정본이다. 여기서 다시 재지 않았다. 그쪽에서 읽어 온 값은 이것뿐이다: 실제 환경의 송신 · 수신 타임아웃은 각각 5,000ms이고 `disable_on_error`는 켜져 있다. 아래 로컬 기본 설정과 같은 값이다. 명령의 출력도 #201과 같은 이름과 단위를 쓴다.

원측정값은 [results.json](results.json), 사용법은 [운영 절차](../../../infra/envs/target-workloads/README.md#정방향-구독-재개-재발-대비)에 있다.

## 판단: 무엇을 어떻게 둘까

| 설정 | 추천 | 이유 |
| --- | --- | --- |
| `disable_on_error` | **끈다** (양방향) | 측정한 연결 장애에서 전부 사람 없이 회복했다. 이번 사고처럼 약 16시간 37분 멈춘 채 있지 않게 된다 |
| `wal_receiver_timeout` | **5초 유지** | 이것만 올려도 3회 모두 꺼졌다. 송신 쪽까지 함께 올려도 40초 끊김에서는 꺼지고, 회복은 오히려 느려졌다 |
| `wal_sender_timeout` | **5초 유지** | 같은 이유다 |

**5초 타임아웃이 재발 원인인가?** 방아쇠는 맞지만 값을 올려서 막을 수 없다. 끊김을 알아채는 것이 타임아웃이고, 구독을 멈춰 두는 것은 `disable_on_error`다. 같은 5초에서 `disable_on_error`만 끄면 같은 시간 초과 오류가 나도 스스로 회복했다.

11/3 사고의 신호는 로컬 재현과 일치한다. SQLSTATE 08006 뒤 구독이 곧바로 꺼졌고(실제 약 18ms, 로컬 0~18ms), 적용 오류 1건 · 동기화 오류 0건, 슬롯은 `reserved`였다. **그 시각에 연결이 왜, 얼마나 끊겼는지는 모른다.**

### 설정별 결과

`netem`으로 양방향 패킷을 버렸고, 100Mbps · RTT 30ms, 쓰기 50 req/s에서 조합마다 3회 쟀다. 괄호는 연결 복구 뒤 행이 다시 흐르기까지 걸린 최대 시간이다. 표의 모든 칸은 3회가 같은 결과였다.

| 수신 / 송신 타임아웃 | `disable_on_error` | 8초 끊김 | 20초 끊김 | 40초 끊김 | 손실 30%, 30초 |
| --- | --- | --- | --- | --- | --- |
| **5초 / 5초 (실제 값)** | 켬 | 꺼짐 | 꺼짐 | 안 잼 | 꺼짐 |
| 30초 / 5초 | 켬 | 꺼짐 | 꺼짐 | 안 잼 | 안 잼 |
| 60초 / 5초 | 켬 | 꺼짐 | 꺼짐 | 안 잼 | 안 잼 |
| 5초 / 30초 | 켬 | 꺼짐 | 꺼짐 | 안 잼 | 안 잼 |
| 30초 / 30초 | 켬 | 회복 (8.1초) | 꺼짐 | 꺼짐 | 안 잼 |
| 60초 / 60초 | 켬 | 회복 (8.4초) | 회복 (12.9초) | 꺼짐 | 회복 (16.9초) |
| **5초 / 5초 (추천)** | **끔** | **회복 (0.9초)** | **회복 (5.6초)** | **회복 (2.1초)** | **회복 (2.2초)** |
| 60초 / 60초 | 끔 | 회복 (8.8초) | 회복 (12.6초) | 안 잼 | 안 잼 |

이 표에서 읽을 것은 셋이다.

- **현재 설정은 4초 끊김부터 꺼진다.** 2초와 3초는 3회 모두 회복했고, 4 · 5 · 6초는 3회 모두 꺼졌다. 5초 미만인 4초에서도 꺼지는 것은, 연결이 돌아와도 TCP 재전송 간격이 벌어져 그 안에 패킷이 오지 않기 때문으로 본다. 패킷을 직접 캡처하지 않은 추정이다. 완전히 끊기지 않고 패킷의 30%만 잃어도 꺼졌다.
- **수신 타임아웃만 올리면 소용없다.** 송신 쪽이 5초에 연결을 끊으므로, 연결이 돌아오는 순간 수신 쪽이 끊긴 연결을 보고(08006) 꺼진다. 로그에 `terminating walsender`와 `could not receive data from WAL stream`이 차례로 남았다.
- **둘 다 올려도 설정값까지 견디지 못한다.** 30초는 20초 끊김에서, 60초는 40초 끊김에서 꺼졌다. 위와 같은 TCP 재전송 탓으로 본다.

### `disable_on_error`를 끄면 잃는 것

충돌이 나도 구독이 멈추지 않고 재시도한다. 일부러 충돌을 만들어 쟀다.

| | 켬 | 끔 |
| --- | --- | --- |
| 충돌 뒤 구독 | 꺼짐 | 켜진 채 16초 동안 오류 4건(약 4초마다) |
| 재개 명령 | 실패 (`failed_check`) | 실패 (`failed_check`) |
| 충돌 행을 지운 뒤 | 다시 켜야 한다 | 스스로 회복 |
| 슬롯이 WAL을 붙드는 것 | 같다 | 같다 |

단일 쓰기 설계에서 충돌은 그 자체가 사고이므로 찾아야 한다. 꺼 두면 "구독이 꺼졌다"는 신호가 사라지므로 **적용 오류 수와 `gap_bytes`에 경보가 함께 필요하다.** 이번 사고는 다음 날 14:35에야 확인됐다. 경보는 이 PR에 없다.

### Executor와의 관계 (코드만 읽음, 미시험)

`disable_on_error`가 켜져 있으면 컷오버 도중 연결이 4초 넘게 끊기는 것만으로 구독이 꺼진다. Executor는 이를 자기 변경이 아닌 외부 변경으로 보고 SAFE_HOLD로 멈춘다(`_restore_source`, 시험 `test_subscription_stopped_outside_the_executor_holds`). 그러면 출발지는 펜싱된 채 목적지도 열리지 않아, 사람이 풀 때까지 어느 DB도 쓸 수 없다. 끄면 구독 표시가 켜진 채라 barrier 대기 실패 뒤 ABORT_PRE_WRITE로 갈 것으로 읽힌다. 실제로 돌려 보지 않았고 T12 담당의 확인이 필요하다.

### 적용 방법 (이 PR에 없음)

`infra/envs/target-workloads/replication.py`의 `"disable_on_error": "true"`를 바꾸면 양방향에 적용된다. CNPG 1.30.1은 이 값을 구독을 다시 만들지 않고 갱신하는 항목으로 다룬다(소스에서 확인, 실제 적용은 안 해 봄). 타임아웃은 바꾸지 않으므로 CNPG 파라미터는 그대로다.

## 재현: 끊어서 끄고, 명령으로 되살리기

쓰기 50 req/s 중에 복제 링크를 끊어 구독을 끄고, 약 4만 행을 더 쓴 뒤 실제 명령을 별도 프로세스로 돌렸다. 데이터는 5.3 크기 기준(10만 행, 200MB)에서 시작했다. 조건마다 3회, 9회 모두 통과했다. 값은 중앙값 / 최대다.

| 조건 | 꺼지기까지(초) | 재개 직전 차이(`gap_bytes`) | 수신 기준점(`received_fixed`, 초) | 시험 행 도착(`barrier`, 초) | 정지 중 쓴 행 | ACK 받고 유실된 행 |
| --- | --- | --- | --- | --- | --- | --- |
| 제한 없음 | 5.57 / 5.58 | 86,341,160 | 1.03 / 1.06 | 1.09 / 1.12 | 40,975 | 0 |
| 100Mbps · RTT 30ms | 5.44 / 5.61 | 86,577,440 | 7.20 / 7.21 | 8.51 / 8.55 | 41,042 | 0 |
| 20Mbps · RTT 30ms | 5.64 / 5.64 | 272,811,080 | 33.99 / 34.08 | 35.24 / 35.31 | 41,008 | 0 |

- 9회 모두 끝난 뒤 쓰기를 멈추고 대조했다. ACK 받은 행이 모두 목적지에 있었고, 정지 중 쓴 행도 같은 수만큼 도착했으며, `messages`와 `attachments`의 행별 해시 합이 양쪽에서 같았다. 시험 행은 양쪽에 남지 않았다.
- 끝난 뒤 목적지 앱 NOLOGIN, 출발지 앱 LOGIN, 역방향 OFF였다. 같은 구독에 다시 돌리면 `enable_submissions`가 0이고 확인만 했다.
- 20Mbps의 차이가 큰 것은 초기 복사 중에 생긴, 행을 담지 않은 WAL이 슬롯에 남았기 때문으로 본다. 옮긴 행 수는 다른 조건과 같다.
- 이 값을 #201과 견주지 않는다. 그쪽은 행이 3개뿐이어서 WAL 차이가 같은 크기여도 보낼 데이터가 거의 없다. 조건이 달라 어느 쪽도 다른 쪽을 대신하지 않는다.

## 거부 조건

각 상태를 실제로 만들어 `--apply`를 돌렸다. 21건 모두 종료 코드 1, 해당 사유 표시, 구독은 꺼진 채였다. 그 상태를 되돌리면 같은 명령이 다시 통과해, 거부가 그 상태 때문임을 확인했다.

| 분류 | 시험한 상태 |
| --- | --- |
| 쓰기 방향 | 역방향 구독 실행, 목적지 앱 LOGIN, 목적지 앱 세션 잔존, 출발지 앱 NOLOGIN |
| Executor | 실행 기록 PENDING · RUNNING · SAFE_HOLD, 기록 접근 정보 없음, 접속 불가, 테이블 없음, 제어 세션 존재 |
| 슬롯과 데이터 | 다른 프로세스가 슬롯을 쥠, 목적지에 출발지보다 많은 행 |
| 신원과 접속 | DSN 뒤바뀜, 두 DSN이 같은 클러스터, 출발지 · 목적지 접속 불가, `verify-full` 없는 원격 호스트 |
| 권한 | ENABLE 권한 없음, 시험 행 DELETE 권한 없음, publication에 barrier 없음 |

그 밖에 실제로 확인한 것은 다음과 같다.

- 슬롯을 실제로 무효화(`wal_removed`)하면 `slot_invalidated`로 거부했다.
- 끝난 실행(DONE)은 막지 않았고, Executor 없음을 선언하면 통과했다. 대조값이 틀리거나 없으면 `--apply`를 거부했다.
- 옵션 없는 실행은 3번 돌려도 양쪽 트랜잭션 ID가 움직이지 않았다. 실제 쓰기를 하면 움직이는 것도 함께 확인했다.
- 모든 DSN에 표시용 비밀번호를 넣었고, 어떤 출력에도 나오지 않았다.

## ENABLE 뒤 일이 잘못되는 경우

| 경우 | 결과 |
| --- | --- |
| 사람이 먼저 켠 구독 | 옵션 없는 실행은 쓰기 없이 확인만 했다. `--apply`도 다시 켜지 않고 시험 행만 보냈다 |
| 연결이 아직 끊긴 상태 | 25초 뒤 실패(`deadline`, `source_slot_active` 거짓). 연결 복구 뒤 다시 돌리니 ENABLE 없이 통과 |
| 따라잡는 중 다시 끊김(약 80MiB, 20Mbps) | 구독이 또 꺼져 9초대에 실패(`failed_check`). 연결 복구 뒤 다시 돌리니 통과, 행 도착 확인 |
| 적용 충돌 | 바로 실패. 충돌 행을 지운 뒤 다시 돌리니 통과 |
| 삭제가 복제되지 않는 publication | 시험 행은 도착하고 삭제가 오지 않아 실패. 시험 행 왕복만 잡을 수 있는 경우다 |
| 다른 프로세스가 슬롯을 쥔 채 직접 ENABLE | 구독은 꺼지지 않고 5초마다 재시도(08P01, 오류 수 그대로). 슬롯이 풀리면 스스로 붙었다 |
| `cutover_control`로 실행 | `cutover.set_subscription`으로 켰다. origin 위치는 읽지 못해 시험 행 삭제 도착으로 확인 |
| 제어 함수가 없는 환경 | 구독 소유 권한의 `ALTER SUBSCRIPTION`으로 켰다 |
| `chat_replicator`로 확인만 | 통과. `target_origin_remote_lsn`과 `source_sender_state`는 `null` |

## `cutover.barrier`를 사전 확인에 넣을까

**넣되 재개의 조건으로 삼지 않는다.** 기본 `schema.sql`의 publication에는 업무 테이블 둘뿐이고, barrier 추가는 환경마다 하는 단계다([T12 계약](../../contracts/T12-platform-integration.md)). 업무 복제는 barrier 없이도 돌기 때문에, 빠져 있다고 복구를 막으면 안 된다. 그래서 옵션 없는 실행은 `barrier_gaps`로 알려 주고 통과하며, 시험 행을 보내는 `--apply`만 거부한다. 빠져 있으면 Executor 5단계가 실패하므로 컷오버 전에는 맞춰야 한다.

## 재지 않은 것

- **실제 환경.** TLS 경로, 실제 역할, Tailscale 경로에서 명령을 돌린 적이 없다. `verify-full` 판단은 첨부 복사의 규칙을 그대로 쓰고 단위 시험만 했다.
- **실제 끊김의 모양.** `netem`의 끊김과 손실은 가정값이다. DERP 전환이나 노드 재시작 같은 실제 장애와 같다고 주장하지 않는다.
- **`disable_on_error`를 끈 채 컷오버.** Executor와 함께 돌리지 않았고, 역방향도 재지 않았다. 실제 CNPG에 적용해 보지 않았다.
- **슬롯 한도까지 쌓인 경우.** 실제 `max_slot_wal_keep_size` 1GB에 도달시키지 않았다. 무효화 거부는 한도를 1MB로 줄여 확인했다.
- **실제 시험 행 쓰기 역할.** `cutover_control`에는 DELETE가 없다. 실제 환경의 어느 역할을 `T8_RESUME_SOURCE_PROBE_DSN`에 쓸지 정하지 않았다.
- **출발지 앱의 쓰기 차단.** DB 밖의 상태라 명령이 읽지 않는다. 운영자가 읽은 값을 기록만 하고, 바꾸는 코드는 없다.
- **해시의 전제.** 앱이 행을 넣기만 한다는 전제로 첫 조회 시점까지의 행을 비교한다. 수정 · 삭제가 생기면 쓰기 중에는 비교할 수 없다.

머신 부하는 다른 세션과 함께 쓴 값으로 1분 평균 2.0~8.1, 다른 컨테이너 최대 3개였다. 원값은 `results.json`에 있다.

## 고쳐서 다시 잰 것

처음 결과를 그대로 믿었다면 틀렸을 항목이다.

- **타임아웃 표 전체를 다시 쟀다.** 실험실이 시작 인자로 5초를 고정해 `ALTER SYSTEM`이 무시됐고, 60초 설정도 5.5초에 꺼졌다. 이제 서버에서 읽은 실제 값을 대조하고 어긋나면 멈춘다. 81회 모두 설정과 같았다.
- **20Mbps 재현을 다시 쟀다.** 슬롯 지연을 기준으로 쌓았더니 약 180MB가 VACUUM WAL이어서 행을 186건밖에 옮기지 않았다. 이제 정지 시점부터 쌓고, 3만 행 미만이면 실패로 친다.
- **코드 주석을 고쳤다.** 슬롯을 쥔 채 켜면 구독이 다시 꺼진다고 적었는데, 재 보니 꺼지지 않고 재시도한다.
- **행 비교 순서를 고쳤다.** 출발지를 먼저 읽어 정상인 목적지가 앞선 것으로 보여 거부됐다. Executor처럼 목적지를 먼저 읽는다.
