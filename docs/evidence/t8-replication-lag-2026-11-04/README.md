# T8 논리 복제 지연 측정 — 2026-11-04

**설계 5.3의 데이터 크기 기준(업무 표 합계 10만 행, 200MB 이하)은 유지를 추천한다.** 같은 Mac의 PostgreSQL 18.4 컨테이너 두 대에서, 쓰기 50 req/s를 멈춘 뒤 마지막 행은 20ms 안에 목적지에 도착했고 양쪽 LSN(WAL 위치)은 약 0.45초 안에 같아졌다. 데이터를 2배로 늘려도 행 도착은 그대로였고, LSN은 3회 중 1회만 0.72초까지 튀었다. 복제가 쓰는 예산은 작고 크기에 따라 뚜렷이 늘지 않으므로, 크기의 한계를 정하는 것은 복제가 아니라 최종 비교다.

**로컬 값이다.** 네트워크 조건 세 가지는 전부 가정값이다. 실제 Tailscale · DERP, TLS, 실제 앱 부하는 재지 않았다. 설계 문서는 고치지 않았다. 5.3 확정은 아래 조건 세 가지를 확인한 뒤에 한다.

## 판단

쓰기 정지 예산 5,000ms는 따라잡는 시간, 최종 비교, 나머지 단계로 나뉜다. 아래 표는 [results.json](results.json)의 `budget_view`다. 최종 비교는 T13 측정의 큰 쪽 값 1,300ms를 넣었다(아래 조건 3).

| 무엇을 기다리나 | 따라잡는 시간 | 나머지 단계에 남는 시간 |
|---|---|---|
| barrier(실행기가 넣는 표시 행) 도착, 평상시 최악 | 172ms | 3,528ms |
| 양쪽 LSN 같아짐, 평상시 최악 | 450ms | 3,250ms |
| barrier 도착, 실행기 문턱(1MiB)까지 밀린 상태 · 20Mbit | 735ms | 2,965ms |
| 양쪽 LSN 같아짐, 같은 밀린 상태 · 20Mbit | 928ms (첫 실행 1,120ms) | 2,772ms (첫 실행 2,580ms) |

- **barrier가 실제 기준이다.** 실행기(`runner.py` `_compare`)는 LSN이 아니라 barrier 행 도착을 50ms 간격으로 확인한다. 그래서 barrier 줄에는 재어 본 모든 행의 최악값 122ms에 50ms를 더했다. barrier도 평범한 행 하나이기 때문이다.
- **나머지 단계는 아직 재지 않았다.** 표의 마지막 열은 그 단계들이 쓸 수 있는 상한이지, 남는다는 뜻이 아니다. T25 반복 측정에서 확정한다.
- **크기를 늘리는 것은 추천하지 않는다.** 복제만 보면 2배도 괜찮지만, 비교 시간이 크기에 비례해 2.6초가 된다면 남는 시간이 크게 줄어든다. 비교 시간과 나머지 단계가 재어지기 전에는 올릴 근거가 없다.

유지하려면 확인할 조건 세 가지:

1. **T13의 DB 안 비교(`db-sql-v1`)가 실행기에 연결돼야 한다.** 지금 `develop`의 기본 비교기는 행을 모두 읽는 방식이라 목적지에서만 약 205MB를 받는다. T13 측정(가정 네트워크)에서 100Mbps 61.6초, 20Mbps 132.3초가 걸렸다. 이 상태로는 예산을 넘으므로 5.3을 유지할 수 없다. 구현은 [#154](https://github.com/Softbank-Hackathon-Finals/platform/pull/154) 머지 전이고, 연결은 T12 몫이다.
2. **실제 경로를 `observe`로 다시 재야 한다.** 2KB 행 50 req/s의 평상 전송량은 1.04Mbit/s였다. 실제 대역폭이 이 근처까지 낮으면 지연이 계속 쌓일 것이다. 계산일 뿐, 이 측정의 어느 조건도 그만큼 좁지 않아 재지는 않았다.
3. **비교 시간을 실제 경로와 현재 규칙으로 다시 재야 한다.** 1,300ms의 출처는 [노션 T13 글](https://app.notion.com/p/40d8bee9ada4814881e7e74bac7f9908) 「구현 방식 비교 (11/3 측정)」의 DB 안 방식 100Mbps · 20Mbps(RTT 30ms) 값이다(출발지 + 목적지 합계, 2회 중앙값). 네트워크 제한은 프록시로 건 가정값이고, 콜레이션 항목을 넣기 전 규칙으로 쟀다. 현재 규칙으로 잰 값은 제한 없는 로컬 0.631초([#154](https://github.com/Softbank-Hackathon-Finals/platform/pull/154))뿐이다.

## 측정

[results.json](results.json)이 원본이다. 조건마다 5회(2배 크기만 3회), 조건을 번갈아 돌렸다. 셀은 `중앙값 / 최대`, 원측정값은 `summary.*.raw`에 있다.

| 조건 (가정값) | 초기 복사 (초) | 평상 지연 평균 (ms) | p95 (ms) | 최대 (ms) | 마지막 행 도착 (ms) | LSN 같아짐 (ms) |
|---|---|---|---|---|---|---|
| 제한 없음 | 1.1 / 1.4 | 2.0 / 2.4 | 3.3 / 4.0 | 24 / 70 | 2.6 / 3.5 | 403 / 405 |
| 100Mbps · RTT 30ms | 16.7 / 16.8 | 17.2 / 17.7 | 18.9 / 20.0 | 59 / 92 | 17.8 / 19.4 | 443 / 450 |
| 20Mbps · RTT 30ms | 78.3 / 78.3 | 18.0 / 18.2 | 19.8 / 20.7 | 50 / 122 | 17.3 / 19.2 | 446 / 447 |
| 20Mbps · RTT 30ms, 데이터 2배 | 155.8 / 156.0 | 18.2 / 18.3 | 19.7 / 20.1 | 56 / 159 | 17.2 / 17.9 | 473 / 717 |

- **데이터:** `messages` 98,000행 + `attachments` 2,000행, 합계 약 198MiB(207.6×10⁶바이트). 2배 조건은 약 396MiB. 전송량은 1배 · 제한 조건 기준 193MB였다.
- **부하:** `messages`에 1,800자 본문을 쓰기 50 req/s로 60초. 달성률 50.0 req/s, 조건마다 약 3,000행. T18 부하 생성기의 본문은 수십 바이트라서, 이 값은 실제보다 무겁게 잡은 쪽이다.
- **초기 복사는 쓰기 정지 예산 밖이다.** 컷오버 전에 끝나는 단계다. 시간은 크기에 비례해 2배가 됐다.
- **마지막 행 도착:** 마지막 쓰기의 응답 시각부터 목적지에서 그 행이 보일 때까지. 같은 구간에 `received_lsn`과 `latest_end_lsn`도 함께 도착했다(`catchup_*`).
- **LSN 같아짐:** 쓰기를 멈춘 시점의 `pg_current_wal_lsn()`을 슬롯의 `confirmed_flush_lsn`이 넘을 때까지. 출발지가 "목적지가 디스크에 기록했다"는 보고를 받는 시점이다.
- **유실:** 모든 실행에서 복사 직후와 쓰기 후 양쪽 행 수 · 최대 ID가 같았고 못 찾은 행은 0개였다.

**설정은 실제에 맞췄다.** DB 컨테이너는 CPU 1 · 메모리 1GiB(`render.py`), `wal_sender_timeout` · `wal_receiver_timeout` 5초(CNPG 1.30.1 기본값), `max_slot_wal_keep_size` 1GB, 구독 옵션은 #131 `replication.py`와 같다(TLS · 비밀번호 제외). 스키마는 `source-workloads/schema.sql`과 #131의 `target-workloads/schema.sql`이다.

**머신은 혼자 쓰지 않았다.** 다른 세션의 Docker 시험이 함께 돌았다. 측정 시점 부하 평균 2.4~13.5, 다른 컨테이너 2~14개(`machine`). 지연 평균 · p95는 조건 안에서 거의 일정했지만 최대값은 튀었고, 같은 구간에 쓰기 응답도 최대 273ms까지 튀었다. 최대값에는 이 잡음이 섞여 있다.

## 찾은 것

- **연결이 5초 넘게 끊기면 구독이 스스로 꺼지고 돌아오지 않는다.** 100Mbps 조건에서 복제 링크를 3초 끊었을 때는 회복해 양쪽 최대 ID가 2,050으로 같아졌다. 8초 끊었을 때는 `wal_receiver_timeout`(5초)에 걸려 `disable_on_error`로 구독이 꺼졌고, 링크를 복구하고 10초 뒤에도 꺼진 채였다(출발지 2,300, 목적지 1,902). 각 1회이고 재현 스크립트는 저장소에 없다(`link_blip_check`). 실행기는 사전 확인에서 꺼진 구독을 보고 멈추므로 쓰기 DB가 둘이 되지는 않는다. 다만 그때까지 지연이 쌓이고, WAL 보관 한도 1GB를 넘으면 슬롯을 다시 만들어야 할 수 있다. 실제 경로에서 5초 넘는 끊김이 나는지는 재지 않았다. 두 설정은 #131 구독 옵션과 CNPG 기본값이라 고치지 않았다.
- **원인을 확인하지 못한 실패 1건.** 코드 정리 뒤 확인 실행에서 초기 복사 중 구독이 꺼져 실패한 적이 있다. 같은 시간대에 이 머신의 인터넷이 끊겨 세션이 멈췄으므로 위 시간 제한 때문으로 추정하지만, 로그가 남지 않아 확인하지 못했다. 같은 조건 재실행 3회와 본 측정 18회에서는 나오지 않았다.
- **LSN 기준은 barrier 기준보다 약 0.4초 늦다.** 값이 200ms와 400ms 근처에 모였다. 구독의 `synchronous_commit` 기본값 off와 WAL 기록 주기 200ms 때문으로 추정하지만, 설정을 바꿔 확인하지는 않았다. 뒤집어 말하면 barrier 도착은 "목적지 디스크에 기록됨"을 보장하지 않는다. 그 보장이 필요하면 0.45초를 더 잡아야 한다.
- **실행기의 1MiB 문턱은 데이터가 밀리지 않아도 넘을 수 있다.** 자동 VACUUM이 측정 구간에 겹치면 WAL이 초당 3.3MB로 늘어(평소 0.16MB) 위치 차이가 최대 2.5MB까지 벌어졌고, 표본의 0.08~0.17%가 1MiB를 넘었다. 이때도 행 지연 p95는 20.7ms 이하였다. 실행기는 이 값을 한 번 읽고 넘으면 쓰기 전 실패로 처리하므로 드물게 시도가 헛돌 수 있다. 데이터 위험은 없다. T12 담당자가 판단할 일이고 코드는 고치지 않았다.
- **VACUUM은 네트워크 효과가 아니다.** 시간 배치 때문에 20Mbit 1배 조건 5회에만 양쪽 VACUUM이 구간과 겹쳤다(`autovacuum_runs_in_window`). 문턱 초과가 20Mbit에서만 보이는 이유이며, 대역폭과 인과 관계로 읽으면 안 된다.

## 측정이 실제로 재는가

| 확인 | 기대 | 결과 |
|---|---|---|
| 구독을 5초 멈추고 쓰기 계속 | 지연이 약 5초로 커지고, 재개 뒤 돌아온다 | p50 2.5ms → 최대 4,995ms → p50 2.4ms (20Mbit: 18.1 → 5,184 → 18.3) |
| 구독을 멈춘 채 쓰기 중단, 2초 뒤 재개 | 따라잡는 시간이 2초 이상 | 2,012ms (20Mbit: 2,690ms) |
| 제한을 빼면 | 지연이 편도 15ms만큼 줄어든다 | 18.0ms → 2.0ms |
| PostgreSQL 자체 `replay_lag`와 비교 | 약 RTT | 제한 없음 0.1ms, 100Mbit 30.4ms, 20Mbit 31.2ms |
| 초기 복사 최소 시간과 비교 | 이론 최소보다 느리다 | 20Mbit: 최소 77.3초, 실측 78.3초 |
| 링크 자체 측정 (ping · iperf3) | 설정값 근처 | RTT 33.4~35.1ms(설정 30ms), 91.1 · 18.4Mbit |

**첫 검증 실패를 남긴다.** 첫 실행에서 20Mbit 검증의 `rows_match`가 거짓이었다. 읽기 전용 점검이 넣은 대조 행 1개가 도착하기 전에(지연 18ms) 행 수를 비교한 시험 순서 문제였고, 행 유실은 아니었다. 그 행을 기다린 뒤 비교하도록 고쳐 검증만 다시 돌렸다(`first_validation_attempt`).

**읽기 전용 모드 확인** (`validation.*.read_only`):

- 조용한 두 DB에 5초 관측하는 동안 양쪽 트랜잭션 ID 카운터와 행 수가 그대로였다. 비교 전에 자동 VACUUM을 껐다. 켜 두면 VACUUM이 ID를 쓰기 때문이다. 대조로 실제 쓰기 1건에는 카운터가 움직였다.
- 관측 세션에서 일부러 시도한 `INSERT`는 서버가 거부했다(`ReadOnlySqlTransaction`).
- 쓰기가 없으면 지연을 0으로 내지 않고 `source_idle: true`로 낸다.
- 부하 중 관측값은 표본 간격(약 26ms) 두 배 안에서 로컬 측정과 일치했다. 관측 모드의 행 지연은 이 간격만큼의 오차가 있다.

측정 도구의 해상도는 약 3ms다(`sample_interval_ms`). 모든 시각은 한 프로세스의 단조 시계로 쟀다.

## 재지 않은 것

- **실제 Tailscale · DERP:** WireGuard 오버헤드, MTU 1280, DERP 중계 대역폭. 값은 netem 가정값이고 유실 · 지터는 넣지 않았다. 복제 왕복과 MTU · DERP 경유 확인은 #131에 있다.
- **TLS 비용:** 실험 DB는 TLS와 비밀번호 없이 붙었다. 실제는 `verify-full`이다.
- **실제 앱 부하:** 앱 · PgBouncer를 거치지 않은 직접 `INSERT`다. 읽기 150 req/s, 재시도, 긴 트랜잭션도 넣지 않았다.
- **실제 저장 장치와 플랫폼:** RKE2 위 CNPG와 로컬 볼륨이 아니라 Docker Desktop VM 디스크다.
- **쓰기 중 초기 복사:** 복사 중에는 쓰기를 멈췄다.
- **나머지 단계와 전체 쓰기 정지 시간:** 컷오버를 실행하지 않았다.
- **체크포인트:** 시드 뒤 1회 외에 구간 안에 일부러 넣지 않았다.

## 실제 경로에서 재는 법

같은 스크립트의 `observe`는 쓰지 않는다. 정해진 `SELECT`만 보내고, 매번 `BEGIN READ ONLY` 안에서 돌리며, 서버가 읽기 전용이라고 확인하지 않으면 끊는다. DSN은 환경 변수로만 받고 출력하지 않는다. **이번에는 실제 환경에 접속하지 않았다.**

```bash
export T8_LAG_SOURCE_DSN='…'
export T8_LAG_TARGET_DSN='…'
uv run --script infra/envs/target-workloads/testing/replication_lag.py observe --seconds 120 --interval 0.02 --out observe.json
```

- **필요한 것:** 부하가 흐르는 상태, 양쪽 `messages` `SELECT` 권한. `pg_read_all_stats`가 없으면 `pg_stat_replication` 열만 비고 나머지는 잰다. 어디서 어떤 역할로 접속할지는 TBD다(tailnet ACL은 5432를 복제 역할에만 연다).
- **못 재는 것:** 쓰기를 멈출 수 없으므로 따라잡는 시간은 직접 나오지 않는다. `received_position_lag_ms`(출발지 위치가 목적지에 닿는 시간)로 가늠한다.
- **컷오버 중에는 돌리지 않는다.** 실행기가 `system_roles` 밖의 세션을 우회 쓰기로 본다(`db.py` `other_sessions`).
- **풀러 경유는 시험하지 않았다.** 직접 연결을 쓴다.

## 재현

Docker와 인터넷(ECR 공개 이미지, Alpine 패키지)이 필요하다. 컨테이너 · 네트워크 · 임시 이미지는 모두 `t8-lag-`로 시작하고 끝나면 지운다. #131이 머지되기 전에는 목적지 스키마를 `origin/feature/T8-replication-runtime`에서 읽는다. 약 1시간 걸린다.

## 입력

- **측정 코드:** `environment.scripts_sha256`은 본 측정 당시 바이트이고 커밋 `3844333`과 같다. 그 뒤 검증 시험 순서와 예산 계산만 바꿨고, 측정 경로는 그대로다. 다시 돌린 검증의 해시는 `validation_scripts_sha256`에 있고 커밋 `14d7cdd`와 같다. 그 뒤에는 비교 시간 출처 표기와, 리뷰에서 나온 측정 시간에 영향 없는 수정(CPU `--` 처리, 이미지 태그 분리, 표본 0건 방어, `observe` 기본 간격)만 했다.
- **이미지 · 스키마:** `environment.postgres_image_id`, `environment.schema_sha256`.
