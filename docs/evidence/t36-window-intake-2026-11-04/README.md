k3s에서 추가로 확인한 것:
- restricted 네임스페이스에서 창 수신이 뜬다.
- `window-producer` 라벨 네임스페이스에서 수신 토큰으로 보내면 201이다. `received_at`은 생산자 값이 아니라 플랫폼 시각이다.
- 같은 창은 409, 콘솔 토큰은 401이다.
- 라벨 없는 네임스페이스와 콘솔 네임스페이스는 올바른 토큰이 있어도 NetworkPolicy가 막는다. 뒤이어 같은 창을 loadgen에서 보내 201이 나와, 막힌 쪽이 저장하지 못했음을 확인했다.
- 창 수신 Pod는 밖으로 나가지 못한다. 대조군인 조회 API는 같은 DNS 53에 연결된다.

자원 실측(앱 지표 약 2000건/초 + 창 10건/초, 3분). 괄호는 cgroup anon(프로세스가 쥔 메모리)이다.

| 컨테이너 | 최대 메모리 (anon) | 평균 / 최대 CPU |
|---|---|---|
| Collector | 223MiB (72MiB) | 29m / 38m |
| Prometheus | 72MiB (43MiB) | 13m / 19m |
| 조회 API | 49MiB (42MiB) | 3m / 7m |
| 창 수신 | 44MiB (41MiB) | 29m / 38m (평상 3m) |

- 창 1,662건 중 1,656건 저장, 6건 연결 거부, 창 수신 재시작 0이다. 거부는 새로 뜬 부하 Pod의 처음 요청이다. k3s가 새 Pod 주소를 NetworkPolicy에 반영하기 전으로 추정하며, 확인하지는 않았다.
- 플랫폼 노드에 필요한 관측 request는 85m · 256Mi다(플랫폼 Collector까지 두면 135m · 384Mi). [서비스 README](../../../services/observability/README.md#플랫폼-노드-몫)에 T7 용량과 함께 적었다.

시험이 찾은 결함 9건은 `results.json`의 `defects_found`에 있다. 그중 두 가지가 중요하다.
- **미래에 끝나는 창 하나가 이후 창을 모두 막는 문제:** 순서 규칙("이미 받은 창보다 늦게 끝나지 않는 창 거부") 때문이다. 수신 시각보다 2초 넘게 미래에 끝나는 창을 받지 않아 막았다.
- **k3s 시험 정리 결함(#152부터):** 결과가 "실패 0건"이어도 종료 코드 143이 나가고 클러스터와 임시 인증서가 남았다. 고친 뒤 종료 코드 0, 남은 것 없음을 확인했다.

시험 이미지는 기준 커밋 소스로 다시 빌드한 이미지와 파일 시스템 레이어가 모두 같다. 단 `README.md`는 자원 표를 시험 뒤에 고쳐 시험 당시 판으로 맞췄다. 원본 시험 로그는 k3s Pod 주소가 있어 저장소에 넣지 않았다. 로그에서 판정과 측정값만 옮겼다.
