# 실제 해피패스 연결을 위한 운영자 인수 요청

상태: **담당자 합의 요청**. 2026-11-08 03:02 KST 읽기 전용 확인 기준이다.
이 문서의 병합은 권한 부여·운영 실행 승인·이전 완료를 뜻하지 않는다.

## 요청

실제 AWS → 온프렘 이전을 같은 계획으로 이어가기 위해 다음 인계를 요청한다.
기존 [T28 조율](https://github.com/Softbank-Hackathon-Finals/platform/issues/36#issuecomment-6709988956)을 구체화한 문서이며 새 실행 담당을 배정하지 않는다.

| 우선순위 | 요청 대상 | 결정·인계할 내용 | 인수 확인 |
|---|---|---|---|
| 1 | T10 담당 | 현재 사용할 실제 계획의 보호된 참조, 앱·양쪽 환경·평가 프로필·현재 버전 | 본인 또는 기존 담당자의 정식 API 조회 결과가 같은 계획을 가리킨다. 과거 `full/1` 계획과 현재 `demo-gate` 설정을 섞지 않는다. |
| 2 | T10 담당 | 아래 두 방식 중 운영자 연결 방법과 담당을 확정 | 본인 계획 조회가 성공하거나 기존 담당자가 정식 조회·승인을 인계한다. |
| 3 | T10·T12·환경 담당 | 롤아웃 완료 여부, 겹치는 작업, 공용 앱·DB·Edge 실행 구간과 실행 담당 | 해당 실행의 시작·종료와 중복 실행 부재를 확인한다. 지난 실행 구간의 허용을 재사용하지 않는다. |
| 후속 | T10·T43 담당 | 두 고정 API 이름을 포함하는 인증서 갱신과 공개 신뢰 정보 인계 | 고정 주소 자체를 대상으로 체인·기한·호스트명 검증이 모두 통과한다. |

실제 계획·테넌트·클라우드 신원·인증 자료는 기존 보호된 인계 경로로 전달한다.
PR에는 선택한 방식과 담당·완료 여부를 남기며, 비밀값을 붙이지 않는다.

## 운영자 연결 제안

**우선 제안: 본인 SSO에 해당 계획의 조회와 담당 업무에 필요한 권한을 한정해 연결한다.**

- T10 담당이 기존 신원 검증 설정에 본인을 연결하고, 기존 `OperatorAccess` 관리 경로에서 해당 계획의 `read`를 부여한다. 테넌트·주체·유효기간·현재 권한 revision·관리 결정 근거를 확인한다.
- T14 원문 수집과 T19 인수에 필요한 `gate:record`·`gate:read` 등은 실제 사용하는 API와 주체를 확인해 별도로 정한다. 등록 호스트의 GateRecord 권한과 승인 호스트의 OperatorAccess 권한을 서로 대신하지 않는다.
- 승인·실행 권한은 한꺼번에 추가하지 않는다. 사람 승인과 기존 반영·실행 주체를 구분해, 담당 단계에 필요한 권한만 합의한다. 클러스터 관리자 신원을 제품 권한으로 간주하지 않는다.
- 기존 실제 계획을 재사용할 수 있다면 환경·앱의 신규 등록 권한은 요청하지 않는다.

**대안: 기존 운영자가 자신의 SSO로 정식 조회·등록·승인을 수행한다.**

본인 신원 연결을 기다리기 어려우면 T10 담당이 같은 실제 계획을 조회하고 필요한 사람 승인을 맡는다.
본인 담당은 새 T14 원문·T19 인수 근거·콘솔 조회 연결이며, 실행은 기존 T10/T12 경로를 사용한다.
타인 토큰 전달이나 포괄적인 사전 승인 없이, 단계마다 현재 계획·버전·변경 내용에 결속된 승인 결과를 인계한다.

## 직접 확인한 상태

| 항목 | 03:02 KST 결과 | 확인 범위 |
|---|---|---|
| 플랫폼 접속 | 등록된 클러스터 UID 및 개인 운영자 그룹 일치 | Tailscale 고정 경로의 읽기 전용 조회 |
| 두 고정 API | 연결 및 TLS 1.3 검증 성공 | 플랫폼 API 확인에 SSM·port-forward를 사용하지 않음 |
| 인증서 이름 | 두 API 모두 tailnet 이름으로 검증하면 오류 62 | 기존에 신뢰한 인증서 이름을 명시하면 검증 통과. 검증을 끄지 않음 |
| 등록 API | 인증 정보 없는 루트 GET 404 | HTTP 도달 확인이며 등록 인증·등록 성공 시험이 아님 |
| 승인 API | 본인 SSO로 보존된 실제 계획 GET 403 `forbidden` | 등록된 운영자 목록에서 본인 신원 부재도 확인. 현재 정본 계획은 별도 인계 필요 |
| 운영 변경 | 0건 | 등록·승인 POST, 권한 변경, DB·Edge 전환 미실행 |

승인 서버는 인증된 Kubernetes 경로에서 확인한 self-signed serving 인증서를 정확히 고정했다.
등록 서버는 담당자가 공개한 CA의 해시를 대조했다. 두 연결 모두 `CERT_REQUIRED`와 호스트명 검증을 유지했다.
접속 주소와 검증 대상 TLS 이름을 분리해 시험했으므로 일반 클라이언트에서 고정 URL만 입력해 정상 동작한다고 주장하지 않는다.
등록 성공에 대한 담당자의 공지와 본인이 직접 실행한 읽기 전용 시험을 구분한다.

## 인계 후 진행과 완료 기준

1. 같은 실제 계획·앱·환경·프로필을 확인하고 실행 구간을 확정한다.
2. 본인 담당의 새 양쪽 T14 원문을 기존 T10 저장·조회에 연결하고 T19 판정을 확인한다.
3. 기존 담당 경로에서 제안·리허설·변경 승인·반영과 최신 보안·데이터 준비 재평가를 이어간다.
4. 현재 근거에 결속된 SHIFT·컷오버 승인과 기존 실행기로 전환한다.
5. 신규 쓰기·첨부·재접속·관측 및 정본 완료 상태를 확인하고 같은 계획의 결과를 콘솔에서 읽는다.

접속 성공·권한 부여만으로 전체 해피패스 완료를 표시하지 않는다. 실제 실행 중 추가 문제가 나오면 해당 단계에서 추적한다.
서버 등록·권한·인증서 변경은 담당자가 합의한 후속 변경으로 처리하며, 이 요청 PR에는 운영 설정 패치를 포함하지 않는다.
