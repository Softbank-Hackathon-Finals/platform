# 설계 문서 버전 이력

설계 문서의 원본은 이 레포의 [`docs/design.html`](../design.html)이다(노션 페이지는 이 파일의 링크와 요약만 둔다). 항상 최신본이 이 경로에 있고, 대체된 버전의 사본은 이 폴더에 둔다. 사본은 고치지 않는다.

## 버전을 올리는 기준

| 변경 | 예 | 버전 |
|---|---|---|
| 작은 수정 | 오타, 실측값 갱신, 표현 다듬기 | 그대로. `design.html`을 고쳐 PR (git 이력으로 남는다) |
| 의미 있는 변경 | 아키텍처 · 시나리오 · 범위 · 요구사항 변경, 작업 계획 재편 | 올린다. `scripts/design-bump.sh <새 버전>`으로 시작한다 |

의미 있는 변경에는 결정이 따르므로 ADR(`docs/adr/`)을 함께 쓰고 아래 표에 연결한다. 작업 계획(11장)이 바뀌면 `docs/tasks.md`도 같이 고친다(작업 계획의 기준은 `tasks.md`).

## 버전 올리는 순서

1. `scripts/design-bump.sh v0.2`를 실행한다. 스크립트가 `origin/main`의 지금 버전을 이 폴더에 복사하고, 그 시점에 `design-<지금 버전>` 태그를 달고, `design.html`의 버전 표기(머리말 · 꼬리말)를 새 버전으로 바꾼다. `main`에서 실행하면 `design-bump-<새 버전>` 브랜치를 만들고, 작업 브랜치에서 실행하면 그 브랜치에서 그대로 한다(본문을 이미 고치고 있어도 된다).
2. `design.html` 본문을 고친다.
3. 아래 표의 "무엇이 바뀌었나" · "관련 ADR"을 채운다.
4. PR로 올린다. 두 버전의 차이는 GitHub에서 `compare/design-<이전 버전>...main`으로 본다.

## 놓치지 않게 하는 장치

- **에이전트**: `todo-task` 스킬이 설계 문서를 고치기 전에 변경 크기를 판단하고, 의미 있는 변경이면 사용자에게 버전 번호를 확인받아 이 스크립트를 먼저 실행한다.
- **CI 경고**: PR이 `design.html`을 바꿨는데 버전 표기가 그대로면 `design-doc` 검사가 PR 화면(바뀐 파일의 버전 줄)에 경고를 남긴다. 필수 검사가 아니라 머지를 막지 않는다. 작은 수정이면 무시한다.

### v0.3 보관 기준

현재 개발 정본인 `develop`의 `c7822e5fb1f6b4adea4392914ff4010e5a258dcd`에서 v0.2를 바이트 그대로 보관했다. 기존 bump 스크립트는 `origin/main`을 읽고 원격 태그를 자동 게시하므로 이번 개발 브랜치 변경에는 실행하지 않았다. 이 PR은 이전 사본 · 머리말/꼬리말 버전 · ADR을 함께 제출하며, 원격 설계 태그 게시나 팀 채택 완료를 의미하지 않는다.

### v0.4 보관 기준

T10의 v0.3이 먼저 병합되어, 개발 정본 `develop`의 `2c43d59914efe9a59133ce285923faa185dcbfe5`에서 v0.3을 바이트 그대로 보관했다. 이미 보관된 v0.2는 변경하지 않았다. T11의 모델 제공자 제안은 v0.4로 구분하고 T10 계획 조회 계약은 유지한다. 기존 bump 스크립트는 `origin/main`과 원격 태그 게시를 전제로 하므로 위와 같은 사본 보관 절차를 적용했다.
