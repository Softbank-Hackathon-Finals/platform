# 로그의 시험용 비밀 노출 검사 (SEC-01.3)

`secret_logs.SecretLogProbe`는 T5 v1의 **로그 내 카나리 비밀 0건 + 같은 로그의 허용 대조군**을
검사한다. 운영 비밀번호를 시험용으로 복사하지 않는다. 이 모듈은 앱 설정을 변경하거나
앱을 재시작하지 않는 신뢰된 서버 라이브러리다. 외부 보고서 업로드 API가 아니다.

## 실행 순서와 책임

1. 호스트가 등록된 앱·환경·revision·설정 지문과 로그 원천·전체 스트림 집합을 고정한다.
   다른 Pod, 누락된 stderr, 실행 중 교체된 Pod의 일부 로그만 검사하지 않는다.
2. 승인된 시험 실행기가 실행마다 새 `bravo_secret_` + 32바이트 난수의 16진수 문자열과
   별도의 `bravo_log_` + 16바이트 난수 문자열을 생성한다. 앞의 값은 사용 권한이 없는
   시험용 값이고 뒤의 값은 공개 가능한 대조 문자열이다.
3. 시험용 값을 앱 설정에 실제로 주입하고 승인된 코드 경로를 실행한다. 각 등록 스트림에
   대조 문자열을 남긴다. 원래 설정 복원 및 앱 상태 확인까지 끝낸다.
4. 전달 큐 drain/flush와 수집 상태를 확인한 호스트가 해당 실행의 `LogCanaryReceipt`를
   만든다. 설정 적용·경로 실행·복원·로그 전달 완료 네 확인이 모두 필요하다.
   **시간을 기다렸거나 마지막 페이지를 읽었다는 사실만으로 전달 완료를 선언하지 않는다.**
5. `SecretLogProbe`가 고정된 구간의 전체 로그를 읽고 카나리 원문과 대조 문자열을 검사한다.
   실행 ID·앱·환경·원천·스트림·설정 지문이 다르거나 10분 이상 지난 영수증은 거부한다.
6. 내용 대신 결과·건수·원천 및 사건 지문을 증거 저장소에 보존한 뒤 Observation을 반환한다.
   저장 실패·조회 거부·시간 초과는 Runner에서 UNKNOWN으로 남는다. 원본 로그의 접근·보존
   정책은 호스트 책임이며 이 코드가 원본 로그를 별도 파일에 복사하지 않는다.

위 영수증은 신뢰된 실행기의 내부 호출 계약이다. JSON의 `acknowledged`를 사용자나 AI가
채웠다는 이유로 수용하지 않는다. 효과 승인·실행권·동시 설정 변경 방지·전후 workload
readback은 운영 호스트에 연결해야 한다. 현재 이 효과 실행부와 운영 연결은 미구현이다.

## 판정

| 조건 | 결과 |
|---|---|
| 전체 스트림의 대조 문자열 확인 + 비밀 원문 0건 | PASS / absent |
| 전체 스트림의 대조 문자열 확인 + 비밀 원문 1건 이상 | FAIL / present |
| 한 스트림이라도 대조 문자열 미확인 | UNKNOWN / POSITIVE_CONTROL_FAILED |
| 일부 검색·마스킹된 뷰·다른 실행·중복 사건·범위 불일치 | UNKNOWN |

비밀만 찍히고 대조 문자열이 빠진 경우도 합격이 아니다. 비밀 검출 건수는 증거에 남지만
허용 대조군이 실패했으므로 T5 계약대로 UNKNOWN을 반환한다. 읽기 실패의 예외 원문은
Runner가 결과에 넣지 않는다. 최대 10,000개 사건·10 MiB의 메모리 예산을 넘으면 거부한다.

## CloudWatch 연결

`CloudWatchSecretLogSearch`는 인증된 SDK 클라이언트와 정확한 log group ARN·stream 목록을
받는다. 계정·호출 역할 및 원천 소유권은 호스트에서 확인한다. AWS·온프렘이 동일한 계정이나
저장소라고 가정하지 않는다. 온프렘 수집기는 같은 `LogWindow` 계약으로 별도 연결한다.

- 카나리나 비밀을 API 검색어로 보내지 않는다. `filterPattern` 없이 구간 전체를 읽는다.
- `unmask=true`를 고정한다. `logs:Unmask` 권한이 없으면 조회 실패이며, 마스킹된 결과로
  자동 재시도하지 않는다. 원문 접근은 별도 승인된 최소 권한 시험 주체에만 부여해야 한다.
- 비어 있는 페이지도 `nextToken`이 있으면 계속 읽는다. 반복 토큰·10페이지·30초 예산
  초과는 불완전한 조회로 거부한다. SDK 연결/읽기 제한과 재시도 제한도 검사한다.
- 사건 시각은 밀리초이므로 호스트가 조회 구간 경계를 밀리초에 맞춰 확정한다. 임의 반올림으로
  끝부분을 빼지 않는다. `searchedLogStreams`의 폐기된 완전성 표시는 사용하지 않는다.

API 동작 근거: [AWS FilterLogEvents 공식 문서](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_FilterLogEvents.html).

## 검증 범위와 남은 일

- 회귀: 비밀 노출, 모든 스트림 대조군, 범위·실행·설정 불일치, 마스킹/부분 결과, 권한 거부,
  빈 페이지·반복 토큰·시간/페이지 예산, 증거 저장 실패를 검사한다.
- 실제 로컬 Python 자식 프로세스의 stdout/stderr에서 정상·누출 두 경로를 검사한다.
  이는 고정 시험 프로세스이며 배포된 demo-chat이나 실제 CloudWatch 검증이 아니다.
- 운영 연결에는 승인된 카나리 설정 주입/복원과 코드 경로 실행, 원천별 전달 완료 확인,
  양쪽 실제 로그 수집기·읽기 권한이 남아 있다. T14 전체 완료 체크를 변경하지 않는다.
- 검출 대상은 **이번 시험의 원문 카나리**다. 임의 운영 비밀 전체, 인코딩/암호화/분할된 값,
  실행하지 않은 코드 경로, 등록하지 않은 로그 목적지의 비노출을 증명하지 않는다.
