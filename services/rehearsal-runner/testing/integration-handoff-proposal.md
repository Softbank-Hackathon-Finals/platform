# T15와 T38·T10 연결 검토안

이 문서는 담당자와 합의할 제안이며 운영 API나 결과 판정 계약의 원본이 아니다.
T10 승인 규칙은 `docs/contracts/T10-change-approval.md`, T38 실행 규칙은 해당 구현을 따른다.

## 검증 요청

1. T15가 제안의 `run_id`, `source_sha`, `proposal_digest`와 시도 번호를 준비한다.
2. T15는 네임스페이스를 생성하고 T3 격리 시험을 통과한 이름·UID와 시험 참조를 같은 요청에 전달한다. T38은 작업 실행 전후와 증거 수집 시 동일 UID를 확인하고, 격리 근거의 출처와 유효성을 확인한다. T15가 생성한 객체를 이름만으로 재사용하지 않는다.
3. T38이 버킷 정책과 자격 증명 이전의 제품 검증 Job을 실행하고, 제안·시도·네임스페이스 및 Job·Pod·이미지·증거를 결속한 결과를 제공한다. 실행 불명과 중복 호출 복구 방법을 합의한다. 현 `verification.py`는 DB_HOST 시험 fixture와 attempt=1만 지원한다.
4. 정리 책임을 한쪽으로 정한다. 제안은 T15가 생성한 UID를 T38의 기존 UID 조건 삭제 기능에 전달하고, T15가 부재를 확인하는 방식이다. 삭제 응답만으로 완료를 가정하지 않고 실패·불명이면 사람에게 넘긴다. 재시도별 UID와 정리 책임도 합의한다.

## T10 인계

T15는 후보 diff 바이트의 `sha256`과 제품 이미지 digest, 대상 환경을 준비한다. 단순 해시는 제안과 이미지의 출처·동일성을 증명하지 않는다. T38의 인증된 검증 원문과 독립적인 산출물 대조, 정리 완료, 현재 시도 및 취소·보안 hold 확인을 수행하는 공급자가 있어야 T10의 `CurrentChange`를 반환할 수 있다. 요청 본문이나 미인증 receipt만으로 만드는 변환기는 설치하지 않는다.

승인 결속은 기존 이벤트 스키마의 `plan_id`, `plan_digest`, `diff_hash`, `image_digest`, `target_environment_id`, `expires_at`를 사용한다. T10 공급자 호출에서 불변 `verification_id`와 최신 `revision`을 조회하고, 현재 계획·권한·만료를 승인과 반영 접수 시 다시 검사한다. 이 확인의 저장소, 인증 방식과 트랜잭션 경계는 T10 담당자와 합의한다.

`integration_handoff.prepare_handoff`는 위 논의를 위한 T15 내부 후보값을 만든다. 네임스페이스 UID와 시험 ID, 시도 번호, 정확한 diff 바이트 해시와 이미지 digest를 묶지만, 제안과 diff·이미지가 실제로 동일한 출처라는 증명이나 승인 권한은 없다. T38과 T10의 운영 연결은 구현되어 있지 않다.

`run_once`의 `isolated_verifier` 접점과 `HandoffVerifier`는 성공한 T3 결과를 후보 요청에 전달한다. 기존 verifier와 동시에 지정하면 네임스페이스 생성 전에 차단한다. 테스트는 모의 Job만 사용하고, Job 실행 중 UID 확인·영수증 인증·T10 승인 공급자를 구현하거나 대신하지 않는다.
