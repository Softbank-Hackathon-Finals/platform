# 실제 AWS → 온프렘 해피패스 인수

2026-11-08 KST 확인 기록이다. 실제 앱 이전의 완료 보고가 아니다.
목표는 기존 T10·T14/T19·T12/T13 경로에서 하나의 실제 계획으로 이전을 끝내고 그 결과를 콘솔에 표시하는 것이다.

## 실제 확인과 현재 차단

| 경계 | 확인 결과 | 이 결과로 확인하지 않은 것 |
|---|---|---|
| 개인 AWS 접속 | `bravo-personal` STS 계정·본인 caller 대조 | 제품 운영자 권한 |
| 플랫폼 | 01:27 KST 클러스터 UID 일치, 배포 7개 Ready, GitOps Synced/Healthy | 해피패스 실행 완료·공용 실행 시간 합의 |
| 배포 이미지 | 등록 API·Reader·승인 호스트의 실제 imageID가 GitOps 고정 digest와 일치 | 재현 빌드·T21 호스트 배포 |
| AWS 출발지 | 기존 EKS CA·등록 UID 일치, 자원 9개·관계 7개·관리 HTTP 탐침 1개 | DB 무결성·게이트 PASS |
| 양쪽 지도 | 동일 revision의 실제 API/DOM 29개 자원·27개 관계·HTTP 탐침 선 2개 | 사용자 트래픽·격리·컷오버 |
| 승인 호스트 TLS | 인증된 K8s 경로의 공개 serving 인증서를 서버 한 곳에 고정. self-signature·기한·호스트명·실제 peer 지문 검증 | 운영자 조회 권한 |
| 제품 운영자 조회 | 본인 operator audience SSO의 실제 계획 GET **403 forbidden** | 현재 정본 계획의 상태·승인 가능 여부 |

해당 승인 서버는 self-signed serving 인증서를 사용한다. 이를 issuer CA라고 표시하지 않았다.
Kubernetes에서 배포가 참조하는 공개 인증서만 읽고, 그 서버의 정확한 이름·지문으로 제한했다.
`CERT_REQUIRED`·hostname 검증을 유지하고 부분 체인 플래그나 검증 생략을 사용하지 않았다.
검증 완료 뒤에만 짧은 SSO 증명을 생성했다. 증명·개인 키는 저장하거나 공개하지 않았다.

현재 확인한 승인 호스트의 운영자 목록에는 본인 caller가 없었다. **AWS/Kubernetes 관리자와 제품 운영자는 별도 경계**다.
DB 직접 조회, 다른 사람 신원, 워크로드 자격으로 이 거부를 우회하지 않는다.
기존 역할 UID와 본인 STS를 대조한 신원 추가 초안만 비공개로 준비했고, 등록·계획 grant는 적용하지 않았다.

## 다음 인계

[T28 조율 요청](https://github.com/Softbank-Hackathon-Finals/platform/issues/36#issuecomment-6709988956)에서 다음을 확인한다.

1. **정본 계획:** 지금 해피패스에 쓰는 실제 계획과 보호된 참조. 보존한 예전 계획은 `full/1`이고 현재 catalog에는 `demo-gate`가 보인다. 서로 다른 계획·프로필의 증거를 섞지 않는다.
2. **조회 권한:** 기존 T10 절차로 본인 SSO와 그 계획의 `read`를 연결한다. 먼저 GET/SSE의 실제 계획·버전·진행을 확인한다. 사람 승인과 실행 역할은 원래 분리 조건을 확인해 별도로 연결한다.
3. **공용 실행 시간:** 현재 이미지 롤아웃 종료와 같은 앱·DB·Edge를 쓰는 작업의 충돌 여부. 과거의 빈 시간이나 Ready 상태를 현재 실행 승인으로 사용하지 않는다.

T10·T12의 핵심 코드와 실행 주체는 기존 담당 경로를 유지한다. 신원·권한·공용 설정 변경은 담당 범위를 합의한 뒤 수행한다.

## 한 계획으로 이어갈 실행 순서

| 단계 | 기존 경로 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 시작 상태 | T28 preflight · 정본 계획 GET | 같은 앱·양쪽 환경·계획·프로필·배포 버전 확인, 현재 실행 없음 |
| 최초 비교 | T14 수집 → T10 원문 저장 → T19 | 등록 프로필의 필수 시험 전부와 양쪽 원문 출처. 열린 버킷 등 결함은 실제 BLOCK |
| 변경안 | T10 initial-proposal · T38/T11 | 실제 실행 영수증·후보 발행 digest·원본 계획 결속 |
| 리허설 | T15 · 독립 verifier | 같은 제안의 실제 시험 결과와 정리 기록 |
| 승인·반영 | T10 변경 승인 → T31 | 현재 diff/digest·버전·유효기간·승인자와 반영 주체의 권한 확인, 실제 반영 readback |
| 재대조 | T14/T19 · T13 | 같은 계획의 새 보안·데이터 준비 근거. 과거 PASS를 재사용하지 않음 |
| 전환 준비 | T18 · T8 · SHIFT 직전 재평가 | 실제 관측 창·첨부 복사·최신 무결성 근거와 등록된 정책 충족 |
| 승인·전환 | T10 → T17 → T12/T13 | 현재 결속의 승인, 단일 writer, fencing·최종 비교·쓰기 대상/Edge readback |
| 운영 확인 | 신규 쓰기·첨부·재접속 · T18/T36 | 실제 클라이언트 요청과 신규 데이터 보존, 정본 영수증·관측 창·안정화 결과 |

첫 인수는 `scripts/happy_path.py`의 **migration** 시나리오다. 장애 주입·되돌리기는 별도의 recovery 인수다.
driver의 단계 완료와 T10 계획의 `DONE` 상태를 구분하며, `WATCH`에 도달했다고 완료를 만들지 않는다.
단순 HTTP 탐침 성공을 데이터 무결성·무중단 운영으로 확대하지 않는다.

전체 콘솔의 운영 배포는 이 실행과 별도다. 기존 승인 API/운영 CLI로 실행할 수 있는 접점을 먼저 인수하고,
T21은 같은 정본과 영수증을 읽는다. 합성 UI나 새 상태 머신을 실제 경로 대신 사용하지 않는다.
