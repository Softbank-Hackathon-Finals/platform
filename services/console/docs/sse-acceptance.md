# T21 SSE 구현 검증과 운영 인수

SSE는 T10이 저장한 계획별 이벤트를 콘솔에 전달하는 통신 방식이다.
기존 [이벤트 계약](../../../docs/contracts/T10-events-v1-proposal.md)과
[계획 snapshot 계약](../../../docs/contracts/T10-plan-snapshot-v1-proposal.md)을 사용한다.
이 문서는 새 이벤트 계약이나 판정기를 정의하지 않는다.

## 체크 기준

| 항목 | 확인할 내용 | 완료 근거 |
|---|---|---|
| SSE 구현·로컬 통합 검증 | 실제 T10 API·로컬 SQLite와 브라우저에서 표시, 이어받기, 중복 제거, 순번 누락 거부, 인증 회수 시 자료 철회 | 병합된 코드, 현재 소스 SHA의 Python·JS·브라우저 시험 |
| 결속된 승인 버튼 | 기존 계획·이미지·차이·대상·기한 등 승인 종류별 결속과 별도 서버 인가 | 기존 완료 체크 유지 |
| 실제 운영 SSE 인수 | 인계받은 실제 계획과 본인 신원으로 native T10 조회·이벤트 스트림을 콘솔에서 확인 | 같은 계획·소스·관측 시각·cursor를 연결한 비공개 기록과 공개 요약 |

전체 이전의 성공을 SSE 구현 체크의 선행 조건으로 두지 않는다. 운영 SSE 인수도
DB 컷오버·Edge 전환을 임의로 발생시켜 확인하지 않는다. 전체 T21 완료는 기존
10장 흐름의 콘솔 조작·설명 완료 기준으로 별도 판단한다.

## 기존 구현 위치

| 경로 | 책임 |
|---|---|
| `src/bravo_console/static/transport.js` | 인증된 same-origin fetch 스트림, SSE 프레임, Last-Event-ID |
| `src/bravo_console/static/model.js` | 계획·순번·중복·상태 결속 검사 |
| `src/bravo_console/static/app.js` | 화면 반영·재연결·권한 회수 처리 |
| `src/bravo_console/static/recovery.js` | 조회·실행 구분, 불명확한 요청의 자동 재전송 방지 |
| `tests/test_app.py`, `tests/transport.test.js`, `tests/model.test.js`, `tests/recovery.test.js` | 서버·전송·모델·복구 경계 회귀 |
| `tests/browser/console.spec.js`, `tests/browser/change.spec.js` | 실제 로컬 HTTP·SSE·브라우저의 통합 |

브라우저 시험의 서버는 실제 제품 T10 코드와 임시 SQLite를 사용한다. 신원·업무
입력·승인 공급자는 시험 fixture이므로 팀 운영 성공으로 사용하지 않는다.
기존 관측 지도와 터미널 대응 시험의 주기적 GET은 native 계획 SSE와 구분한다.

## 운영 인수 전 준비

1. T10 담당자가 최신 실제 계획의 보호된 참조와 본인에게 허용한 읽기 범위를 인계한다.
2. 고정 접속 주소와 CA·등록된 서버 신원을 검증한다. 인증서 검증·hostname 검사를
   끄지 않으며, 신뢰가 확인되기 전에 SSO proof를 보내지 않는다.
3. 본인 `bravo-personal` SSO 신원과 계획 GET을 확인한다. Kubernetes 접속 성공을
   T10 앱 권한으로 대신하지 않는다. 403이면 인수 보류로 기록하고 임의 등록하지 않는다.
4. 동일 계획의 `events?follow=false`를 읽어 endpoint와 권한을 확인한다. 보존 이력
   재생은 현재 실시간 이벤트 수신이나 전체 운영 시연 성공을 의미하지 않는다.

현재 인계 요청은 [#872](https://github.com/Softbank-Hackathon-Finals/platform/pull/872)다.
계획·자격·운영 식별자는 보호된 경로로 전달하고 공개 이슈에 붙이지 않는다.

## 운영 인수 실행

| 확인 | 실행 방법 | 통과 기준 |
|---|---|---|
| 초기 상태 | 같은 계획 snapshot과 이벤트 watermark 조회 | 계획·버전·cursor가 일치하며 다른 계획 자료가 섞이지 않음 |
| 실시간 표시 | 합의된 진행 중 실제 실행이 발생시킨 새 이벤트 관측 | 서버 저장 이벤트 ID·순번과 콘솔 표시가 일치 |
| 재접속 | 해당 브라우저 연결만 종료·재연결 | 마지막 처리 ID 다음부터 재생, 이미 처리한 이벤트 중복 적용 없음 |
| 누락·만료 cursor | 격리된 로컬 시험에서 검증 | 오류를 표시하고 실행 잠금. 운영 이력을 삭제하거나 cursor를 임의 전진하지 않음 |
| 권한 경계 | 운영자와 합의한 본인 전용 시험 세션으로 확인 | 읽기 회수 시 스트림·기존 화면 자료 철회. 실제 권한 변경은 담당자의 별도 승인 범위 |
| 작업 마무리 | 시험에 연 로컬 스트림만 종료 | 공용 Pod·계획·DB·Edge·다른 사용자 세션에 변경 없음 |

실시간 이벤트가 아직 없으면 수신 대기 또는 보존 이력 확인까지만 기록한다.
heartbeat는 연결 생존 증거이며 업무 진행·게이트 PASS가 아니다.
403·연결 실패·미확인은 인수 완료로 바꾸지 않는다.

## 근거와 체크 절차

현재 소스 SHA, 시험 명령·종료 상태·모의/실제 범위와 운영 인계 조건을 공개 요약에
남긴다. 실제 계획·사용자·원문·cursor·접속 자료는 비공개 원본에 연결한다.
SSE 코드·로컬 통합 검증 항목은 해당 계획 문구 변경 PR 병합 뒤 이슈 #27에서
체크한다. 운영 인수 항목은 실제 근거가 생기기 전까지 미완료를 유지한다.
`docs/tasks.md`의 진행 체크는 직접 고치지 않고 기존 sync-tasks 경로를 사용한다.

| `transport.test.js`, `model.test.js`, `recovery.test.js` | 49개 통과 | 프레임·순번·중복·이어받기·누락·권한·재전송 경계 |
| Chromium | 선정한 6개 시나리오 통과 | 로컬 HTTP·SSE 표시, 누락 시 잠금, 인증 거부·회수, 등록 응답 유실·S2 승인 |
| WebKit | 같은 6개 시나리오 통과 | Chromium과 분리한 새 임시 T10/SQLite 서버 |

브라우저는 `console.spec.js`와 `change.spec.js`에서 위 여섯 시나리오를 선택했다.
전체 브라우저 시험을 실행한 것으로 표시하지 않는다. 최초에는 두 브라우저가
변경되는 시험 계획을 공유해 8개 통과·4개 실패했다. 그 결과를 보존하고 브라우저별
독립 서버로 재실행했다. 제품 코드 변경이나 타임아웃 연장·재시도·시험 제외로
통과시킨 것이 아니다.

같은 날 별도 운영 재확인에서는 본인 SSO·클러스터 신원은 유효했지만 기존 계획 GET과
동일 계획 SSE GET이 모두 `403 forbidden`이었다. 서버 인증서·등록 신원 검증 후
조회했으며 등록·승인·권한 변경·컷오버는 하지 않았다. 따라서 위 로컬 통과 근거는
첫 구현 항목에만 사용하고 운영 인수와 전체 T21에는 사용하지 않는다.

원본 실행 보고서·초기 실패·운영 재확인은 비공개 검증 폴더에 보존한다.
